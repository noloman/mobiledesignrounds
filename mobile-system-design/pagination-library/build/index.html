Draft v1. Companion to the pagination library interview case.

This is the implementation material behind the pagination library interview case. It covers:

  • The public surface and key styles
  • The state model and engine rules
  • The mediator (the hook that writes fetched pages into a database) and versioning
  • The Swift side and platform limits

None of it belongs in the 45 minutes. I draw it only if asked.

The sketches are simplified and are not the real Paging 3 signatures. They were compiled against Paging 3.4.2; Paging 3.5.3 is current as of 2026-10-14. Room (Android's database library) appears only in prose here. The official Room guide now shows Room 3 (androidx.room3), and the architecture is the same either way.

1. Public API surface and what stays internal

The rule: expose the fewest types that let a consumer do everything, and make every extra public type earn its place.

Public:

  • PageSource<K, V>: one suspend function to load a page, plus a refresh key function (section 2).
  • PagingConfig: page size, prefetch distance, initial load size, max cached items, placeholders flag.
  • LoadState and CombinedLoadStates: the state model (section 3).
  • PagingData<V>: the opaque snapshot you hand to the UI adapter.
  • Mediator: the optional hook for database-backed paging (section 6).
  • PagingEvents: the observability interface (section 7).

Internal:

  • The fetcher, the coordinator and the page store
  • The prefetch policy and retry scheduling
  • The diffing glue

Consumers must not be able to reach any of these, not even by reflection or by guessing class names.

Enforcement tools:

  • Kotlin internal plus explicit API mode, which forces a visibility decision on every declaration.
  • A binary-compatibility checker in CI that diffs the public API dump on every pull request. Kotlin's guidelines for library authors describe the validator.
  • Swift package or internal access, plus library evolution settings when you ship a binary framework.

Two design habits matter here:

  • Sealed results over exceptions for expected outcomes. A page load returns Page or Error, not "throws sometimes".
  • Stay closed by default. You can open a class later without breaking anyone. You cannot close one.

2. Generics and the data source abstraction

The library should know nothing about how a key is encoded. A generic key type covers all three styles.

// Sketch: the core contract
interface PageSource<K : Any, V : Any> {
    suspend fun load(params: LoadParams<K>): LoadResult<K, V>
    fun refreshKey(state: PagingState<K, V>): K?     // where to restart after invalidation
}

sealed interface LoadParams<K> {
    val key: K?            // null on first load
    val loadSize: Int
    class Refresh<K>(override val key: K?, override val loadSize: Int) : LoadParams<K>
    class Append<K>(override val key: K, override val loadSize: Int) : LoadParams<K>
    class Prepend<K>(override val key: K, override val loadSize: Int) : LoadParams<K>
}

sealed interface LoadResult<K, V> {
    data class Page<K, V>(val data: List<V>, val prevKey: K?, val nextKey: K?) : LoadResult<K, V>
    data class Error<K, V>(val cause: Throwable) : LoadResult<K, V>
}

How each key style fits:

StyleKnextKeyPitfall
Page numberIntkey + 1Skips or repeats rows when data is inserted mid-scroll
OffsetIntkey + loadSizeSame drift problem, plus slow deep offsets on the server
CursorString (opaque)Server valueCursors can expire; need a restart path

Steer consumers toward cursors in the docs, but do not forbid the others; you will not control every backend.

refreshKey is the easy-to-miss part. PagingState is the snapshot of what is on screen; the sketch borrows Paging 3's type.

When data is invalidated, the library asks the source where to restart. The user keeps their scroll position instead of jumping to the top. Paging 3 has the same idea. The load-and-display page describes the key as the one passed to load when data is refreshed or invalidated after the first load.

The loaded size is passed in, not hard-coded, because the initial load is usually larger than later pages. The source should treat loadSize as a hint it may ignore, and the library must cope with a short or long page.

Known gaps in the sketch above. The compile check and the doc read on 2026-10-14 found these; I left the code as compiled and list the changes here.

  • PageSource has two members, not one: load and refreshKey.
  • Paging 3 documents an invalid result: a source that is no longer valid, for example after an underlying data change, returns it so the library replaces the source. LoadResult here has only Page and Error. I would add an Invalid case.
  • LoadResult.Page has no counts of items before and after the page. Placeholders (null items for rows not yet loaded) need those counts, so the sketch cannot express them. Paging also needs nextKey and prevKey for placeholders and jumping.
  • Paging 3.4 added PagingState.closestItemAroundPosition, an item-based way to build a refresh key when the ideal anchor is near, not at, the target position.

3. State model

Consumers build spinners, retry rows and empty views from this, so it is the most-used part of the API. Paging 3 models it as three states per load type:

  • NotLoading with an endOfPaginationReached flag.
  • Loading.
  • Error carrying the cause.

Load types are refresh (initial or restart), prepend and append. A combined object also carries state for the source and for the mediator separately, so UI can tell "reading the local database" from "syncing with the network".

sealed interface LoadState {
    data class NotLoading(val endReached: Boolean) : LoadState
    data object Loading : LoadState
    data class Error(val cause: Throwable) : LoadState
}

data class CombinedLoadStates(
    val refresh: LoadState, val prepend: LoadState, val append: LoadState,
    val source: LoadStates, val mediator: LoadStates?,
)

LoadStates, the per-source type, is not defined in the sketch. It is a refresh, prepend and append triple.

Design points I'd make here:

  • Separate refresh from append. A failed append should leave the list on screen with a retry row. A failed refresh with no data should show a full-screen error. One combined "loading" flag cannot express either.
  • End of list is a state, not an error. Model it as NotLoading(endReached = true) so UI can show a footer.
  • Retry and refresh are two verbs. retry() repeats only the failed load. refresh() discards the generation and starts over. This split is my design; the load-state page shows retry() in its click handlers and does not contrast it with refresh.
  • Loading footers and placeholders conflict. The load-state page says its footer example only works with placeholders disabled; otherwise the footer appears after the placeholders.
  • Emit distinct values only. Collapse repeated identical states so UI does not recompose for nothing.
  • Make states cheap to compare. Plain value types, no lambdas inside state. The sketch uses data classes for brevity. Kotlin's library guidelines list "avoid using data classes in your API" as a compatibility rule, so a shipped library would hand-write them.

4. Cache, deduplication, cancellation and prefetch

All of this lives in the internal engine, and consumers see it only through config.

In-memory cache. Keep loaded pages in a bounded store. With maxSize set, drop pages from the end farthest from the viewport.

  • Check the config when it is built. If maxSize is smaller than pageSize + 2 * prefetchDistance, fail fast with a clear message instead of thrashing at runtime.
  • Paging 3 enforces exactly this rule in PagingConfig and throws IllegalArgumentException. Its maxSize default is unbounded.
  • Paging 3 documents in-memory caching as built in. The 3.5.3 release notes add that at least two pages stay loaded when the cap is exceeded.

Request deduplication. Track at most one in-flight load per direction. A second append request while one is running joins the first or is dropped. Without this, a fast scroll fires ten requests for the same key. Paging 3 lists built-in request deduplication among its features.

Generations. Tag each refresh with a generation number. Results from a cancelled generation are discarded, even if the network call finished. This closes the race where a slow old response overwrites a fresh refresh.

Prioritization and cancellation.

  • Refresh outranks append. Starting a refresh cancels any running append or prepend.
  • A visible-range load outranks a speculative prefetch.
  • Cancellation is cooperative. On Android, the load runs in a coroutine, and cancelling the scope cancels the call if the source uses cancellable suspend functions. Document that sources must not swallow CancellationException.
  • When the stream has no collectors, stop loading and release pages, unless the app opted into caching beyond the collector's lifetime.

Prefetch distance. Config field prefetchDistance: how many items from the loaded edge the user may be before the next page is requested. Defaults and trade-offs:

  • Too small: users see the end and wait.
  • Too large: wasted requests and memory, and extra data on cellular.
  • A sensible default is one page size. Paging 3's default is also one page size (prefetchDistance = pageSize in PagingConfig), and its initial load defaults to three pages.

Let consumers set it, and let the library clamp it so a huge value cannot defeat maxSize.

Config defaults and rules, as read from the PagingConfig source on 2026-10-13:

5. Threading and concurrency contract

Write this down as part of the API, because it is the thing integrators break first.

  • PageSource.load is called from the library's dispatcher, one call at a time per direction, and may suspend.
  • load must be main-safe: the library never calls it on the main thread, and the source need not switch threads for ordinary work. State this explicitly, or every consumer will add a redundant withContext.
  • State and data are emitted on a documented context. Choose one (for example, the collector's context) and never change it in a minor release.
  • Internal state is confined to one serialized context (a single-threaded dispatcher or a mutex-guarded actor), not scattered locks.
  • Public classes are immutable or documented as thread-safe. PagingData is a snapshot and is safe to pass between threads.
  • No hidden global singletons. A Pager owns its state, so two lists never share a cache by accident.

6. Composing with a local database

The library should not require a database, but it should make the database path easy. Paging 3's design is the template. The database is the source of truth. A RemoteMediator fetches from the network when the cached range runs out and writes results into the database. A database-generated PagingSource feeds the UI. Inserting data invalidates the source, and a new generation reads the updated rows.

// Sketch: mediator contract, shape adapted from the Paging 3 network-and-database
// sample (Apache License 2.0), https://developer.android.com/topic/libraries/architecture/paging/v3-network-db
interface Mediator<K : Any, V : Any> {
    suspend fun initialize(): InitializeAction      // skip or launch the first refresh
    suspend fun load(type: LoadType, state: PagingState<K, V>): MediatorResult
}

Invalidation is the part people forget. When a row is edited, deleted or inserted underneath the list, the database-backed source invalidates itself. The library starts a new generation, and refreshKey picks the restart position so the user stays near the same item. With Room that trigger comes for free. With a hand-rolled source the app has to call invalidate itself, which is why the contract should say so.

What the library guarantees, and what the app owns:

Library:

  • Call initialize() first. If it asks for a refresh, hold appends until the refresh succeeds.
  • Surface mediator state separately from source state.
  • Cancel a mediator load when the generation ends.

App:

  • Store remote keys.
  • Run the refresh as one transaction.
  • Clear old rows only after the network succeeds.
  • Keep local pending changes when merging server data.

In offline-first terms the mediator pulls from the server on demand, as the user scrolls. The news feed build guide section 2 has a full mediator, and the offline-first guide covers the wider write and sync choices.

A mediator result is Success(endReached) or Error(cause). The mediator reports "end reached" by return value, not by an empty page, so the library does not guess. The sketch also uses three types it does not list in section 1 (LoadType, InitializeAction, MediatorResult). In Paging 3 the last two are nested in RemoteMediator.

7. Testability, versioning and observability

Testability. Ship test tooling as a separate artifact so production code does not carry it. Paging 3 does this with a testing module:

  • TestPager loads a source page by page.
  • asSnapshot collects a stream while you simulate scrolling.
  • asPagingSourceFactory builds fake sources from lists. A flow of lists simulates invalidation.

Mediator tests check the returned result (valid data, empty response, thrown exception) and use an in-memory database. Make time injectable (a clock and a dispatcher parameter) so tests do not sleep.

The integration I'd put in the one page of docs matters as much as the internals (a sketch against my API, not compiled):

class FeedViewModel(source: PageSource<String, Post>) : ViewModel() {
    val posts = Pager(PagingConfig(pageSize = 20), source).flow.cachedIn(viewModelScope)
}

@Composable
fun FeedScreen(vm: FeedViewModel) {
    val items = vm.posts.collectAsLazyPagingItems()
    LazyColumn { items(items.itemCount) { i -> items[i]?.let { PostRow(it) } } }
}

Versioning and compatibility.

  • Use semantic versioning: removals and signature changes are major; additions are minor; fixes are patch.
  • Behavior is API. Changing a default page size, an error type, a callback thread or the retry policy is a breaking change for someone, even if the compiler is silent.
  • Deprecate before removing: mark the symbol deprecated with a replacement and keep it for a stated window (for example, two minor releases and at least six months). Warn at build time, not at runtime.
  • Binary compatibility: on Android, avoid changing public method signatures or adding abstract members to public interfaces (use default methods or new interfaces). Use a binary-compatibility validator in CI. On iOS, a binary XCFramework needs library evolution mode and @frozen used sparingly.
  • Config as a builder or a data class with defaults. Adding a field with a default is compatible; reordering constructor parameters is not. Prefer named parameters.
  • Ship a sample app and run it against each release as a contract test.

Observability. Provide an opt-in listener, not a logging dependency.

interface PagingEvents {
    fun onLoadStarted(type: LoadType, key: Any?) {}
    fun onLoadFinished(type: LoadType, durationMs: Long, itemCount: Int, error: Throwable?) {}
    fun onCacheHit(pageCount: Int) {}
    fun onGenerationCancelled(reason: String) {}
}

Keep payloads free of item contents so the hook is safe to forward to analytics. Default to a no-op. The aim is for each host app to answer "how slow are our pages, and how often do they fail" without patching the library.

One gap: onLoadStarted as sketched passes the raw page key, and a cursor can encode user data. I would pass a key kind (offset, page number, cursor) instead of the key.

8. Doing it on iOS

The design carries over unchanged: a generic page source, a state model, an engine with one in-flight load per direction, and an optional database mediator. I know of no official Apple paging library, so the iOS version is the part you build and own.

The Paging release notes list iOS among the native targets of the common modules (3.3 for iOS compatibility, 3.4 for more targets). A Kotlin-compiled core is therefore a real alternative; section 1 of the interview page says what I would test before choosing. Swift concurrency supplies the primitives:

  • async functions for loads
  • Structured Task cancellation
  • An actor (a type that guards its own state) for engine state
  • AsyncSequence (most often AsyncStream) for results

// Sketch: iOS public surface (signatures only)
public protocol PageSource<Key, Item>: Sendable {
    associatedtype Key: Sendable
    associatedtype Item: Sendable
    func load(_ params: LoadParams<Key>) async throws -> Page<Key, Item>
}

public actor Pager<Key: Sendable, Item: Sendable> {
    public init(source: some PageSource<Key, Item>, config: PagingConfig)
    // One stream per call, built with .bufferingNewest(1); snapshot must be Sendable
    public func updates() -> AsyncStream<PagingSnapshot<Item>>
    public func loadMoreIfNeeded(visibleIndex: Int) async
    public func refresh() async
    public func retry() async
}

What changes on iOS:

  • One stream per subscriber. An AsyncStream is meant for a single consumer. Apple's page does not spell it out, but the proposal that added it, SE-0314, calls concurrent iteration a programmer error. If two views, or a view and a test, iterate the same stream they will compete for elements.
  • So updates() is meant to create a stream per call. The sketch shows signatures only. The implementation keeps the continuations inside the actor and uses .bufferingNewest(1), because only the latest snapshot matters. An @Observable snapshot is the other option.
  • Swift cancellation is cooperative. Cancelling the task that reads an AsyncSequence does not force the source to stop. Document that sources must check for cancellation, and clean up in the continuation's onTermination callback, which Apple documents as called when iteration is cancelled. Keep that callback non-blocking: Apple says it carries the same deadlock considerations as withTaskCancellationHandler.
  • Sendable shows up in the API. Key and item types must be Sendable to cross the actor boundary. State that requirement in the public signature instead of discovering it in a consumer's build.
  • No built-in list integration. You ship thin adapters, kept in a separate module so the core stays toolkit-free. One is a SwiftUI helper that calls loadMoreIfNeeded from onAppear. The other is a UIKit prefetching delegate.
  • Prefetch is a hint. Apple's prefetching page says the callback is not necessarily called for every cell. The cell provider must handle data that is ready, in flight or never requested. The lazy vertical stack page says nothing about appear callbacks, so the SwiftUI trigger is design intent.
  • Binary distribution has stricter rules. If you ship an XCFramework, library evolution constrains what you can change; if you ship source via Swift Package Manager, source compatibility is the main concern. Decide which you offer.

10. More practice prompts

Practice prompts, not a claim about what any interviewer asks; chosen by me, and reconstructed like the pushes on the interview page.

  1. How do you remove an API that thirty apps use? (Deprecation window, replacement, telemetry on usage, a codemod or migration guide, then a major release.)
  2. How do you test the library itself? (Fake sources, a controlled dispatcher, property tests on generation races, a sample app run against each release.)
  3. How would you add placeholders? (A nullable item list plus a known total; explain the cost when the total is unknown, and the footer conflict in section 3.)
  4. How do you make list scrolling and image loading cooperate? (Cancel prefetched image work for rows scrolled past; see image loading.)
  5. Someone proposes a thin wrapper around Paging 3 instead of a library. What do you check? (What the wrapper would hide, what the 3.5 item-snapshot flow already exposes, and who owns the wrapper's versioning.)
