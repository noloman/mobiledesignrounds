This is the build material behind the pagination library interview case. It covers:

  • The public surface and key styles
  • The state model and engine rules
  • The mediator (the hook that writes fetched pages into a database) and versioning
  • The Swift side and platform limits

None of it belongs in a 45-minute round (the length I assume). I draw it only if asked.

The sketches are simplified. They are not the real Paging 3 signatures. I compiled them against Paging 3.4.2. Paging 3.5.3 is current as of 2026-10-14. Room (Android's database library) appears only in prose here. The official Room guide now shows Room 3 (androidx.room3). The design is the same with either version.

1. Public API surface and what stays internal

The rule: show the fewest types that let a user of the library do everything. Every extra public type must earn its place.

Public:

  • PageSource<K, V>: one suspend function to load a page, plus a refresh key function (section 2).
  • PagingConfig: page size, prefetch distance (how far ahead to load), initial load size, max cached items, and a placeholders flag.
  • LoadState and CombinedLoadStates: the state model (section 3).
  • PagingData<V>: the opaque snapshot that you give to the UI adapter. Opaque means the user cannot look inside it.
  • Mediator: the optional hook for paging that uses a database (section 6).
  • PagingEvents: the interface for watching what the library does (section 7).

Internal:

  • The fetcher, the coordinator and the page store
  • The prefetch policy and retry timing
  • The diffing glue (code that finds the changes between two lists)

Users of the library must not be able to reach any of these. Reflection (code that finds classes at run time) and guessing class names must not work either.

Tools that enforce this:

  • Kotlin internal plus explicit API mode, which forces a choice of visibility for every declaration.
  • A binary-compatibility checker in CI (the automatic checks that run on every change). It compares the public API dump on every pull request. Kotlin's guidelines for library authors describe the validator.
  • Swift package or internal access, plus library evolution settings when you ship a binary framework.

Two design habits matter here:

  • Sealed results over exceptions for expected outcomes. A page load returns Page or Error. It does not "throw sometimes".
  • Stay closed by default. You can open a class later without breaking anyone. You cannot close one.

2. Generics and the data source abstraction

The library should know nothing about how a key is encoded. A generic key type covers all three styles.

// Sketch: the core contract
interface PageSource<K : Any, V : Any> {
    suspend fun load(params: LoadParams<K>): LoadResult<K, V>
    fun refreshKey(state: PagingState<K, V>): K?     // where to restart after invalidation
}

sealed interface LoadParams<K> {
    val key: K?            // null on first load
    val loadSize: Int
    class Refresh<K>(override val key: K?, override val loadSize: Int) : LoadParams<K>
    class Append<K>(override val key: K, override val loadSize: Int) : LoadParams<K>
    class Prepend<K>(override val key: K, override val loadSize: Int) : LoadParams<K>
}

sealed interface LoadResult<K, V> {
    data class Page<K, V>(val data: List<V>, val prevKey: K?, val nextKey: K?) : LoadResult<K, V>
    data class Error<K, V>(val cause: Throwable) : LoadResult<K, V>
}

How each key style fits:

StyleKnextKeyPitfall
Page numberIntkey + 1Skips or repeats rows when data is inserted mid-scroll
OffsetIntkey + loadSizeSame drift problem, plus slow deep offsets on the server
CursorString (opaque)Server valueCursors can expire; need a restart path

In the docs, steer users toward cursors. Do not forbid the others, because you will not control every backend.

refreshKey is the part that people miss. PagingState is the snapshot of what is on screen. The sketch borrows the type from Paging 3.

When data changes, the library asks the source where to restart. The user keeps the scroll position and does not jump to the top. Paging 3 has the same idea. The load-and-display page says the key is the one passed to load when data is refreshed or invalidated after the first load.

The loaded size is passed in, not fixed in code. The initial load is usually larger than later pages. The source should treat loadSize as a hint that it may ignore. The library must work with a short or long page.

Known gaps in the sketch above. The compile check and the doc read on 2026-10-14 found these. I left the code as compiled and list the changes here.

  • PageSource has two members, not one: load and refreshKey.
  • Paging 3 documents an invalid result. A source that is no longer valid, for example after a change in the underlying data, returns it so the library replaces the source. LoadResult here has only Page and Error. I would add an Invalid case.
  • LoadResult.Page has no counts of items before and after the page. Placeholders (null items for rows not yet loaded) need those counts, so the sketch cannot express them. Paging also needs nextKey and prevKey for placeholders and jumping.
  • Paging 3.4 added PagingState.closestItemAroundPosition. It helps to build a refresh key from an item when the best anchor is near the target position, not at it.

3. State model

Users of the library build spinners, retry rows and empty views from this model. So it is the most used part of the API. Paging 3 models it as three states for each load type:

  • NotLoading with an endOfPaginationReached flag.
  • Loading.
  • Error with the cause.

The load types are refresh (the first load or a restart), prepend and append. A combined object also holds state for the source and for the mediator, kept apart. So the UI can tell "reading the local database" from "syncing with the network".

sealed interface LoadState {
    data class NotLoading(val endReached: Boolean) : LoadState
    data object Loading : LoadState
    data class Error(val cause: Throwable) : LoadState
}

data class CombinedLoadStates(
    val refresh: LoadState, val prepend: LoadState, val append: LoadState,
    val source: LoadStates, val mediator: LoadStates?,
)

LoadStates, the type for one source, is not defined in the sketch. It is a refresh, prepend and append triple.

Design points I would make here:

  • Separate refresh from append. A failed append should leave the list on screen with a retry row. A failed refresh with no data should show a full-screen error. One combined "loading" flag cannot show either.
  • End of list is a state, not an error. Model it as NotLoading(endReached = true) so the UI can show a footer.
  • Retry and refresh are two verbs. retry() repeats only the failed load. refresh() discards the generation and starts over. This split is my design. The load-state page shows retry() in its click handlers. It does not compare it with refresh.
  • Loading footers and placeholders conflict. The load-state page says its footer example works only with placeholders off. With placeholders on, the footer appears after the placeholders.
  • Emit only values that changed. Merge repeated identical states, so the UI does not redraw for no reason.
  • Make states cheap to compare. Use plain value types, with no lambdas inside state. The sketch uses data classes to be short. Kotlin's library guidelines list "avoid using data classes in your API" as a compatibility rule. So a shipped library would write them by hand.

4. Cache, duplicate requests, cancellation and prefetch

All of this lives in the internal engine. Users of the library see it only through the config.

In-memory cache. Keep loaded pages in a bounded store. When maxSize is set, drop pages from the end that is farthest from the visible rows.

  • Check the config when it is built. If maxSize is smaller than pageSize + 2 * prefetchDistance, fail at once with a clear message. The other choice is to thrash (load and drop the same pages again and again) at run time.
  • Paging 3 enforces exactly this rule in PagingConfig and throws IllegalArgumentException. Its maxSize default is unbounded.
  • Paging 3 documents in-memory caching as built in. The 3.5.3 release notes add that at least two pages stay loaded when the cap is passed.

Request deduplication (joining duplicate requests into one). Allow at most one running load for each direction. A second append request while one is running joins the first or is dropped. Without this, a fast scroll sends ten requests for the same key. Paging 3 lists built-in request deduplication among its features.

Generations. Give each refresh a generation number. Discard results from a cancelled generation, even if the network call finished. This closes the race where a slow old response replaces a fresh refresh.

Priority and cancellation.

  • Refresh outranks append. Starting a refresh cancels any running append or prepend.
  • A load for visible rows outranks a guess-ahead prefetch.
  • Cancellation is cooperative, which means the code must check for it. Nothing stops the code by force. On Android, the load runs in a coroutine. Cancelling the scope cancels the call if the source uses suspend functions that can be cancelled. Document that sources must not swallow CancellationException.
  • When the stream has no collectors, stop loading and release pages. The exception is when the app chose to cache beyond the life of the collector.

Prefetch distance. The config field is prefetchDistance. It sets how many items from the loaded edge the user may be before the next page is requested. Defaults and trade-offs:

  • Too small: users see the end and wait.
  • Too large: wasted requests and memory, and extra data on a cellular network.
  • A sensible default is one page size. Paging 3 also uses one page size (prefetchDistance = pageSize in PagingConfig). Its initial load defaults to three pages.

Let users of the library set the distance. Let the library clamp it (cut it to a safe limit), so a huge value cannot defeat maxSize.

5. Threading and concurrency contract

Write this down as part of the API. Users of the library break it first.

  • PageSource.load is called from the library's dispatcher (the thread pool that runs its work). It runs one call at a time for each direction, and it may suspend.
  • load must be main-safe. The library never calls it on the main thread, and the source does not need to switch threads for ordinary work. Say this clearly. If you do not, every user adds an extra withContext.
  • State and data are emitted on a documented context. Choose one, for example the context of the collector. Never change it in a minor release.
  • Internal state stays in one serialized context. This is a single-threaded dispatcher or an actor guarded by a mutex (a lock that lets one caller in at a time). Do not scatter locks through the code.
  • Public classes are immutable (they never change) or are documented as thread-safe. PagingData is a snapshot and is safe to pass between threads.
  • No hidden global singletons. A Pager owns its state, so two lists never share a cache by accident.

6. Composing with a local database

The library should not require a database, but it should make the database path easy. Paging 3 is the model to follow. The database is the source of truth.

A RemoteMediator fetches from the network when the cached range runs out. It writes the results into the database. A source made by the database feeds the UI. When data is inserted, the source becomes invalid, and a new generation reads the updated rows.

// Sketch: mediator contract, shape adapted from the Paging 3 network-and-database
// sample (Apache License 2.0), https://developer.android.com/topic/libraries/architecture/paging/v3-network-db
interface Mediator<K : Any, V : Any> {
    suspend fun initialize(): InitializeAction      // skip or launch the first refresh
    suspend fun load(type: LoadType, state: PagingState<K, V>): MediatorResult
}

Invalidation is the part people forget. A row may be edited, deleted or inserted under the list. Then the database-backed source invalidates itself. The library starts a new generation, and refreshKey picks the restart position. So the user stays near the same item.

With Room, that trigger comes for free. With a source that you write by hand, the app must call invalidate itself. This is why the contract should say so.

What the library guarantees, and what the app owns:

Library:

  • Call initialize() first. If it asks for a refresh, hold appends until the refresh succeeds.
  • Show mediator state apart from source state.
  • Cancel a mediator load when the generation ends.

App:

  • Store remote keys.
  • Run the refresh as one transaction (all changes are saved together or not at all).
  • Clear old rows only after the network call succeeds.
  • Keep local changes that are not yet sent when merging server data.

In offline-first terms, the mediator pulls from the server on demand, as the user scrolls. The news feed build guide section 2 has a full mediator. The offline-first guide covers the wider choices for writing and syncing.

A mediator result is Success(endReached) or Error(cause). The mediator reports "end reached" by return value, not by an empty page, so the library does not guess. The sketch also uses three types that section 1 does not list: LoadType, InitializeAction and MediatorResult. In Paging 3, the last two are nested in RemoteMediator.

7. Testability, versioning and observability

Testability. Ship test tools as a separate artifact, so production code does not carry them. Paging 3 does this with a testing module:

  • TestPager loads a source page by page.
  • asSnapshot collects a stream while you simulate scrolling.
  • asPagingSourceFactory builds fake sources from lists. A flow of lists simulates invalidation.

Mediator tests check the returned result (valid data, empty response, thrown exception) and use an in-memory database. Make time injectable (pass in a clock and a dispatcher), so tests do not need to sleep.

The use example in the one page of docs matters as much as the internals. This is a sketch against my API. I did not compile it:

class FeedViewModel(source: PageSource<String, Post>) : ViewModel() {
    val posts = Pager(PagingConfig(pageSize = 20), source).flow.cachedIn(viewModelScope)
}

@Composable
fun FeedScreen(vm: FeedViewModel) {
    val items = vm.posts.collectAsLazyPagingItems()
    LazyColumn { items(items.itemCount) { i -> items[i]?.let { PostRow(it) } } }
}

Versioning and compatibility.

  • Use semantic versioning (the version number tells the size of the change). Removals and signature changes are major. Additions are minor. Fixes are patch.
  • Behavior is API. A change to a default page size, an error type, a callback thread or the retry policy breaks something for someone, even if the compiler says nothing.
  • Deprecate before you remove. Mark the symbol deprecated with a replacement. Keep it for a stated period, for example two minor releases and at least six months. Warn at build time, not at run time.
  • Binary compatibility: on Android, do not change public method signatures. Do not add abstract members to public interfaces. Use default methods or new interfaces. Use a binary-compatibility validator in CI. On iOS, a binary XCFramework needs library evolution mode, and @frozen should be used rarely.
  • Make config a builder or a data class with defaults. Adding a field with a default is compatible. Changing the order of constructor parameters is not. Prefer named parameters.
  • Ship a sample app and run it against each release as a contract test.

Observability. Give an opt-in listener, not a logging dependency.

interface PagingEvents {
    fun onLoadStarted(type: LoadType, key: Any?) {}
    fun onLoadFinished(type: LoadType, durationMs: Long, itemCount: Int, error: Throwable?) {}
    fun onCacheHit(pageCount: Int) {}
    fun onGenerationCancelled(reason: String) {}
}

Keep payloads free of item contents, so the hook is safe to send to analytics. Default to a no-op (a listener that does nothing). The aim is that each host app can answer "how slow are our pages, and how often do they fail" without changing the library.

One gap: onLoadStarted as sketched passes the raw page key, and a cursor can encode user data. I would pass a key kind (offset, page number, cursor) instead of the key.

8. Doing it on iOS

The design carries over unchanged: a generic page source, a state model, an engine with one running load for each direction, and an optional database mediator. I know of no official Apple paging library. So the iOS version is the part you build and own.

The Paging release notes list iOS among the native targets of the common modules (3.3 for iOS compatibility, 3.4 for more targets). A core compiled from Kotlin is therefore a real option. Section 1 of the interview page says what I would test before choosing. Swift concurrency gives the building blocks:

  • async functions for loads
  • Structured Task cancellation
  • An actor (a type that guards its own state) for engine state
  • AsyncSequence (most often AsyncStream) for results

// Sketch: iOS public surface (signatures only)
public protocol PageSource<Key, Item>: Sendable {
    associatedtype Key: Sendable
    associatedtype Item: Sendable
    func load(_ params: LoadParams<Key>) async throws -> Page<Key, Item>
}

public actor Pager<Key: Sendable, Item: Sendable> {
    public init(source: some PageSource<Key, Item>, config: PagingConfig)
    // One stream per call, built with .bufferingNewest(1); snapshot must be Sendable
    public func updates() -> AsyncStream<PagingSnapshot<Item>>
    public func loadMoreIfNeeded(visibleIndex: Int) async
    public func refresh() async
    public func retry() async
}

What changes on iOS:

  • One stream per subscriber. An AsyncStream is meant for a single consumer. Apple's page does not say this directly. But the proposal that added it, SE-0314, calls concurrent iteration a programmer error. If two views, or a view and a test, read the same stream, they compete for items.
  • So updates() is meant to create a stream on each call. The sketch shows signatures only. The real code keeps the continuations inside the actor and uses .bufferingNewest(1), because only the latest snapshot matters. An @Observable snapshot is the other option.
  • Swift cancellation is cooperative. Cancelling the task that reads an AsyncSequence does not force the source to stop. Document that sources must check for cancellation. Clean up in the continuation's onTermination callback, which Apple documents as called when iteration is cancelled. Keep that callback non-blocking. Apple says it has the same deadlock risks as withTaskCancellationHandler.
  • Sendable appears in the API. Key and item types must be Sendable (safe to pass between threads) to cross the actor boundary. State this requirement in the public signature. Do not let a user find it in their own build.
  • No built-in list integration. You ship thin adapters in a separate module, so the core stays free of any UI toolkit. One is a SwiftUI helper that calls loadMoreIfNeeded from onAppear. The other is a UIKit prefetching delegate.
  • Prefetch is a hint. Apple's prefetching page says the callback is not necessarily called for every cell. The cell provider must handle data that is ready, running or never requested. The page for the lazy vertical stack says nothing about appear callbacks. So the SwiftUI trigger is design intent.
  • Binary distribution has stricter rules. If you ship an XCFramework, library evolution limits what you can change. If you ship source through Swift Package Manager, source compatibility is the main concern. Decide which one you offer.

10. More practice prompts

These are practice prompts, not a claim about what any interviewer asks. I chose them, and I reconstructed them like the follow-up questions on the interview page.

  1. How do you remove an API that thirty apps use? (Deprecation period, replacement, telemetry on usage, a codemod or migration guide, then a major release.)
  2. How do you test the library itself? (Fake sources, a controlled dispatcher, property tests on generation races, a sample app run against each release.)
  3. How would you add placeholders? (A nullable item list plus a known total. Explain the cost when the total is unknown, and the footer conflict in section 3.)
  4. How do you make list scrolling and image loading work together? (Cancel prefetched image work for rows scrolled past; see image loading.)
  5. Someone proposes a thin wrapper around Paging 3 instead of a library. What do you check? (What the wrapper would hide, what the 3.5 item-snapshot flow already exposes, and who owns the wrapper's versioning.)

Words on this page (14)
Actor
A Swift type that runs one task at a time. This keeps its data safe when many tasks use it.
Coroutine
A light background task in Kotlin. It can pause and continue later without blocking a thread.
Cursor
A saved place in a list. The server gives it to the app, and the app sends it back to get the next part.
Dedupe
To keep only one copy of the same item. For example, a message that arrives twice is stored once.
Host app
The app that contains an SDK. You write the SDK, and another team writes the host app.
Main thread
The thread that draws the screen. If slow work runs on it, the screen freezes.
Offline-first
A design where the app works without a network. It saves each change on the phone first and sends it later.
Paging
Loading a long list in small parts. The app asks for one page at a time.
Prefetch
Loading data before the user asks for it. It makes scrolling smooth, but it can waste data.
Repository
The class that reads and writes data for the rest of the app. It hides whether the data comes from the network or the database.
Room
Android's library for the database on the phone. You use a DAO to read and write the data.
Snapshot
A copy of the data as it was at one moment. It is not a list of changes.
Source of truth
The one copy of the data that the app trusts. In these cases it is the database on the phone, and the screen only reads it.
SwiftData
Apple's library for saving data on an iPhone. It has the same role as Room on Android.
