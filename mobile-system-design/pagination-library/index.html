Build it. The database schema, API, code and platform limits for a pagination library are on a separate page: Build it: a pagination library on Android and iOS (20 min read).

How to read this. This page is a 45-minute round (the length I assume), in the order I would spend it. API sketches, config rules, threading, iOS code and platform limits are in the build guide. The follow-up questions are my reconstruction of challenges that public prep material reports, not transcripts of real rounds.

TL;DR. Ask why not Paging 3 (Google's Android paging library) first. Build only for one contract shared with iOS. Keep the public core small: a page source, a config, a state per direction and a stream. A private engine owns generations (numbered refreshes), one load at a time per direction, and prefetch (loading ahead). Every default is API.

1. Scope and constraints (minutes 0 to 4)

In short: Ask why not Paging 3, set the scope, and park placeholders, two-way lists and telemetry.

A prompt I would expect: "Design a pagination library for our mobile apps." My users are engineers; my product is the API. I ask five things:

  • Who uses it? Five app teams, different backends.
  • Which key styles? Page number, offset and cursor (a server token that points to the next page), with cursor steered.
  • A database too? Network by default. A database is optional, through a mediator (code that writes fetched pages into it).
  • Which UI toolkits? None in the core.
  • The server? A page, and maybe a next key.
In scopeOut of scopeParked until you ask

Load state and a result streamList renderingTwo-way lists
Optional database mediator, test toolsThe network stackTelemetry hooks

The phone does four things:

Your decision. The scope follow-up question I expect: "Paging 3 already exists, and the same library must serve iOS." Do you adopt it, wrap it, or build?

First idea, and why it fails. Start drawing classes, or say "use Paging 3" and stop. Both fail when the exercise is the library: one shows no judgment, the other no design.

What I would say.

Say this. "On Android, I would adopt Paging behind a thin module unless someone can name what it cannot do. A contract shared with iOS is a reason to build, so I will design that. I am parking placeholders, two-way lists and telemetry."

I reject a hand-built engine on both platforms from day one: two codebases before anyone names a gap.

The follow-up question I expect:

"Paging compiles for iOS now. Why build?"

The release notes list iOS targets for the common modules, so I claim no unchecked gap. I would test three guesses:

  • Swift ergonomics (how natural the API feels)
  • House rules
  • Binary size

2. Data and contracts (minutes 4 to 14)

In short: Keys are generic, docs steer people to cursors, and the source says where to restart.

Your decision. The host app's backend pages by number, offset or cursor, and rows change underneath. Which key type does the library accept, and what do you steer people toward?

First idea, and why it fails. Put an integer page number in the API. When a row is inserted during a scroll, every later page moves: a row is skipped or shown twice. Deep offsets slow the server.

What I would say. The key is a generic type, so all three styles fit, and the docs steer people to cursors. I do not forbid offset; I will not control every backend. I reject a fixed integer key.

The follow-up question I expect:

"The backend returns the same cursor twice. And what about one that has expired?"

The engine compares the next key with the current one. Each case has a defined result:

  • Same key twice: paging ends with an error, not a loop.
  • Expired cursor: a typed error, then a refresh from the restart key.

The contract has four lines:

  • Load: parameters in (a key, a size, a direction); a page, an error or an invalid result out.
  • Restart: given what is on screen, return the key to restart from.
  • Size is a hint. The source may return a short or long page.
  • The library never removes repeated items by item ID. The app or its database does.

Paging documents both a refresh key and an invalid result (a load result that tells the library to replace the source) (load and display). My sketch lacks the second one. I would add it.

3. Client structure (minutes 14 to 22)

In short: A state holder that outlives the screen owns the stream. The database keeps rows after a kill.

Your decision. Who owns the paged stream and its cache: the screen, one object for the whole app, or a state holder that outlives the screen?

First idea, and why it fails. The screen builds the pager and collects it. But rotation rebuilds the screen, and a new collection starts from the first page. A PagingData (a snapshot of the paged list) can be collected only once unless cached (transform).

What I would say. The ViewModel (Android's state holder for a screen) builds the Pager and caches the stream in its scope, as the Paging docs do (load and display). A repository can build it if two screens share a list.

I reject a singleton, which outlives every screen, and a service. When the list must survive a killed process, the database holds the rows. To return to the exact scroll spot, I need a saved anchor key (the key of an item near the visible rows). That is my design, not in the Paging docs.

The follow-up question I expect:

"Two screens show the same list."

Caching shares the stream between collectors. One owner scope builds the pager; each screen only collects.

The Paging overview places the layers:

  • Source and mediator: the repository layer.
  • Pager and PagingData: the ViewModel layer.
  • LazyPagingItems: the UI.

The app supplies how to fetch a page; the library decides when. Three rules:

  • Nothing from a UI toolkit in the core.
  • Everything is internal until a user needs it.
  • A pager owns its state, so two lists never share a cache.

4. Make the hard part work (minutes 22 to 40)

In short: Each refresh starts a new generation, one load runs per direction, and state is per direction.

4.1 Data changes underneath (minutes 22 to 31)

Your decision. A row above the visible rows is deleted, or an old response arrives after a newer refresh. What does the list do?

First idea, and why it fails. On any change, reload from the top. The user loses their place, and a late old response replaces fresh rows with old ones.

What I would say.

Say this. "Every refresh starts a new generation. A result from an older generation is thrown away, even if the network call finished. The source tells me where to restart, from the item nearest the visible rows. With a database, the mediator writes in one transaction, and the database source marks itself out of date."

Paging 3.4 added a helper that finds the loaded item closest to a target position. This suits restart keys. I reject patching the list in memory, which works until a second writer appears.

The follow-up question I expect:

"Who starts the new generation if there is no Room?"

Room is Android's database library. Without it, nothing tells the source its data is out of date. The app must call invalidate, and the contract says so.

  • If the deleted row was the anchor, the anchor moves to its neighbor, and the restart key follows.

4.2 Load engine and state (minutes 31 to 40)

Your decision. The user scrolls fast, a load is running, and the next append fails. What does the engine do, and what does the UI see?

First idea, and why it fails. Load when the last row appears, with one loading flag. A fast scroll fires several calls for the same key. And one flag cannot say "keep the list, show a retry row" when an append fails, so the whole screen shows an error.

What I would say.

Say this. "Prefetch is a distance in items, and at most one load runs per direction. A refresh outranks an append and cancels it. State is kept per direction. The end of the list is a state, not an error. Retry repeats only the failed load. Refresh starts over."

I reject one boolean. Two verbs, retry and refresh, are my design. The load-state page shows only retry. It also says footers need placeholders off, which I would name if placeholders come up.

The follow-up question I expect:

"A host app sets max size 30 with page size 20 and prefetch 20."

Creating the config fails with a clear message, as in Paging (source).

  • The rule: max size is at least page size plus twice prefetch.
  • Here that is 20 + 2 x 20 = 60, so 30 fails.

If the interviewer cuts in, I answer first:

Say this. "Yes, two quick refreshes are harmless. The second cancels the first, and a late result is dropped. I was on load state, so I will finish that."

4.3 Where iOS changes the design

The engine is the same, with weaker guarantees. Swift code is in the build guide.

  • UIKit does not call its prefetch callback for every cell (Apple). So a row appearing must also be able to start the load. Whether SwiftUI gives that signal is design intent.
  • A Swift stream is meant for one consumer, so each subscriber gets its own. The proposal that added it calls concurrent iteration a programmer error (SE-0314).
  • Key and item types must cross an actor boundary (a limit on which code may touch the data), so the requirement shows in the public signature.

In short: Each failure has a recovery. Rollback is the host app's flag plus a patch.

At release:

  • A Play staged rollout can be halted, and users who already have the build keep it (Play help). My library lives inside host apps, so halting is their decision.
  • Old library versions stay in host apps for months, so the server accepts old cursors.
  • The host app's off switch reaches installed apps: a remote flag around behavior such as prefetch distance.
  • A flag cannot undo a public signature or schema change. That waits for a major version and a deprecation window.

Say this. "I cannot recall a release from a host app, so rollback is the flag plus a patch. I would watch request counts, memory and jank (visible stutter). Left out: placeholders, two-way lists, telemetry."

6. Follow-ups that change a constraint

In short: Each follow-up changes one constraint and has a strong and a weak answer.

Practice prompts, not a claim about what interviewers ask.

  1. A list of a million items, and the user jumps to the middle. Strong: I say what breaks: placeholders need a known total, and a jump needs a restart key near the target and a threshold for dropping loaded pages. Weak: load them all in the background.
  2. Open a chat at a search hit and scroll both ways. Strong: the first load is a refresh at the hit's key. Then prepend and append run alone, each with its own state. Weak: a second pager glued on top.
  3. Another device edits the list while this one scrolls. Strong: a push or sync marks the source out of date, a new generation reads the changed rows, and the anchor keeps the user in place. Weak: refresh from the top every time.
  4. The user logs out and someone else logs in. Strong: the cache belongs to the old account, so I tear down the pager with its owner. A telemetry hook carries a kind of key, not the key, since a cursor can hold user data. Weak: clearing the list, keeping the cache.
  5. After a library release, host apps report scroll jank. Strong: defaults are API, so I compare page size and prefetch first, then main-thread work, then request counts. Flip the flag, ship a patch. Weak: "roll back the release."
  6. The server changes its cursor encoding while three old versions are in the field. Strong: the library treats cursors as opaque, but old apps still send theirs. The server accepts both; stored cursors are dropped on upgrade. Weak: assuming everyone updates.

7. What changes by level

In short: Mid builds the basics, senior adds the split, staff adds the decision and rollout.

These levels are my own reading of vendor and prep material, not any company's rubric.

  • Mid-level: a generic page source, a pager that loads near the end, loading and error state, retry.
  • Senior: a public and internal split, per-direction state, generations, a written threading contract.
  • Staff: adopt-or-build with a revisit trigger, a deprecation plan, a multi-team rollout.

Common weak answers. These repeat across public prep material. This is not a dataset.

  • Ten minutes on the backend, happy path only.
  • Naming Paging 3 without saying what it covers.
  • The UI calling the network.
  • No restart key, so every change jumps to the top.
  • No versioning story.
  • Designing the list view, not the library.

Staff answer: the decision and the rollout

Decision: on Android, adopt Paging 3 behind a thin module unless I can name what it cannot do. For a contract shared with iOS, first test whether the Kotlin-compiled common modules meet it. Build only if Swift ergonomics, house rules or binary size fail.

Alternative: a hand-built core on both platforms: full control, larger cost. Revisit trigger: two or more teams work around the same limit, or the wrapper becomes the thing teams fight. Paging 3.5 can expose loaded items outside the UI, which removes one reason to wrap it.

Rollout: a release goes to a sample app, one host app, then the rest, with defaults behind a flag. Guardrail: no rise in request counts or memory. A deprecated API is removed only when adoption telemetry shows the old version below a threshold agreed in advance.

Opinion vs verified: the Paging components and 3.5 additions were read on developer.android.com, the halting behavior on the Play help page. The shared-core reasons, telemetry, thresholds and policy are my opinion. The native vs cross-platform guide covers shared against separate code.

Words on this page (14)
Actor
A Swift type that runs one task at a time. This keeps its data safe when many tasks use it.
Cursor
A saved place in a list. The server gives it to the app, and the app sends it back to get the next part.
Dedupe
To keep only one copy of the same item. For example, a message that arrives twice is stored once.
Host app
The app that contains an SDK. You write the SDK, and another team writes the host app.
Paging
Loading a long list in small parts. The app asks for one page at a time.
Prefetch
Loading data before the user asks for it. It makes scrolling smooth, but it can waste data.
Remote flag
A setting that the server can change. It can turn a feature on or off without a new release.
Repository
The class that reads and writes data for the rest of the app. It hides whether the data comes from the network or the database.
Rollback
Going back to the old behavior after a problem. A build on a user's phone cannot be taken back, so teams use a kill switch.
Room
Android's library for the database on the phone. You use a DAO to read and write the data.
Snapshot
A copy of the data as it was at one moment. It is not a list of changes.
Staged rollout
A release to a growing share of users, not to everyone at once. It limits the harm of a bad release.
Stale data
Saved data that may be out of date. The app should show how old it is, or refresh it.
ViewModel
A class that holds the state of one screen. It survives a screen rotation.
