Design a pagination library (Android and iOS): API, state model and caching

How to read this. This is a library question, not an app-feature question. Your users are app developers, and your product is the public API. Sections 1 to 9 use Kotlin, with Jetpack Paging 3 as the reference design. Section 10 shows what an iOS equivalent looks like.

TL;DR. Split the library into a small stable public core (a page source contract, a config, a state model, a stream of results) and an internal engine that owns caching, deduplication, cancellation and prefetch. Make the page key a generic type so offset, cursor and page number all fit. Model load state explicitly per direction (refresh, prepend, append). Let the app own the data source and the UI, and let the library own the scheduling. Treat every default, error type and threading rule as part of the API you must keep compatible.

1. Clarify the requirements (about 5 min)

The consumers are other engineers, so ask them. Good opening questions:

  • Who are the integrating teams, and how many? (Assume five app teams, each with different backends.)
  • Which key styles must we support? (Offset, page number and opaque cursor, all three.)
  • Network only, or network plus a local database? (Both: the database is optional but must compose cleanly.)
  • Which UI toolkits? (Compose and RecyclerView on Android; SwiftUI and UIKit on iOS. The core must not depend on any UI toolkit.)
  • Is the list one-directional (feed) or bidirectional (chat history)? (Support both, default to append only.)
  • Which minimum OS and language versions do consumers target? (This sets the API ceiling.)
  • What can the library assume about the server? (Nothing beyond "returns a page and maybe a next key".)

Functional: load an initial page, load more near the end, refresh, retry after an error, expose load state, expose items as a stream, optional placeholders, optional database-backed mode.

Non-functional (the part that makes it a library question):

ConcernTarget
API sizeA new team integrates in under a day with one page of docs
StabilityNo source or binary breaks inside a major version
EfficiencyNo duplicate in-flight requests, bounded memory, cancelled work stops quickly
PredictabilityDocumented threading contract; callbacks never on a surprise thread
TestabilityConsumers can test their list logic without a network or a UI
FootprintFew dependencies, small binary, no hidden global state
ObservabilityHooks for load timing, errors and cache hits, off by default

Out of scope for now: image loading, list rendering, diffing algorithms, the network stack itself. Say this out loud. A pagination library that also loads images becomes impossible to version.

2. High-level architecture (about 10 min)

Official architecture mapping: PageSource and Mediator sit in the app's data layer, wrapped by a repository, with Room as source of truth. Pager and PagingData are built in the ViewModel and cached with cachedIn(viewModelScope). The UI layer collects them (collectAsLazyPagingItems). See Paging overview and data layer.

The key decision: the app supplies "how to fetch one page", and the library decides "when, how many, and what to do on failure". Everything on the first side is a small interface. Everything on the second side is internal and can be rewritten without a major version.

This mirrors Paging 3, which splits responsibilities into PagingSource (one data source), RemoteMediator (layered network plus database), Pager with PagingConfig (stream construction) and PagingData (a snapshot container). The UI layer only adapts that stream to a list. The ViewModel never touches the DAO or network service itself; a repository hands it the PagingSource or Mediator.

3. Public API surface and what stays internal

The rule: expose the fewest types that let a consumer do everything, and make every extra public type earn its place.

Public:

  • PageSource<K, V>: one suspend function to load a page.
  • PagingConfig: page size, prefetch distance, initial load size, max cached items, placeholders flag.
  • LoadState and CombinedLoadStates: the state model (section 5).
  • PagingData<V>: the opaque snapshot you hand to the UI adapter.
  • Mediator: the optional hook for database-backed paging (section 8).
  • PagingEvents: the observability interface (section 9).

Internal: the fetcher, coordinator, page store, prefetch policy, retry scheduling and the diffing glue. Consumers must not be able to depend on them, even by reflection-friendly naming.

Enforcement tools: Kotlin internal plus explicit API mode, which forces a visibility decision on every declaration; a binary-compatibility checker in CI that diffs the public API dump on every pull request; Swift package or internal access plus library evolution settings when you ship a binary framework.

Two design habits matter here:

  • Sealed results over exceptions for expected outcomes. A page load returns Page or Error, not "throws sometimes".
  • Stay closed by default. You can open a class later without breaking anyone. You cannot close one.

4. Generics and the data source abstraction

The library should know nothing about how a key is encoded. A generic key type covers all three styles.

// Sketch: the core contract
interface PageSource<K : Any, V : Any> {
    suspend fun load(params: LoadParams<K>): LoadResult<K, V>
    fun refreshKey(state: PagingState<K, V>): K?     // where to restart after invalidation
}

sealed interface LoadParams<K> {
    val key: K?            // null on first load
    val loadSize: Int
    class Refresh<K>(override val key: K?, override val loadSize: Int) : LoadParams<K>
    class Append<K>(override val key: K, override val loadSize: Int) : LoadParams<K>
    class Prepend<K>(override val key: K, override val loadSize: Int) : LoadParams<K>
}

sealed interface LoadResult<K, V> {
    data class Page<K, V>(val data: List<V>, val prevKey: K?, val nextKey: K?) : LoadResult<K, V>
    data class Error<K, V>(val cause: Throwable) : LoadResult<K, V>
}

How each key style fits:

StyleKnextKeyPitfall
Page numberIntkey + 1Skips or repeats rows when data is inserted mid-scroll
OffsetIntkey + loadSizeSame drift problem, plus slow deep offsets on the server
CursorString (opaque)Server valueCursors can expire; need a restart path

Steer consumers toward cursors in the docs, but do not forbid the others; you will not control every backend.

refreshKey is the easy-to-miss part. When data is invalidated, the library asks the source where to restart so the user keeps their scroll position instead of jumping to the top. Paging 3 uses the same idea.

The loaded size is passed in, not hard-coded, because the initial load is usually larger than later pages. The source should treat loadSize as a hint it may ignore, and the library must cope with a short or long page.

5. State model

Consumers build spinners, retry rows and empty views from this, so it is the most-used part of the API. Paging 3 models it as three states per load type:

  • NotLoading with an endOfPaginationReached flag.
  • Loading.
  • Error carrying the cause.

Load types are refresh (initial or restart), prepend and append. A combined object also carries state for the source and for the mediator separately, so UI can tell "reading the local database" from "syncing with the network".

sealed interface LoadState {
    data class NotLoading(val endReached: Boolean) : LoadState
    data object Loading : LoadState
    data class Error(val cause: Throwable) : LoadState
}

data class CombinedLoadStates(
    val refresh: LoadState, val prepend: LoadState, val append: LoadState,
    val source: LoadStates, val mediator: LoadStates?,
)

Design points to say out loud:

  • Separate refresh from append. A failed append should leave the list on screen with a retry row. A failed refresh with no data should show a full-screen error. One combined "loading" flag cannot express either.
  • End of list is a state, not an error. Model it as NotLoading(endReached = true) so UI can show a footer.
  • Retry and refresh are two verbs. retry() repeats only the failed load. refresh() discards the generation and starts over.
  • Emit distinct values only. Collapse repeated identical states so UI does not recompose for nothing.
  • Make states cheap to compare. Data classes and objects, no lambdas inside state.

6. Cache, deduplication, cancellation and prefetch

All of this lives in the internal engine, and consumers see it only through config.

In-memory cache. Keep loaded pages in a bounded store. With maxSize set, drop pages from the end farthest from the viewport. Validate config at construction: if the max size cannot hold the initial load plus the prefetch window, fail fast with a clear message instead of thrashing at runtime. Paging 3 documents in-memory caching as built in.

Request deduplication. Track at most one in-flight load per direction. A second append request while one is running joins the first or is dropped. Without this, a fast scroll fires ten requests for the same key. Paging 3 lists built-in request deduplication among its features.

Generations. Tag each refresh with a generation number. Results from a cancelled generation are discarded, even if the network call finished. This closes the race where a slow old response overwrites a fresh refresh.

Prioritization and cancellation.

  • Refresh outranks append. Starting a refresh cancels any running append or prepend.
  • A visible-range load outranks a speculative prefetch.
  • Cancellation is cooperative. On Android, the load runs in a coroutine, and cancelling the scope cancels the call if the source uses cancellable suspend functions. Document that sources must not swallow CancellationException.
  • When the stream has no collectors, stop loading and release pages, unless the app opted into caching beyond the collector's lifetime.

Prefetch distance. Config field prefetchDistance: how many items from the loaded edge the user may be before the next page is requested. Defaults and trade-offs:

  • Too small: users see the end and wait.
  • Too large: wasted requests and memory, and extra data on cellular.
  • A sensible default is one page size (Paging 3 uses the same default; see the Draft notes on verification).

Let consumers set it, and let the library clamp it so a huge value cannot defeat maxSize.

7. Threading and concurrency contract

Write this down as part of the API, because it is the thing integrators break first.

  • PageSource.load is called from the library's dispatcher, one call at a time per direction, and may suspend.
  • load must be main-safe: the library never calls it on the main thread, and the source need not switch threads for ordinary work. State this explicitly, or every consumer will add a redundant withContext.
  • State and data are emitted on a documented context. Choose one (for example, the collector's context) and never change it in a minor release.
  • Internal state is confined to one serialized context (a single-threaded dispatcher or a mutex-guarded actor), not scattered locks.
  • Public classes are immutable or documented as thread-safe. PagingData is a snapshot and is safe to pass between threads.
  • No hidden global singletons. A Pager owns its state, so two lists never share a cache by accident.

8. Composing with a local database

The library should not require a database, but it should make the database path easy. Paging 3's design is the template: the database is the source of truth, a RemoteMediator fetches from the network when the cached range runs out, writes results into the database, and a database-generated PagingSource feeds the UI. Inserting data invalidates the source, and a new generation reads the updated rows.

// Sketch: mediator contract, simplified from the Paging 3 shape
interface Mediator<K : Any, V : Any> {
    suspend fun initialize(): InitializeAction      // skip or launch the first refresh
    suspend fun load(type: LoadType, state: PagingState<K, V>): MediatorResult
}

What the library guarantees, and what the app owns:

  • Library: call initialize() first; if it asks for a refresh, hold appends until the refresh succeeds; surface mediator state separately from source state; cancel a mediator load when the generation ends.
  • App: store remote keys, run the refresh as one transaction, clear old rows only after the network succeeds, keep local pending changes when merging server data.

In offline-first terms this is pull-based sync: the mediator fetches on demand as the user scrolls. A mediator result is Success(endReached) or Error(cause). A detail worth saying: the mediator reports "end reached" by return value, not by an empty page, so the library does not guess.

9. Testability, versioning and observability

Testability. Ship test tooling as a separate artifact so production code does not carry it. Paging 3 does this with a testing module: TestPager loads a source page by page, asSnapshot collects a stream while you simulate scrolling, and asPagingSourceFactory builds fake sources from lists, where a flow of lists simulates invalidation. Mediator tests check the returned result (valid data, empty response, thrown exception) and use an in-memory database. Make time injectable (a clock and a dispatcher parameter) so tests do not sleep.

Versioning and compatibility.

  • Use semantic versioning: removals and signature changes are major; additions are minor; fixes are patch.
  • Behavior is API. Changing a default page size, an error type, a callback thread or the retry policy is a breaking change for someone, even if the compiler is silent.
  • Deprecate before removing: mark the symbol deprecated with a replacement, keep it for a stated window (for example, two minor releases and at least six months), and log a build-time warning, not a runtime one.
  • Binary compatibility: on Android, avoid changing public method signatures or adding abstract members to public interfaces (use default methods or new interfaces). Use a binary-compatibility validator in CI. On iOS, a binary XCFramework needs library evolution mode and @frozen used sparingly.
  • Config as a builder or a data class with defaults. Adding a field with a default is compatible; reordering constructor parameters is not. Prefer named parameters.
  • Ship a sample app and run it against each release as a contract test.

Observability. Provide an opt-in listener, not a logging dependency.

interface PagingEvents {
    fun onLoadStarted(type: LoadType, key: Any?) {}
    fun onLoadFinished(type: LoadType, durationMs: Long, itemCount: Int, error: Throwable?) {}
    fun onCacheHit(pageCount: Int) {}
    fun onGenerationCancelled(reason: String) {}
}

Keep payloads free of item contents so the hook is safe to forward to analytics. Default to a no-op. The aim is for each host app to answer "how slow are our pages, and how often do they fail" without patching the library.

10. How to build a pagination library on iOS (Swift)

The design carries over unchanged: a generic page source, a state model, an engine with one in-flight load per direction, and an optional database mediator. There is no official Apple paging library, so the iOS version is the part you build and own. Swift concurrency supplies the primitives: async functions for loads, structured Task cancellation, an actor for engine state, and AsyncSequence (most often AsyncStream) for results.

// Sketch: iOS public surface
public protocol PageSource<Key, Item>: Sendable {
    associatedtype Key: Sendable
    associatedtype Item: Sendable
    func load(_ params: LoadParams<Key>) async throws -> Page<Key, Item>
}

public actor Pager<Key: Sendable, Item: Sendable> {
    public init(source: some PageSource<Key, Item>, config: PagingConfig)
    public nonisolated let updates: AsyncStream<PagingSnapshot<Item>>   // snapshot must be Sendable
    public func loadMoreIfNeeded(visibleIndex: Int) async
    public func refresh() async
    public func retry() async
}

What is genuinely different:

  • Cancellation is cooperative, and so is the loop. Cancelling the task that consumes an AsyncSequence does not by itself make every source stop. Document that sources must check for cancellation, and clean up in the continuation's onTermination callback, which Apple documents as called when iteration is cancelled.
  • Swift 6 Sendable rules show up in the API. Key and item types must be Sendable to cross the actor boundary. State that requirement in the public signature instead of discovering it in a consumer's build.
  • No built-in list integration. You ship thin adapters (a SwiftUI helper that calls loadMoreIfNeeded from onAppear, a UIKit prefetching delegate), kept in a separate module so the core stays toolkit-free.
  • Binary distribution has stricter rules. If you ship an XCFramework, library evolution constrains what you can change; if you ship source via Swift Package Manager, source compatibility is the main concern. Decide which you offer.

12. What changes by level

  • Mid-level: a working generic PageSource, a Pager that loads the next page near the end, a state model with loading and error, and retry.
  • Senior: a deliberate public/internal split, key-type genericity, per-direction state, deduplication and generation-based cancellation, a documented threading contract, and a semantic versioning and deprecation policy.
  • Staff: binary compatibility tooling and a migration plan for breaking changes, version-adoption telemetry, the database mediator contract, a multi-team rollout (sample app, docs, support model), measuring the library's own cost (memory, jank, request counts), and the build-versus-adopt decision against Paging 3 on Android.

13. Follow-up questions to expect

  1. Why not just use Paging 3? (On Android, often you should; a wrapper is justified only for house conventions, a shared cross-platform contract, or missing features. Say this honestly.)
  2. How do you support bidirectional paging, such as jumping to a search result in a chat? (Prepend and append from a restart key; jumpThreshold-style reinitialization.)
  3. How do you remove an API that thirty apps use? (Deprecation window, replacement, telemetry on usage, codemod or migration guide, then a major release.)
  4. How do you test the library itself? (Fake sources, controlled dispatcher, property tests on generation races, a sample app run against each release.)
  5. How do you measure it? (Load latency per type, error rate, cache hit rate, duplicate-request count, peak items in memory.)
  6. How would you add placeholders? (A nullable item list plus a known total; explain the cost when the total is unknown.)
