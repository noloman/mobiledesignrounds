Build it. The schema, API, code and platform limits for a pagination library are on their own page: Build it: a pagination library on Android and iOS (19 min read).

How to read this. This page is the 45 minutes, in the order I would spend them. The API sketches, config rules, threading contract, iOS code and platform limits are in the build guide. The pushes below are my reconstruction of the kinds of challenges public prep material reports, not transcripts of real rounds.

TL;DR. Ask why not Paging 3 (Google's Android paging library) first. If the reason is one contract shared with iOS, build a small public core: a page source, a config, a state per direction and a stream. Under it sits a private engine that owns generations (numbered refreshes), one load in flight per direction and prefetch (loading ahead). Every default is API.

1. Scope and constraints (minutes 0 to 4)

In short: Ask why not Paging 3, set the scope, and park placeholders, two-way lists and telemetry.

A prompt I would expect: "Design a pagination library for our mobile apps." My users are engineers and my product is the API. I ask five things and give my default:

  • Who integrates it? Five app teams, different backends.
  • Which key styles? Page number, offset and cursor (a server token for the next page), with cursor steered.
  • A database too? Network by default. A database is optional, through a mediator (code that writes fetched pages into it).
  • Which UI toolkits? None in the core.
  • The server? A page, and maybe a next key.
In scopeOut of scopeParked until you ask

The phone is not one box:

Your call. The scope push I would expect: "Paging 3 already exists, and the same library must serve iOS." Do you adopt it, wrap it, or build?

First instinct, and why it breaks. Start drawing classes, or say "use Paging 3" and stop. Both break once the exercise is the library itself: one shows no judgment about owning code, the other no design.

What I'd say.

Say it. "On Android I'd adopt Paging behind a thin module unless someone can name what it cannot do. A contract shared with iOS is a reason to build, so I'll design that. I'm parking placeholders, two-way lists and telemetry."

I reject a hand-built engine on both platforms from day one. That is two codebases before anyone has named a gap.

The push I would expect:

"Paging compiles for iOS now. Why build?"

The release notes list iOS targets for the common modules, so I claim no gap I have not checked. I would test three hypotheses:

  • Swift ergonomics
  • House rules
  • Binary size

2. Data and contracts (minutes 4 to 14)

In short: Keys are generic, the docs steer to cursors, and the source says where to restart.

Your call. The host's backend pages by number, offset or cursor, and rows change underneath. What key type does the library accept, and what do you steer people toward?

First instinct, and why it breaks. Put an integer page number in the API. When a row is inserted while the user scrolls, every later page shifts: a row is skipped or shown twice, and deep offsets slow the server.

What I'd say. The key is a generic type, so all three styles fit, and the docs steer to cursors. I do not forbid offset; I will not control every backend. I reject a fixed integer key.

The push I would expect:

"The backend returns the same cursor twice. And one that has expired?"

The engine compares the next key with the current one. Each case has a defined outcome:

  • Same key twice: paging ends with an error, not a loop.
  • Expired cursor: a typed error, then a refresh from the restart key.

The contract fits in four lines on the board:

  • Load: parameters in (a key, a size, a direction), a page, an error or an invalid result out.
  • Restart: given what is on screen, return the key to restart from.
  • Size is a hint. The source may return a short or long page.
  • The library never dedupes by item ID. The app or its database does.

Paging documents both a refresh key and an invalid result (a load result that replaces the source) (load and display). My sketch lacks the second; I would add it.

3. Client structure (minutes 14 to 22)

In short: A state holder that outlives the screen owns the stream. The database survives a killed process.

Your call. Who owns the paged stream and its cache: the screen that shows the list, a repository-wide singleton, or a state holder that outlives the screen?

First instinct, and why it breaks. The screen builds the pager and collects it. But a screen is destroyed and rebuilt on rotation, and a new collection starts from the first page. A PagingData (the paged-list snapshot) can be collected only once unless it is cached (transform).

What I'd say. The ViewModel (Android's screen-level state holder) builds the Pager and caches the stream in its scope, as the Paging docs do (load and display). Building it in a repository is a fair variant when two screens share a list.

I reject a singleton, which outlives every screen and holds memory, and a service. When the list must survive a killed process, the database holds the rows. The exact scroll spot needs a saved anchor key (the key of an item near the viewport). That is my design, not something the Paging docs give you.

The push I would expect:

"Two screens show the same list."

Caching shares the stream between collectors. One owner scope builds the pager, and each screen only collects.

The Paging overview places the layers:

  • Source and mediator: the repository layer.
  • Pager and PagingData: the ViewModel layer.
  • LazyPagingItems: the UI.

The app supplies how to fetch a page; the library decides when. Three rules:

  • Nothing from a UI toolkit in the core.
  • Everything is internal until a consumer needs it.
  • A pager owns its state, so two lists never share a cache by accident.

4. Make the hard part work (minutes 22 to 40)

In short: Each refresh starts a new generation, one load runs per direction, and state is per direction.

4.1 Data changes underneath (minutes 22 to 31)

Your call. A row above the viewport is deleted, or an old response lands after a newer refresh. What does the list do?

First instinct, and why it breaks. On any change, refresh and reload from the top. The user loses their place, and a late old response overwrites fresh rows with stale ones.

What I'd say.

Say it. "Every refresh starts a new generation. A result from an older generation is thrown away, even if the network call finished. The source also tells me where to restart, from the item nearest the viewport. With a database, the mediator writes in one transaction and the database source invalidates itself."

Paging 3.4 added a helper that finds the loaded item closest to a target position, which suits restart keys. I reject patching the list in memory: it works until a second writer appears.

The push I would expect:

"Who starts the new generation if there is no Room?"

Without Room (Android's database library), nothing invalidates the source for me. The app calls invalidate, and the contract says so in writing.

  • If the deleted row was the anchor, it moves to its neighbor and the restart key follows.

4.2 Load engine and state (minutes 31 to 40)

Your call. The user flings, a load is already running, and the next append fails. What does the engine do, and what does the UI see?

First instinct, and why it breaks. Load when the last row appears, and keep one loading flag. A fling fires several calls for the same key. And when an append fails, one flag cannot say "keep the list, show a retry row", so the whole screen becomes an error.

What I'd say.

Say it. "Prefetch is a distance in items, and at most one load runs per direction. A refresh outranks an append and cancels it. State is kept per direction, and the end of the list is a state, not an error. Retry repeats only the failed load. Refresh starts over."

I reject one boolean. Two verbs is my design; the load-state page shows only retry. It also says footers need placeholders off, which I would name if placeholders come up.

The push I would expect:

"A host sets max size 30 with page size 20 and prefetch 20."

Creating the config fails with a clear message. Paging throws too (source).

  • The rule: max size is at least page size plus twice prefetch.
  • Here that is 20 + 2 x 20 = 60, so 30 fails.

If I am cut off mid-answer, I answer first:

Say it. "Yes, two quick refreshes are harmless: the second cancels the first and a late result is dropped. I was partway through load state, so I'll finish that."

4.3 Where iOS changes the design

Same engine, weaker guarantees. The Swift code is in the build guide.

  • UIKit's prefetch callback is not called for every cell (Apple), so a row appearing must be able to start the same load. Whether SwiftUI gives that signal is design intent.
  • A Swift stream is meant for one consumer, so each subscriber gets its own. The proposal that added it calls concurrent iteration a programmer error (SE-0314).
  • Key and item types must cross an actor boundary, so the requirement shows in the public signature.

5. Break it, ship it, roll it back (minutes 40 to 45)

In short: Each failure has a recovery. Rollback is the host app's flag plus a patch.

Release reality:

  • A Play staged rollout can be halted, and users who already have the build keep it (Play help). My library rides inside host apps, so a halt is their call.
  • Old library versions stay in host apps for months, so the server accepts old cursors.
  • The host app's kill switch reaches installed apps: a remote flag around behavior such as prefetch distance.
  • A public signature or schema change cannot be flagged. It waits for a major version and a deprecation window.

Say it. "I can't recall a release from a host app, so the rollback is the flag plus a patch. I'd watch request counts, memory and jank on sample screens. Left out: placeholders, two-way lists, telemetry."

6. Follow-ups that change a constraint

In short: Each follow-up changes one constraint and has a strong and a weak answer.

Practice prompts, not a claim about what any interviewer asks.

  1. A list of a million items, and the user jumps to the middle. Strong: I say what breaks: placeholders need a known total, and a jump needs a restart key near the target and a threshold for dropping what is loaded. Weak: "load them all in the background."
  2. Open a chat at a search hit and scroll both ways. Strong: the first load is a refresh at the hit's key, then prepend and append run independently, each with its own state. Weak: a second pager glued on top.
  3. Another device edits the list while this one scrolls. Strong: a push or sync invalidates the source, a new generation reads the changed rows, and the anchor keeps the user in place. Weak: refresh from the top every time.
  4. The user logs out and someone else logs in. Strong: the cache belongs to the old account, so I tear the pager down with its owner. A telemetry hook must carry a kind of key, not the key, since a cursor can encode user data. Weak: clearing the list and keeping the cache.
  5. After a library release, hosts report scroll jank. Strong: defaults are API, so I diff page size and prefetch first, then main-thread work, then request counts. Flip the flag, ship a patch. Weak: "roll back the release."
  6. The server changes its cursor encoding while three old versions are in the field. Strong: cursors are opaque to the library, but old apps still send theirs. The server accepts both, and stored cursors are dropped on upgrade. Weak: assuming everyone updates.

7. What changes by level

In short: Mid builds the basics, senior adds the split, staff adds the decision and rollout.

These levels are my own reading, drawn from vendor and prep material (courses and books), not any company's rubric.

  • Mid-level: a generic page source, a pager that loads near the end, loading and error state, retry. I want to hear: "The source returns a page and a next key."
  • Senior: a public and internal split, per-direction state, generations, a written threading contract. I want to hear: "Page keys are generic, so cursor, offset and page number all fit."
  • Staff: adopt-or-build with a revisit trigger, a deprecation plan, a multi-team rollout. I want to hear: "Here is what would make me stop maintaining this, and the flag that undoes a bad release."

Common weak answers. The list below repeats across public prep material. It is not a dataset.

  • Ten minutes on the backend, happy path only.
  • Naming Paging 3 without saying what it covers.
  • The UI calling the network.
  • No restart key, so every change jumps to the top.
  • No versioning story.
  • Designing the list view instead of the library.

Staff answer: the decision and the rollout

Decision: on Android, adopt Paging 3 behind a thin module unless I can name what it cannot do. For a contract shared with iOS, first test whether the Kotlin-compiled common modules satisfy it. Build only if Swift ergonomics, house rules or binary size fail.

Alternative: a hand-built core on both platforms: full control, larger bill. Revisit trigger: two or more teams working around the same limitation, or the wrapper becoming the thing teams fight. Paging 3.5 can expose loaded items outside the UI, which removes one reason to wrap it.

Rollout: a release goes to a sample app, then one host, then the rest, with defaults behind a flag. Guardrail: no rise in request counts or memory on sample screens. A deprecated API goes only when adoption telemetry shows the old version below a threshold agreed in advance.

Opinion vs verified: the Paging components and 3.5 additions were read on developer.android.com, the halting behavior on the Play help page. The shared-core reasons, telemetry, thresholds and policy are my opinion. The native vs cross-platform guide covers shared against separate code.
