Design photo backup and file sync (Android and iOS): resumable uploads and conflicts

TL;DR. My answer: an upload is a durable, resumable job, not a request. Split each file into content-hashed blocks, ask the server which blocks it lacks, and upload only those. Store the session and per-block state in a local database so a killed process or a dead network costs one block, not the file. Let the OS run the transfer (WorkManager and user-initiated jobs on Android, a background URLSession on iOS), and gate it on Wi-Fi and charging by default. I would never show "backed up" until the server has confirmed every block, and that is the rule I would defend hardest.

1. Clarify the requirements (about 5 min)

Questions worth asking:

  • Photos only, or arbitrary files too? (Assume camera roll backup first, then a Drive-style folder tree as a follow-up.)
  • One direction (device to cloud) or two-way sync? (Assume backup is one-way; file sync is two-way.)
  • How big are files? (Assume photos of 3 to 10 MB and videos up to several GB.)
  • Which network and power conditions are allowed? (Assume Wi-Fi and charging by default, with a user setting for cellular.)
  • Single device or several devices on one account? (Assume several; this is where conflicts come from.)
  • Encryption? (Assume TLS in transit and encryption at rest on the server; mention end-to-end as a follow-up.)

Functional: pick which folders to back up, upload new and changed items automatically, show progress and "backed up" state per item, browse and download from the cloud, restore, delete, and handle the same file edited on two devices.

Non-functional (the part that makes it a mobile question):

ConcernTarget
ReliabilityNo lost items, no duplicates, no corrupt files
ResumabilityA dropped connection or killed process loses at most one block
Battery and dataNo upload on cellular or low battery unless the user opts in
MemoryConstant memory use for a multi-GB video
Perceived stateThe user always sees what is backed up, queued, or failed
SecurityTLS in transit, scoped credentials, no plaintext secrets on disk

Out of scope for now: sharing and permissions, search, face grouping, and editing. I'd say this early, so it can be redirected.

2. High-level architecture (about 10 min)

Where this sits in Android's architecture guidance: Compose and a ViewModel are the UI layer, and the ViewModel exposes one uiState built from repository Flows. SyncRepository is the data-layer repository, and the local DB, change detector and the two APIs are its data sources. The uploader has to survive the process dying, so it runs on WorkManager. This paraphrases the Android data layer and offline-first guides (documentation content from the Android Open Source Project, Apache License 2.0).

Three decisions shape everything:

  1. The local database is the source of truth for sync state. The UI shows "uploading 14 of 212" by reading it through the repository as a Flow. The scheduler and uploader write to it. I save state locally first and let the uploader catch up. Uploads are pushed by the device; cloud changes come back by asking for everything since a cursor. The offline-first guide has the write-strategy table this follows, and the durable-work pattern is the same one as the send path in the chat app case study.
  2. Blocks and metadata are separate. Blocks are immutable bytes named by their hash. Metadata says which blocks make up which version of which file. This is what makes dedupe, resume, and versioning cheap.
  3. The OS owns the long-running transfer. The app can be killed at any time, so the app plans the work and the OS carries it out.

3. Data model and API

Local schema (Room)

@Entity(tableName = "items", indices = [Index(value = ["localUri"], unique = true)])
data class ItemEntity(
    @PrimaryKey val itemId: String,       // client-generated UUID
    val localUri: String,                 // MediaStore content URI or file path
    val size: Long,
    val contentHash: String?,             // whole-file hash, filled after hashing
    val remoteFileId: String? = null,     // null until the server has created the file
    val baseVersion: Long? = null,        // version this edit is based on, for conflict checks
    val state: State,
) { enum class State { DETECTED, HASHING, UPLOADING, DONE, FAILED } }

@Entity(tableName = "blocks", primaryKeys = ["itemId", "index"])
data class BlockEntity(
    val itemId: String, val index: Int,
    val hash: String,                     // SHA-256 of the block bytes
    val length: Int,
    val state: BlockState,                // PENDING, PRESENT_ON_SERVER, UPLOADED
)

@Entity(tableName = "upload_sessions")
data class UploadSessionEntity(
    @PrimaryKey val itemId: String,
    val sessionUri: String,               // server-issued resumable session
    val expiresAt: Long,
)

The server's missing list is the truth about what is stored, and a block is UPLOADED only after the server acknowledged it. Treat anything the client sent but the server did not acknowledge as unsent.

REST (sketch)

POST /v1/files/{id}/uploads         body: { size, blockHashes: [...] }
     → { sessionUri, missing: [3, 4, 9] }          (blocks the server does not have)
PUT  <sessionUri>?block=3   Content-Range: bytes 12582912-16777215/52428800
     X-Block-Hash: <sha256>   → 200 { stored: true } | 422 (hash mismatch, resend)
POST /v1/files/{id}/uploads  again with the same body        (after a failure: returns the current missing list)
POST /v1/files/{id}/commit          body: { baseVersion, blockHashes }
     → 200 { version } | 409 { currentVersion }     (conflict)
                                                   (a retry with the same block list returns the version it already created)
GET  /v1/changes?cursor=<opaque>                   (what changed in the cloud; the server returns the next cursor)

The session borrows from Google's resumable upload model (a session URI, chunks with Content-Range) and from the tus protocol, but I changed one thing. Both of those take one contiguous byte stream and ask the server for its offset after a failure. Skipping blocks the server already has breaks that, so in my sketch each block is its own PUT into the session and the server owns the missing list instead of an offset. That is my design, not Google's or tus's behavior. Whichever shape you pick, say why; the point is that the server, not the client, decides what is stored. Because a commit response can be lost like any other, I would make the commit idempotent on the block-list hash: a retry with an identical list returns the existing version instead of hitting the 409 branch.

4. Resumable block upload

The core flow, per item:

  1. Detect the new or changed item and insert it as DETECTED (see section 5).
  2. Split the file into blocks and hash each block while reading it as a stream. Do not read the file into memory.
  3. Send the block hashes. The server replies with the blocks it is missing. Blocks it already has, from this user or from a previous version of this file, are never uploaded.
  4. Upload only the missing blocks, in order, one PUT each. Check the block still hashes to what you sent in step 3, and after each acknowledged block mark its BlockEntity UPLOADED.
  5. Send a commit with the full list of block hashes and the baseVersion. Only the commit makes the new version visible.
  6. Mark the item DONE.
// Sketch: upload only the blocks the server said it is missing. Constant memory: one reused buffer.
// Runs in a data-layer component called by the worker (never by a Composable or ViewModel); dispatcher injection and entity mapping omitted for brevity
suspend fun uploadMissing(item: ItemEntity, session: UploadSessionEntity, missing: List<Int>) {
    contentResolver.openInputStream(item.localUri.toUri())!!.use { input ->
        val buf = ByteArray(BLOCK_SIZE)                    // for example 4 MiB
        var pos = 0L                                       // where the stream is now
        for (index in missing.sorted()) {
            val block = dao.block(item.itemId, index)      // hash and length saved while hashing
            val start = index.toLong() * BLOCK_SIZE
            input.skipNBytes(start - pos)                  // API 33+; throws EOFException if the file shrank
            val n = input.readNBytes(buf, 0, block.length) // API 33+; on older versions loop on read()
            pos = start + n
            check(n == block.length && sha256(buf, n) == block.hash) { "file changed since hashing" }
            val ack = api.putBlock(session.sessionUri, index, buf, n, start, item.size)  // Content-Range
            check(ack.stored) { "server did not keep block $index" }
            dao.setBlockState(item.itemId, index, BlockState.UPLOADED)
        }
    }
}

What I'd call out:

  • A changed file fails loudly. The re-hash before each PUT is what catches a photo edited after step 2. The sketch throws, the worker re-queues the item as HASHING, and nothing gets committed. If the file simply shrank, skipNBytes throws EOFException; it does not end quietly.
  • Block size is a trade-off. Small blocks dedupe better and lose less on failure, but add per-request overhead and metadata. A few MiB is a common starting point, and the 4 MiB in the sketch is only an example. Google's resumable upload docs require chunks in multiples of 256 KB except the last one and advise using the largest practical size; my block-per-request shape keeps that multiple.
  • Fixed-size blocks break on insertion. Add bytes near the start of a file and every later block hash changes. Content-defined chunking (boundaries chosen by a rolling hash) keeps most blocks stable. For photos and videos, which are rarely edited in place, fixed blocks are usually enough. For documents, mention content-defined chunking.
  • Verify what you sent. Send a per-chunk checksum (tus defines an Upload-Checksum extension). A corrupt block that dedupes is corrupt for every file that uses it.
  • Sessions expire. Google's resumable session URIs last one week. On 404, start a new session; dedupe means stored blocks cost nothing.
  • Cross-user dedupe has a privacy cost. If blocks are shared across accounts, a hash probe reveals whether someone already stored a given file. Say so, and say that end-to-end encryption mostly defeats cross-user dedupe.

Block hashing, dedupe, resumable sessions and conflicted copies are common ideas in file-sync design rather than anyone's confirmed internals. The Drive and tus pages in the reading list back the upload protocol; the rest is my own design reasoning. For where the write and conflict choices come from, see the offline-first guide; the lost-acknowledgement walkthrough is in the staff mobile loop guide.

Memory: never load a file into a ByteArray or Data. Stream it with one reused buffer and hash block by block, so peak memory stays near the block size. The file is read twice, once to hash and once to upload the missing blocks, and I accept that cost.

5. Finding what changed

The detector decides what enters the queue. Polling the whole library is slow and drains the battery.

Android: use MediaStore change signals. MediaStore.getVersion() (API 29) tells you if the store changed substantially since your last sync (check it at process start and rescan everything if it changed), and MediaStore.getGeneration() (API 30) returns a monotonically increasing number you can persist and compare to find items added or modified since then. Google's docs call generation numbers more robust than DATE_ADDED and DATE_MODIFIED, which can move when apps or users change timestamps and clocks. Register a ContentObserver for live changes while the process is alive, and run a catch-up scan on each scheduled run. The photo picker is the privacy-friendly route when the user selects items by hand. Automatic backup needs broad media access (READ_MEDIA_IMAGES, READ_MEDIA_VIDEO), which Play allows only when the picker cannot deliver your core functionality and you declare it in Play Console, so check that your use case qualifies under the photo and video permissions policy. On Android 14 and later users can also grant only selected photos (READ_MEDIA_VISUAL_USER_SELECTED). Detect that with checkSelfPermission on each run, because the partial access docs say not to store the state, and show "backing up N selected items" instead of "library backed up".

iOS: register a PHPhotoLibraryChangeObserver for live changes. It only reports while your app runs, so also save a PHPersistentChangeToken and call fetchPersistentChanges(since:) (iOS 16 and later; it throws) on launch and on background runs. If it fails with persistentChangeTokenExpired, fall back to a full re-sync. Respect limited-library access: if the user shares only some photos, you back up only those, and the UI should say so.

The cloud pushes too, but only as a hint. A push message can tell a device to pull /v1/changes sooner. It can be delayed or dropped, so the cursor pull stays the source of truth; the push SDK case study covers that.

What counts as an item. A photo can be several resources: the original, an edited render, a paired video for a Live Photo. I would decide up front which of these are backed up and say so, since the choice decides what "restore" and "delete" mean. That is my design call, not something the platform decides for you.

Do not trust modification dates alone. Check size and stamp cheaply, then confirm with a content hash. A renamed file with the same hash is a metadata update, not an upload.

Android specifics. I pick by who started the upload. A backup the user did not just ask for goes on ordinary constrained WorkManager jobs. A transfer the user starts goes on a user-initiated data transfer (UIDT) job on API 34 and up, with a foreground worker below that.

  • WorkManager is the default. An upload must survive process death, so it is never a viewModelScope coroutine. Hilt can inject the worker's dependencies (@HiltWorker). Constraints combine with AND, and if one stops being true mid-run, WorkManager stops the worker and retries when all hold again, so the upload must be resumable at any instant.
  • Long runs. WorkManager treats work that can exceed about 10 minutes as long-running and expects setForeground() with a notification, which runs the worker as a foreground service. Apps targeting API 34 or higher must declare a foreground service type. A dataSync foreground service is capped at 6 hours per 24 hours on Android 15 and later (the system calls onTimeout() and the service must stop), so each run has to checkpoint block states and expect to be rescheduled. See the timeout docs.
  • UIDT jobs. Google notes that on Android 16 long-running workers can exhaust the app's job quota and suggests UIDT jobs for transfers the user starts. They must be scheduled while the app is visible, need RUN_USER_INITIATED_JOBS and a notification, and are not subject to standby bucket quotas. The system can still stop them, so persist progress and expect onStartJob() to run again. No Jetpack library wraps UIDT, so gate it on API 34 and fall back to a foreground worker below that.
  • Quotas still apply to ordinary jobs. Android 16 also ties the runtime quota of regular and expedited jobs to the standby bucket, so plain workers can be stopped for quota too. Log WorkInfo.getStopReason() and keep chunks small so a quota stop costs one block.

Backoff and retries. Result.retry() uses exponential backoff (30 second default, 10 second minimum). Treat IOException, 408, 429 and 5xx as transient and honour Retry-After when the server sends it. Other 4xx responses are permanent and the item becomes FAILED, except the protocol cases: 404 on a session means start a new one, and 409 on commit is a conflict (section 7).

iOS specifics. For library photos on iOS 26.1 and later, Apple has a purpose-built path: a Photos background-upload extension in which you create PHAssetResourceUploadJobs for PHAssetResources, and the system runs the extension when it can. In-flight jobs are capped by PHAssetResourceUploadJob.jobLimit; the docs page states no value and I could not find the entitlement requirements, so check them before committing to it. The extension protocol is marked deprecated in the current docs, so confirm the replacement name for your target SDK. For your own files and older OS versions, use a background URLSession. A background URLSession hands the transfer to the system, which continues it while your app is suspended or not running and relaunches the app to deliver events. In general, background uploads must come from a file (check the current docs for your target iOS version). Re-create the session with the same identifier on launch so the delegate receives pending results; store the completion handler from application(_:handleEventsForBackgroundURLSession:completionHandler:) and call it on the main thread from urlSessionDidFinishEvents(forBackgroundURLSession:). Apple documents that a user force-quit cancels background transfers and the app is not relaunched until the user opens it again. BGProcessingTask is for work like hashing and planning; Apple says it runs only when the device is idle and may be interrupted, and requiring power or network narrows when it can run. iOS also added BGContinuedProcessingTask in iOS 26: a task that starts in the foreground and can continue in the background, with its progress shown in a Live Activity that the person can cancel. It should start from a user action, can still be terminated under resource pressure, and closing the app from the app switcher cancels it, so report progress and persist state. It suits user-started work like a visible upload, not automatic backup. Say plainly that iOS gives no guarantee of when a backup finishes.

7. Conflicts and versioning

Backup is mostly conflict-free: the device is the only writer. File sync is not.

  • Never overwrite silently. Every file has a server version. An edit commits with baseVersion. If the server's current version is newer, the commit returns 409.
  • On conflict, keep both. The common client-side answer is a conflicted copy (for example, report (Alex's conflicted copy).docx) so no edit is lost. Offer a merge only for formats you can merge.
  • Keep old versions. Blocks are immutable, so a version is just a block list. Restoring is a metadata write; garbage-collect unreferenced blocks after a retention period.
  • A delete must leave a marker. The marker (a tombstone) carries a version, so a stale upload from another device cannot bring the file back and baseVersion checks still work.

8. Progress UI and security

  • Progress comes from the database. Count confirmed blocks over total blocks, and throttle UI and notification updates to a few per second. Dedupe makes progress jump; that is fine.
  • Show the state, not just a bar: waiting for Wi-Fi, waiting for charger, uploading, paused, failed with a reason. Show "backed up" only after the commit succeeds.
  • Account limits. If the storage quota fills or the auth token expires mid-upload, say so in the UI and pause rather than burn retries. Refresh the token once and resume with the blocks still missing; a full quota is a state the user must fix, not an error to retry.
  • Freeing space. Offer to delete local copies only for items that are committed and confirmed by the server, and ask first.
  • In transit: TLS everywhere. Treat resumable session URIs as bearer tokens: short-lived, never logged. Keep the auth token in the Keystore or Keychain.
  • At rest: encrypt blocks on the server with per-user or per-file keys. End-to-end encryption breaks cross-user dedupe and server-side thumbnails and search, so raise it as a follow-up, not a default.

10. Battery, data and platform limits

  • Default to Wi-Fi and charging for bulk backup, with a cellular opt-in. Never poll; use the change APIs from section 5.
  • Upload the newest items first so recent photos are protected within minutes, and let the old library backfill trickle in.
  • Cap concurrency at a few blocks. More parallel connections raise radio and memory use for little gain.

11. How to build photo backup and file sync on iOS (Swift)

The design is the same: a local database of items, blocks, and sessions; a server-owned missing list; and a block-and-metadata split. The platform primitives are what change. The background URLSession sketch from the transfer step lives here.

ConcernAndroidiOS
Local DBRoomSwiftData or Core Data (or GRDB)

Durable transferWorkManager, UIDT jobsPhotos upload jobs on iOS 26.1+, background URLSession

What really changes:

  • The system owns the transfer, not you. Background URLSession tasks continue after your app is suspended, but you can't run arbitrary code between chunks. Plan blocks ahead, write them to files, and queue several tasks, instead of looping in a coroutine.
  • Uploads should be file-based. Write each block to a temp file and delete it once acknowledged.
  • Force-quit stops everything. Unlike WorkManager, nothing relaunches the app. Say this in the interview and describe the recovery on next launch.
  • No guaranteed schedule. Do cheap work (detect, hash) on launch and foreground, and let the background session carry the bytes.
  • Delegate wiring. A SwiftUI-lifecycle app needs @UIApplicationDelegateAdaptor to receive application(_:handleEventsForBackgroundURLSession:completionHandler:).

Sketch of the background upload of one block that was written to a temp file:

// One session per identifier, created once (for example in the SDK singleton), never per request.
static let backgroundSession: URLSession = {
    let config = URLSessionConfiguration.background(withIdentifier: "app.backup.uploads")
    config.isDiscretionary = true            // bulk backup: system may wait for Wi-Fi and power; applies to transfers started in the foreground. For a user-started upload set it to false
    // sessionSendsLaunchEvents already defaults to true for background configurations
    config.allowsCellularAccess = false      // user setting
    return URLSession(configuration: config, delegate: UploadDelegate.shared, delegateQueue: nil)
}()

func uploadBlock(sessionUri: URL, offset: Int, len: Int, total: Int, blockFileURL: URL) {
    var req = URLRequest(url: sessionUri)
    req.httpMethod = "PUT"
    req.setValue("bytes \(offset)-\(offset + len - 1)/\(total)", forHTTPHeaderField: "Content-Range")
    Self.backgroundSession.uploadTask(with: req, fromFile: blockFileURL).resume()
}

12. What changes by level

This level split is my own reading, not any company's rubric.

  • Mid-level: a working upload with WorkManager, a progress indicator, retry on failure, and Wi-Fi-only constraints. A sentence that fits: "The upload is a WorkManager job that retries and only runs on Wi-Fi."
  • Senior: resumable sessions with a server-owned missing list, block hashing and dedupe, streaming with constant memory, the MediaStore and Photos change APIs, and a clear account of what the OS will and will not run in the background. A sentence that fits: "The server owns what is stored, so a lost acknowledgement costs one block."
  • Staff: conflict and version design across devices, content-defined chunking and its cost, cross-user dedupe privacy and end-to-end encryption trade-offs, upload success metrics and quotas, rollout of a new chunk size without breaking old clients, and cost control on the backend. A sentence that fits: "I would ship the new chunk size behind a server flag and keep the old path until old clients fade out."

Staff answer: the decision and the rollout

Decision: I would share the protocol first: one written spec for sessions, missing blocks, commit and conflicts, plus conformance tests that both the Android and iOS uploaders must pass. I would share code through Kotlin Multiplatform only if duplicated bug fixes are measured to cost more than the shared module. If more than one app will consume the uploader, a small public contract (enqueue, observe progress, resolve conflict) is worth a platform team. Revisit trigger: the same sync bug fixed twice in a quarter, or a second app needing behavior the contract cannot express. The native vs cross-platform decision guide has the criteria.

What to measure: upload completion rate per attempt and per day, resume-after-interruption success, bytes re-sent and time to fully synced. Guardrail: no rise in data-loss or duplicate-file reports, and no rise in battery or cellular-data complaints for the new cohort.

Rollback on mobile: you cannot recall a build, so the server accepts both the old and new protocol while old clients exist. Roll out a new chunk size behind a server-controlled flag, keep the old path in the binary, and reject nothing until old-client traffic is negligible. Local migrations need a downgrade-safe format, or a forward-only migration with the flag off by default. The staff mobile loop guide has the full loop.

Opinion vs verified: the background-execution limits are from Apple and Android docs earlier on this page; the ownership model, compatibility rule and metrics are my opinion.

13. Follow-up questions worth practising

  1. How would you back up a 4 GB video on a flaky connection? (Block upload, server-owned missing list, constraints, foreground or UIDT work, progress in the database.)
  2. How do you avoid re-uploading a photo the user already backed up from another device? (Whole-file hash lookup, then block-level dedupe.)
  3. Two devices edit the same file offline. What happens? (baseVersion, 409, conflicted copy, no silent overwrite.)
  4. How would you add end-to-end encryption? (Encrypt before upload, effect on dedupe, thumbnails, and search, key recovery.)
  5. The user's storage fills halfway through a 4 GB upload. What do they see, and what does the uploader do? (Pause with a reason, no retry loop, resume with the blocks still missing.)
  6. How would a "free up space" button decide what is safe to delete? (Only committed, server-confirmed items, with a confirmation.)
  7. How do you show "backup complete" honestly? (Count only committed items; show reasons for the rest.)
