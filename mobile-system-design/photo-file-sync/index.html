Design photo backup and file sync (Android and iOS): resumable uploads and conflicts

How to read this. This page is the 45 minutes, in the order I would spend them. Schema, REST, code and platform tables are in the build guide; in a round I would not draw them unless asked. The pushes below are my reconstruction of the kinds of challenges public prep material reports, not transcripts of real rounds.

TL;DR. My answer: an upload is a durable, resumable job, not a request. The server, not the phone, says which pieces of a file it still lacks, and the phone sends only those. Progress lives in a local database, so a killed process costs one block. I never show "backed up" until the server has confirmed the whole file.

1. Scope and constraints (minutes 0 to 4)

A prompt I would expect: "Design photo backup for our app. Photos and videos from the camera roll should end up safe in the cloud." I ask four things and give my default:

  • How much is the phone? The app and its API contract, not the storage servers.
  • Direction? Camera roll to cloud only.
  • Sizes and conditions? Photos of 3 to 10 MB, videos up to several GB, Wi-Fi and charging by default.
  • Devices? One phone each.

Your call. The scope push I would expect: "Edits on two phones, and encrypted too." Which do you keep?

First instinct, and why it breaks. Say yes to both. Two writers need versions and conflicts from the first commit, and encryption changes what the server can compare, so the protocol gets redesigned halfway.

What I'd say. Neither yet. I design for one writer and keep both parked.

Say it. "Camera-roll backup, one way, is in. Edits on two phones and end-to-end encryption each change the upload protocol, so I'm parking them. Tell me if you want one earlier."

The push I would expect: "Which comes first?" Two phones: it adds a base version to the commit. Encryption goes last, since it costs cross-account dedupe.

2. Data and contracts (minutes 4 to 14)

Your call. Who knows what is already stored: a counter or flag the app keeps per file, the server alone, or a local database the app records its job in and the server corrects?

First instinct, and why it breaks. Keep an offset per file and add to it as chunks go out. If the response to a chunk is lost after the server stored it, or the process dies between send and save, the phone's number and the server's disagree. Trust the phone's number and you leave a gap in the file or send a chunk twice.

What I'd say. The local database holds the job: items, blocks and a session. The server owns the truth about what is stored, and the phone asks it instead of guessing. I reject a single byte offset: it assumes one contiguous stream and cannot skip blocks the server already has.

The push I would expect: "The user re-adds a video that is already in the cloud. Do you send it again?" No: the server answers a hash list with the blocks it lacks. The tables and REST sketch are in the build guide.

The contract fits in four lines on the board:

  • Open: size and block hashes in, a session and the missing blocks out. Asking again returns the current list.
  • Put block: one block with its hash; the server refuses a mismatch.
  • Commit: the block list and the version it was based on in, the new version out. The same list again returns the same version.
  • Changes: a cursor in, cloud changes and the next cursor out.

3. Client structure (minutes 14 to 22)

Your call. Who owns the upload: the screen's ViewModel, a foreground service held open until the backlog is done, or the OS scheduler working from a database the app writes?

First instinct, and why it breaks. The ViewModel launches the upload in its scope, or a foreground service keeps it going for the whole backlog. A ViewModel is cleared when its owner is destroyed (ViewModel overview), and an upload held in memory dies with the process; Android answers process death with small saved state (saved state). A dataSync foreground service in an app targeting Android 15 or later is documented to get 6 hours in any 24, then a few seconds to stop (timeouts).

What I'd say. The app plans the work and the OS carries it out. Items, blocks and sessions are rows. Constrained WorkManager jobs, whose queued work is documented to persist across restarts (persistent work), run the uploader. I reject the service, which the system can end, and an app-scoped coroutine, which dies with the process.

The push I would expect: "Where does the progress bar get its number?" From the database: confirmed blocks over total blocks, throttled to a few updates a second.

In Android's terms, Compose and the ViewModel are the UI layer, and SyncRepository is the data layer with the database, detector and two APIs as its data sources (data layer; Android documentation content from the Android Open Source Project, Apache License 2.0). Three rules:

  • The UI never touches the network. It observes the database.
  • The uploader runs in a data-layer component called by the worker, never by a Composable or ViewModel.
  • Blocks are immutable and named by hash; metadata says which blocks make which version.

4. Make the hard part work (minutes 22 to 40)

Two deep dives, both forced by the table in section 1.

4.1 The upload (minutes 22 to 33)

Your call. A 4 GB video is queued on a flaky connection. Do you send it as one request, as chunks the phone counts, or as the pieces the server says it still needs?

First instinct, and why it breaks. One request per file from a coroutine. The connection drops at 90 percent and the next attempt starts at zero, the process dies with the progress only in memory, and a lost response leaves it unsure whether the last chunk landed.

What I'd say.

Say it. "I read the file as a stream and hash each block, never holding the file in memory. I send the hashes; the server replies with the blocks it lacks. I upload only those, one PUT each, and mark a block uploaded only when the server acknowledges it. A commit with the full block list makes the version visible."

Drive's resumable upload and core tus both send one contiguous stream and resume by offset. I reject phone-counted chunks because they cannot skip blocks the server already has, so in my design the server owns a missing list. The upload code is in the build guide.

The push I would expect: "The user edits the photo after you hashed it." I re-hash each block just before sending it. A mismatch throws, the item goes back to hashing, and nothing is committed. A lost commit response is safe: the commit is idempotent on the block list. Sessions expire too: Google's resumable session URIs last one week (Drive uploads); on a 404 I open a new session, and stored blocks cost nothing.

4.2 Running the transfer (minutes 33 to 40)

Your call. The user is not looking at the app. What keeps the bytes moving: a service you hold open, a scheduled job with constraints, or the system's own transfer machinery?

First instinct, and why it breaks. Hold a foreground service or a coroutine until the backlog is done. The system ends the service at its limit, a constraint can stop the worker mid-run, and on iOS the app is suspended.

What I'd say.

Say it. "I pick by who started the upload. Automatic backup goes on constrained WorkManager jobs, not a service I hold open: unmetered network, charging, battery not low. A transfer the user just started goes on a user-initiated data transfer job on Android 14 and up. Every run checkpoints, so being stopped costs one block. On iOS the system owns the transfer, and I say that it guarantees no finish time."

The push I would expect: "How does the app know what is new without scanning the whole library?" On Android I persist the MediaStore generation number and ask for items changed since it. On iOS I save a persistent change token and fetch the changes since it at launch.

4.3 Where iOS changes the design

Same architecture, weaker guarantees. Swift is in the build guide.

  • The system owns the transfer. A background URLSession continues while the app is suspended, but I cannot count on running code between chunks, so I write blocks to files and queue tasks.
  • A force-quit cancels background transfers and nothing relaunches the app. I recover on the next launch from the database.
  • On iOS 26.1 and later the Photos background-upload path is the purpose-built route for library assets; I would check its requirements first.

Release reality:

  • A Play staged rollout can be halted, but phones that already have the update keep it (staged rollouts).
  • Old clients stay in the field, so the server accepts both protocols until old traffic is negligible.
  • A new chunk size ships behind a server-controlled flag with the old path kept in the binary. In my design that flag is the kill switch, the only rollback that reaches installed apps.
  • In my view a local migration cannot be flagged off. It needs a downgrade-safe format, or it ships forward-only with the flag off by default.

Say it. "I can't recall a bad build, so the rollback is the flag plus a fixed build. I'd watch completion rate, bytes re-sent, duplicate files and battery complaints. Left out: sharing, search, encryption."

6. Follow-ups that change a constraint

Practice prompts, not a claim about what any interviewer asks. They get harder.

  1. A 4 GB video over a connection that drops every few minutes. Strong: only missing blocks go up, state is per block, each run checkpoints, and the user sees a reason, not a stuck bar. Weak: "retry the upload."
  2. Any file type, edited later. Strong: a file is a list of blocks per version, an edit commits against the version it started from, and fixed blocks shift on insertion, so content-defined chunking is the cost to name. Weak: "upload the file again."
  3. Two phones edit the same file offline. Strong: the commit carries baseVersion, a newer server version returns 409, and I keep both as a conflicted copy. Weak: "last write wins."
  4. End-to-end encryption. Strong: encrypt before upload and name what breaks: cross-account dedupe, thumbnails, server search, key recovery. Weak: "encrypt the file first."
  5. After release, duplicate-file reports rise for a slice of users. Strong: flip the flag to the old path, pause the staged release, ship a fix. Weak: "roll back the release."
  6. The backend wants a new block size. Strong: old versions stay in the field, so the server speaks both shapes, cross-size dedupe is lost and I say so, and the flag moves cohorts gradually. Weak: assuming everyone updates.

7. What changes by level

These levels are my own reading of the bar, drawn from vendor and prep material (courses and books), not any company's rubric. The wording below is mine.

  • Mid-level: a WorkManager upload with retry. I want to hear: "The upload is a job that retries and only runs on Wi-Fi."
  • Senior: a server-owned missing list, block hashing, constant memory, and what each OS will not run in the background. I want to hear: "The server owns what is stored, so a lost acknowledgement costs one block."
  • Staff: conflicts across devices, dedupe against encryption, metrics, and a chunk-size rollout old clients survive (staff guide). I want to hear: "I'd ship the new chunk size behind a server flag and keep the old path until old clients fade."

As I read it, the levels differ in who raises the problem: the interviewer, the candidate, or the candidate with a rollout plan.

Common weak answers. Ten minutes on storage when the question was the phone. A happy path only. A ViewModel coroutine doing the upload. Showing "backed up" before the server confirmed. No kill switch. Reading the whole file into memory. These repeat across public prep material; they are not a dataset.

Staff answer: the decision and the rollout

Decision: share the protocol first: one written spec for sessions, missing blocks, commit and conflicts, with conformance tests both uploaders must pass. Share code through Kotlin Multiplatform only if duplicated bug fixes are measured to cost more. Alternative: one shared engine from day one. Revisit trigger: the same sync bug fixed twice in a quarter, or a second app needing behavior the contract cannot express. The native vs cross-platform guide has the criteria.

Rollout: the section 5 flag, then a staged release. Guardrail: no rise in data-loss, duplicate-file or battery complaints.

Opinion vs verified: the Android background cap, the session lifetime and the Apple force-quit behavior were read from official docs. The ownership model, protocol rule, metrics, assumed numbers and level signals are my opinion.
