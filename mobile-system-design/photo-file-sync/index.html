How to read this. This page follows the 45 minutes of the interview, in order. The schema, REST calls, code and platform tables are in the build guide. The follow-up questions are my reconstruction of challenges that public prep material reports, not transcripts of real rounds.

TL;DR. My answer: an upload is a saved job that can resume, not one request. The server says which blocks (pieces of a file) it lacks, and the phone sends only those. Progress is saved locally, so a killed app loses at most one block. I show "backed up" only after the server confirms the file.

1. Scope and constraints (minutes 0 to 4)

In short: Keep scope to one-way camera-roll backup, and name what the phone does to an upload.

A prompt I would expect: "Design photo backup for our app. Photos and videos from the camera roll should be safe in the cloud." I ask four questions and give a default:

  • How much is the phone? The app and its API contract, not the storage servers.
  • Which direction? Camera roll to cloud only.
  • Which sizes? Photos of 3 to 10 MB, videos up to several GB. Wi-Fi and charging by default.
  • How many devices? One phone.

Your decision. The scope question I expect: "Edits on two phones, and encrypted too." Which do you keep?

First idea, and why it fails. Say yes to both. Two writers need versions and conflict handling from the first commit. Encryption changes what the server can compare. The protocol then changes.

What I would say. Neither yet. I design for one writer.

Say this. "Camera-roll backup, one way, is in. Edits on two phones and end-to-end encryption each change the upload protocol, so I am parking them. Tell me if you want one earlier."

The follow-up question I expect:

"Which comes first?"

Two phones first, encryption last. Each has a cost:

  • Two phones: the commit needs a base version (the version the edit started from).
  • Encryption: it costs cross-account dedupe (storing identical files once).

2. Data and contracts (minutes 4 to 14)

In short: A local database holds the job, and the server owns what is stored.

Your decision. Who knows what is already stored? Pick one: a counter per file in the app, the server alone, or a local database that the app writes and the server corrects.

First idea, and why it fails. Keep an offset (a byte count) per file and add to it as blocks go out. Sometimes the server stores a block but the response is lost. Sometimes the app dies between the send and the save. Then they disagree, and you leave a gap or send a block twice.

What I would say. The local database holds the job: items, blocks and a session (the server's record of one upload in progress). The server owns the truth about what is stored, and the phone asks it. I reject a single byte offset.

The follow-up question I expect:

"The user adds a video that is already in the cloud. Do you send it again?"

No. The tables and REST sketch are in the build guide.

  • The phone sends the hashes (short fingerprints) of its blocks.
  • The server answers with the blocks it lacks (the missing list).

The contract has four calls:

  • Open: size and block hashes in; a session and the missing list out. Asking again returns the current list.
  • Put block: one block and its hash. The server refuses a wrong hash.
  • Commit: the block list and base version in; the new version out. The same list again returns the same version.
  • Changes: a cursor (a saved position) in; cloud changes and the next cursor out.

3. Client structure (minutes 14 to 22)

In short: The app plans the work in a database. The OS scheduler carries it out.

Your decision. Who owns the upload? The ViewModel (it holds the state of one screen), a foreground service kept open for the whole backlog, or the OS scheduler working from the app's database?

First idea, and why it fails. The ViewModel starts the upload, or a foreground service runs the whole backlog. Three things fail:

  • A ViewModel is cleared when its owner is destroyed (ViewModel overview). An upload held in memory dies with the process.
  • Android answers process death with a small saved state (saved state).
  • A dataSync foreground service in an app targeting Android 15 or later is documented to get 6 hours in any 24. Then it has a few seconds to stop (timeouts).

What I would say. The app plans the work and the OS carries it out. Items, blocks and sessions are database rows. Constrained WorkManager jobs run the uploader. WorkManager is Android's background-work library, and its queued work is documented to persist across restarts (persistent work). I reject the other two.

The follow-up question I expect:

"Where does the progress bar get its number?"

From the local database.

  • The number is confirmed blocks divided by total blocks.
  • Updates run a few times a second at most.

In Android's terms, Compose (the UI toolkit) and the ViewModel are the UI layer. SyncRepository is the data layer. The database, change detector and two APIs are its data sources (data layer; Android documentation content from the Android Open Source Project, Apache License 2.0). Three rules:

  • The UI observes the database and never touches the network.
  • The worker calls the uploader, which lives in the data layer. A Composable or ViewModel never runs it.
  • Blocks never change, and each is named by its hash. Metadata says which blocks make which version.

4. Make the hard part work (minutes 22 to 40)

In short: The server lists the blocks it lacks. The phone sends only those, and the OS runs the transfer.

4.1 The upload (minutes 22 to 33)

Your decision. A 4 GB video waits to upload on a weak connection. Do you send it as one request, as blocks the phone counts, or as the blocks the server says it still needs?

First idea, and why it fails. One request per file from a coroutine. Three things fail:

  • The connection drops at 90 percent, and the next try starts at zero.
  • The app dies, and the progress was only in memory.
  • A lost response leaves the app unsure whether the last block arrived.

What I would say.

Say this. "I read the file as a stream and hash each block. I never hold the file in memory. I send the hashes, and the server replies with the blocks it lacks. I upload only those, one PUT for each. I mark a block uploaded only when the server confirms it. A commit with the full block list makes the version visible."

Drive's resumable upload and core tus (an open resumable-upload protocol) both send one continuous stream and resume by offset. I reject blocks counted by the phone, because they cannot skip blocks the server already has. The code is in the build guide.

The follow-up question I expect:

"The user edits the photo after you hashed it."

I hash each block again just before I send it. If the hash differs, the code throws an error, the item goes back to hashing, and nothing is committed.

  • A lost commit response is safe. The commit is idempotent: doing it twice has the same result as doing it once.
  • Sessions expire: Google's resumable session URIs last one week (Drive uploads).
  • On a 404 I open a new session. Blocks the server already stored cost nothing.

4.2 Running the transfer (minutes 33 to 40)

Your decision. The user is not looking at the app. What keeps the bytes moving: a service you keep open, a scheduled job with constraints, or the system's own transfer feature?

First idea, and why it fails. Keep a foreground service or coroutine running until the backlog is done. Three things stop it:

  • The system ends the service at its limit.
  • A constraint can stop the worker mid-run.
  • On iOS the system suspends the app.

What I would say.

Say this. "I choose by who started the upload. Automatic backup uses constrained WorkManager jobs, not a service I keep open: unmetered network, charging, battery not low. A transfer the user starts uses a user-initiated data transfer job (Android 14 and up). Every run saves its progress, so a stop costs one block. On iOS the system owns the transfer and gives no finish time."

The follow-up question I expect:

"How does the app know what is new without scanning the whole library?"

I do not scan. I save a position and ask only for changes after it.

  • Android: I save the MediaStore generation number. MediaStore is Android's shared media database, and the number rises when media changes. I ask for items changed since it.
  • iOS: I save a persistent change token (a saved position in the change history). At launch I fetch the changes since it.

4.3 Where iOS changes the design

The design is the same, with weaker guarantees. Swift code is in the build guide.

  • The system owns the transfer. A background URLSession (Apple's networking API) continues while the app is suspended. I cannot count on running code between blocks, so I write each block to a file and create several tasks.
  • A force-quit cancels background transfers, and nothing restarts the app. I recover at the next launch.
  • On iOS 26.1 and later, the Photos background-upload path is built for library assets. I would check its requirements first.

In short: List how it fails, say what the user sees, and keep a server flag as the kill switch.

Release reality:

  • A Play staged rollout (a release to a growing share of users) can be halted, but phones with the update keep it (staged rollouts).
  • Old clients stay in use, so the server accepts both protocols until old traffic is small.
  • A new block size ships behind a server flag, with the old path kept in the app. In my design that flag is the kill switch, the only rollback that reaches installed apps.
  • In my view, a flag cannot turn off a local database migration. It needs a format that is safe to downgrade, or it ships forward-only with the flag off by default.

Say this. "I cannot recall a bad build, so the rollback is the flag plus a fixed build. I would watch completion rate, bytes sent again, duplicate files and battery complaints. Left out: sharing, search, encryption."

6. Follow-ups that change a constraint

In short: Each follow-up changes one constraint. A strong answer names what breaks and the fix.

These are practice prompts, not claims about interviewers.

  1. A 4 GB video over a connection that drops every few minutes. Strong: only missing blocks go up, state is per block, each run saves progress, and the user sees a reason, not a stuck bar. Weak: "retry the upload."
  2. Any file type, edited later. Strong: a file is a list of blocks per version, and an edit commits against the version it started from. Fixed blocks shift when bytes are inserted, so name content-defined chunking (cutting blocks by content, not position) as the cost. Weak: "upload the file again."
  3. Two phones edit the same file offline. Strong: the commit carries baseVersion. A newer server version returns 409, and I keep both as a conflicted copy. Weak: "last write wins."
  4. End-to-end encryption. Strong: encrypt before upload and name what breaks: cross-account dedupe, thumbnails, server search, key recovery. Weak: "encrypt the file first."
  5. After release, duplicate-file reports rise for some users. Strong: switch the flag to the old path, pause the staged release, ship a fix. Weak: "roll back the release."
  6. The backend wants a new block size. Strong: old versions stay in use, so the server speaks both shapes. Dedupe across sizes is lost, and I say so. The flag moves users in steps. Weak: assuming everyone updates.

7. What changes by level

In short: Levels differ in who raises the problem, and whether a rollout plan comes with it.

These levels are my own reading, drawn from vendor and prep material (courses and books). They are not any company's rubric.

  • Mid-level: a WorkManager upload with retry. I want to hear: "The upload is a job that retries and runs only on Wi-Fi."
  • Senior: a missing list owned by the server, block hashing, constant memory, and what each OS will not run in the background. I want to hear: "The server owns what is stored, so a lost acknowledgement costs one block."
  • Staff: conflicts across devices, dedupe against encryption, metrics, and a block-size rollout that old clients survive (staff guide). I want to hear: "I would ship the new block size behind a server flag and keep the old path until old clients disappear."

Common weak answers. Ten minutes on storage when the question was the phone. Only the happy path. A ViewModel coroutine doing the upload. Showing "backed up" before the server confirmed. No kill switch. Reading the whole file into memory.

Staff answer: the decision and the rollout

Decision: share the protocol first. Write one spec for sessions, missing blocks, commit and conflicts, with tests that both uploaders must pass. Share code through Kotlin Multiplatform only if duplicated bug fixes are measured to cost more.

Alternative: one shared engine from day one.

Revisit trigger: the same sync bug fixed twice in a quarter, or a second app needing behavior the contract cannot express. See the native vs cross-platform guide.

Rollout: the flag from section 5, then a staged release. Guardrail: no rise in data-loss, duplicate-file or battery complaints.

Opinion vs verified: I read the Android background cap, the session lifetime and the Apple force-quit behavior in the official docs. The ownership model, protocol rule, metrics, assumed numbers and level signals are my opinion.
