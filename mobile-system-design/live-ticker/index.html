Design a stock ticker app (Android and iOS): streaming, conflation and resync

How to read this. Sections 1 to 8 are the platform-neutral design, with Kotlin/Android code. Section 9 shows what changes on iOS. The architecture is identical on both; the platform primitives differ.

TL;DR. The server is the source of truth for prices; the client holds a last-known snapshot and applies deltas on top of it. Subscribe only to symbols on screen or in the watchlist, and release them when the screen goes away. Conflate ticks so the UI renders the latest value, not every value. Number every update per symbol so you can detect a gap and resync with a snapshot. Never use a binary float for money. Always show how old a price is.

1. Clarify the requirements (about 5 min)

Questions worth asking:

  • Which assets and how many symbols? (Assume equities, a watchlist of up to about 50 symbols, a universe of thousands for search.)
  • How real-time? (Assume real-time for the visible screen, delayed or snapshot data is acceptable elsewhere.)
  • Which screens? (Watchlist, symbol detail with a chart, price alerts.)
  • Which markets? (Assume several exchanges in different time zones, so "market closed" is a per-symbol fact.)
  • Offline? (Always-online product: show last known prices marked stale.)

Functional: search symbols, manage a watchlist, see live prices, open a chart for a range (1D, 1W, 1Y), set a price alert and get a push when it triggers.

Non-functional:

ConcernTarget
Render rateAt most one UI update per frame, regardless of tick rate
CorrectnessPrices are exact decimals; no silent gaps after reconnect
FreshnessEvery price shows its age; market-closed state is explicit
Battery and dataSocket only while visible; subscribe only to what is on screen
Cold startWatchlist rendered from cache, marked stale, then refreshed with a snapshot
AccessibilityScreen readers are not flooded by tick updates

Out of scope: order entry, news, options, order books. Say this out loud.

2. High-level architecture (about 10 min)

How this maps to Android's architecture guidance: the Compose screen and its ViewModel are the UI layer. QuoteRepository is the single entry point to the data layer, and the REST client, the QuoteStream socket and the local DB sit behind it. I skip a domain layer; I would add use cases only if two screens shared logic. See the Android architecture recommendations.

Why a WebSocket? The stream is two-way: the client subscribes and unsubscribes as screens come and go. If it were one-way, server-sent events would be simpler. I would rule out polling at this update rate, because each request pays connection and header cost for data that is already old.

Two decisions shape the rest. First, live ticks do not go to the database. Writing every tick to disk costs battery and I/O for data that is obsolete in a second. Ticks live in a conflated in-memory map; only the watchlist and the last snapshot per symbol are persisted. This is a conscious exception to the single-source-of-truth rule, which makes sense for ephemeral data and not for anything the user would be upset to lose. Second, the socket exists only while the app is visible: nothing is worth delivering while the user is not looking, and alerts go through push.

3. Data model and API

Money is a decimal

Never use Double or Float for a price. Binary floating point cannot represent most decimal fractions exactly, so sums and comparisons drift. On Android use BigDecimal, which stores an integer unscaled value plus a scale (java.math.BigDecimal, which Android ships too). On iOS use Decimal, a base-10 number type. On the wire, send prices as strings ("187.42"), so JSON number parsing never touches a float. One trap: BigDecimal equality includes scale, so 1.0 and 1.00 are not equals. Compare with compareTo, and normalize scale at the parse boundary.

Models

data class Quote(
    val symbol: String,
    val price: BigDecimal,
    val seq: Long,               // per-symbol sequence from the server
    val serverTime: Instant,     // when the exchange or feed produced it
    val marketState: MarketState // OPEN, CLOSED, PRE, POST, HALTED
)

serverTime drives the "last updated" label. seq is assigned by the server per symbol and, in this design, is contiguous: that is what lets the client detect a gap by counting. Chat's seq is different, because gaps there are allowed and healed by a cursor sync, and the analytics page uses a client-side counter with the same name. See the chat case study.

REST

GET  /v1/quotes?symbols=AAPL,MSFT      → [{ symbol, price, seq, serverTime, marketState }]   (snapshot)
GET  /v1/symbols/{s}/history?range=1D&points=300   → { open, points: [[t, price], ...] }
PUT  /v1/watchlist/{symbol}                          (idempotent)
POST /v1/alerts   { symbol, condition, price, clientId }   (idempotent on clientId)

WebSocket messages

client → server:  subscribe { symbols }, unsubscribe { symbols }
server → client:  snapshot { symbol, price, seq, ts }
                  tick     { symbol, price, seq, ts }
                  market   { exchange, state }

The history call asks for a point count so the server downsamples and the client never receives more points than pixels.

4. The hard part: stream, conflate, render

A busy symbol can tick many times per frame (about 16 ms at 60 Hz). Rendering per tick wastes CPU and battery, because nobody can read the intermediate values. The rule is: process every tick, render the latest.

Pipeline on Android: socket frames are parsed on a background dispatcher, applied to an in-memory map, and exposed as a StateFlow. The kotlinx.coroutines docs state that a StateFlow always conflates updates, so a slow collector skips intermediate values and gets the most recent one, and that equal consecutive values are suppressed using equals. For a plain Flow, conflate() does the same thing: the emitter is never suspended by a slow collector, and the collector always gets the most recent value. sample(period) emits at most the latest value per period, but it is marked @FlowPreview, and its docs say the latest element is not emitted if it does not fit into the sampling window. For prices that matters: the last value of a burst can be dropped and a row can sit on a stale number.

// Sketch: applying ticks. Single collector coroutine, so book.value and resyncing are only touched from it.
class QuoteStream(private val socket: QuoteSocket) {
    private val book = MutableStateFlow<Map<String, Quote>>(emptyMap())
    val quotes: StateFlow<Map<String, Quote>> = book.asStateFlow()
    private val resyncing = HashSet<String>()   // symbols waiting for a snapshot

    suspend fun run() = socket.events().collect { e ->
        when (e) {
            is Event.Snapshot -> {
                resyncing.remove(e.quote.symbol)
                book.update { it + (e.quote.symbol to e.quote) }
            }
            is Event.Tick -> onTick(e)
        }
    }

    private fun onTick(t: Event.Tick) {
        val cur = book.value[t.symbol]
        when {
            t.symbol in resyncing -> Unit                                  // waiting for the snapshot
            cur != null && t.seq <= cur.seq -> Unit                        // duplicate or old
            cur == null || t.seq != cur.seq + 1 -> {                       // no snapshot yet, or a gap
                resyncing += t.symbol
                socket.requestSnapshot(t.symbol)                           // asked once per gap
            }
            else -> book.update { it + (t.symbol to cur.copy(price = t.price, seq = t.seq, serverTime = t.ts)) }
        }
    }
}

The resyncing set is what makes step 3 in section 6 true. Without it, every later tick of a gapped symbol also fails the seq check and asks for another snapshot, so one gap turns into a burst of requests. A snapshot overwrites the entry unconditionally, which is what a reconnect needs. It also means a late snapshot can move seq backwards, so the server should only send one in answer to a request. One limit of the sketch: if a requested snapshot never arrives, that symbol stays in resyncing and ignores ticks. A reconnect, or a timeout on the request, has to clear the set, and I left that out.

The ViewModel exposes one immutable uiState, built from the repository's flows with stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), initial), so the pipeline stops shortly after the screen stops collecting.

The data layer owns the socket loop. It runs QuoteStream.run() in an injected external CoroutineScope, started on the first subscriber. Not viewModelScope, and not WorkManager, because nothing here needs to survive the process dying.

In Compose, collect with collectAsStateWithLifecycle(), which by default starts collecting at STARTED and stops at STOPPED, so the UI stops observing in the background. Compose applies state changes once per frame, so extra writes between frames should cost little. That is my reading, not something I measured, so I would profile before relying on it. If a list still recomposes too often, hand each row only its own symbol's value so one tick recomposes one row. Avoid .sample(100) on prices for the reason above; if you cap the rate, prefer conflate() plus a short delay in the collector (my suggestion, not documented), and keep the age label so a stale row is visible. The value is a tuning knob.

Replacing the whole map on every tick allocates. That is fine at tens of symbols; say that you chose the simple form.

5. Subscriptions: only what is visible

A socket subscribed to everything burns data and CPU. Subscribe to the union of (a) symbols on the visible screen and (b) the watchlist if it is on screen. Use a reference count per symbol, so two screens showing AAPL cause one subscribe, and the unsubscribe happens only when both are gone.

// Sketch: ref-counted subscriptions, a data layer class; screens reach it only through the ViewModel and repository
class Subscriptions(private val socket: QuoteSocket) {
    private val refs = mutableMapOf<String, Int>()

    @Synchronized fun acquire(symbol: String) {
        val n = (refs[symbol] ?: 0) + 1
        refs[symbol] = n
        if (n == 1) socket.subscribe(symbol)
    }

    @Synchronized fun release(symbol: String) {
        val n = (refs[symbol] ?: return) - 1
        if (n == 0) { refs.remove(symbol); socket.unsubscribe(symbol) } else refs[symbol] = n
    }

    @Synchronized fun active(): Set<String> = refs.keys.toSet()   // for re-subscribing after a reconnect
}

Tie acquire and release to visibility, not to object creation: on Android the screen calls ViewModel methods (for example onSymbolsVisible) from a DisposableEffect or lifecycle effect, and the ViewModel calls the repository, never Subscriptions directly; on iOS use onAppear and onDisappear. Delay the release briefly so a quick back-and-forth does not thrash the server. After a reconnect, re-send the whole current set, which active() returns. The sketch calls the socket while holding the lock; that is fine at this size, and I would move the socket calls out of the lock if they could block.

6. Correctness: sequence numbers, gaps, resync

A reconnect loses whatever was in flight. Each symbol carries a server seq that increases by one per update:

  1. A tick with seq <= last is a duplicate or late packet. Drop it.
  2. A tick with seq == last + 1 is applied.
  3. A tick with seq > last + 1 is a gap. Do not apply it. Request a snapshot for that symbol, once, and ignore deltas for it until the snapshot arrives.
  4. On reconnect, re-subscribe; the server replies with a snapshot per symbol, and the client resets seq from it.

The client never replays history; a snapshot is cheap and self-healing. Reconnect with exponential backoff and jitter so a server restart does not produce a thundering herd; the chat case study gives an example schedule (1 s up to about 30 s, randomized).

An open socket is not a live one. A connection can stay open while nothing arrives, for example behind a flaky network or a proxy. Send a ping on an interval and treat a missing pong as a dead connection: rebuild it, re-send the subscriptions and take snapshots. OkHttp has a pingInterval setting for this and URLSessionWebSocketTask has sendPing; I did not check how OkHttp reports a missed pong, so test that on your version. A long-lived socket also outlives its auth token. Refresh the token and re-authenticate without dropping the subscription set, and let the server tag each quote as real-time or delayed (see the follow-ups).

For a plain last-price display, a missed tick is harmless. The gap check matters when the stream carries state that is not self-contained, such as volume totals or an order book. State which case you are in.

7. Charts, stale data, time zones

Charts. Fetch the history for the selected range, already downsampled by the server (a 1Y daily chart needs a few hundred points). Append live ticks to the last candle in memory; do not refetch. On Android, draw with the Compose Canvas composable, which wraps Modifier.drawBehind. Build the Path once and cache it with Modifier.drawWithCache, which keeps objects until the size or read state changes. Do the downsampling and point math off the main thread. On iOS, Swift Charts (iOS 16 and later) with LineMark covers a standard line chart; for thousands of points or a custom crosshair, draw with Core Graphics or a Canvas in SwiftUI.

Stale data. Three states, always visible: live (a tick within the expected interval), stale (connected but no recent update, or restored from cache), closed (the market state says so). Show "Updated 14:03:21" or "2 min ago" next to the price, and gray the price when stale. A closed market is not an error: show the close price and "Market closed", and stop expecting ticks.

Time zones. Exchanges trade in their own zones. Store instants in UTC, and format with the device zone for "last updated" and the exchange zone for "opens 9:30 ET". Never hard-code offsets; DST changes them. Apple's TimeZone is keyed by identifiers such as America/Los_Angeles. Use IANA identifiers like America/New_York (ZoneId on Android, TimeZone on iOS), never raw offsets. Let the server send marketState and the next open time, so holidays and half days are not client logic.

Derived values. Half of a ticker UI is numbers computed from the price. The day change is the price minus the previous close, and the percent is that change divided by the previous close. I would take the previous close from the server in the snapshot rather than derive it from ticks, and compute both with the decimal type, not a double. Format with the user's locale, but keep the decimal places the exchange sends. Show direction with an arrow or sign, and treat halted and auction states as their own display state instead of a frozen live price.

Always-online stance. Offline, show the cached watchlist from the last snapshot, every row marked stale with its age, and a banner. Disable alert creation, since the server holds the rules. Nothing is queued. Creating an alert needs the server, so it fails fast instead of waiting. A watchlist edit is saved locally first and synced with a plain PUT. Quotes are fetched as snapshots on demand, with deltas streaming in only while the screen is visible.

8. Lifecycle, alerts, accessibility, failure modes

Backgrounding. On the way to the background, close the socket and clear subscriptions. On return, reconnect, re-subscribe, and take snapshots; do not try to replay missed ticks.

Price alerts. The server evaluates alert rules against the feed, so alerts fire when the app is closed. When one triggers, the server sends a push. Treat the push as a hint plus a short text ("AAPL crossed 190.00"); tapping opens the symbol, which loads a fresh snapshot. APNs limits payloads to 4 KB for most notifications, so send identifiers, not data. Creating the alert is a POST: if it fails, retry with the same clientId when the cause is transient (an I/O error, 408, 429 honouring Retry-After when present, or 5xx) and treat other 4xx as permanent.

Accessibility. Do not announce ticks. Android's accessibility guidance warns against live regions on fast-changing text such as a countdown, because the screen reader would talk over itself. Leave the price as plain readable text, and use a polite live region only for rare state changes such as "Market closed" or "Alert triggered". On iOS, the updatesFrequently trait tells assistive technology to poll for changes instead of expecting notifications. Show movement with a sign or arrow, not color alone.

Failure modes.

ScenarioHandling
Socket dropsMark rows stale, reconnect with backoff and jitter, re-subscribe, snapshot
Gap in seqDrop the delta, fetch a snapshot for that symbol
Duplicate or late tickIgnore when seq <= last
Device clock wrongAge from serverTime; clamp negative ages to zero
Market closed or haltedShow close price and state, stop the stale timer

9. How to build a stock ticker app on iOS (Swift)

The design is the same. Only the primitives change.

What is genuinely different:

  • Conflation is an explicit buffering choice. AsyncStream buffers without limit by default. A fast feed with a slow consumer then grows memory. Choose .bufferingNewest(1): when the buffer is full, the oldest element is discarded, so the consumer sees the latest state.
  • Apple documents no reconnect behavior for URLSessionWebSocketTask. Treat a failed receive as the end of the task, then rebuild it and resubscribe yourself. It supports ping (sendPing) for liveness checks and maximumMessageSize as a safety limit. Apple's docs describe the receive API as returning a message once all of its frames are available.
  • Backgrounding is driven by scenePhase. Close the socket with cancel(with:reason:) when the phase leaves .active; .background means the scene is not visible.
  • Money. Decimal is a base-10 type. Initialize it from a string, not a Double, or you import the binary error you were avoiding. That is also why the wire format uses strings: JSONDecoder reads a JSON number through a Double. I have not verified either point against Apple's docs. If you use Decimal(string:), pass Locale(identifier: "en_US_POSIX"), since some overloads are locale-sensitive (also unverified).
// Sketch: sequence-checked book exposed as a conflated stream.
// AsyncStream.makeStream is listed on Apple's page for iOS 13+ (back-deployed before iOS 17).
struct Quote: Sendable { let symbol: String; var price: Decimal; var seq: Int; var ts: Date }

actor QuoteBook {
    let updates: AsyncStream<[String: Quote]>
    private let out: AsyncStream<[String: Quote]>.Continuation
    private var book: [String: Quote] = [:]
    private var resyncing = Set<String>()   // symbols waiting for a snapshot

    init() {
        let pair = AsyncStream.makeStream(of: [String: Quote].self, bufferingPolicy: .bufferingNewest(1))
        updates = pair.stream
        out = pair.continuation
    }

    func snapshot(_ q: Quote) { resyncing.remove(q.symbol); book[q.symbol] = q; out.yield(book) }

    /// Returns true to request a snapshot: once per gap, or when there is no snapshot yet.
    /// Ticks for a symbol that is waiting for its snapshot are ignored.
    func tick(_ q: Quote) -> Bool {
        if resyncing.contains(q.symbol) { return false }
        let cur = book[q.symbol]
        if let cur, q.seq <= cur.seq { return false }            // duplicate or old
        guard let cur, q.seq == cur.seq + 1 else {               // no snapshot yet, or a gap
            resyncing.insert(q.symbol)
            return true
        }
        book[q.symbol] = q
        out.yield(book)
        return false
    }
}

// Consumer, e.g. in a @MainActor view model. The sleep caps the render rate.
// for await latest in quoteBook.updates { self.quotes = latest; try? await Task.sleep(for: .milliseconds(100)) }

The actor keeps the same resyncing set as the Kotlin version. tick returns true only when the caller should send requestSnapshot for that symbol, which is once per gap; every later tick of that symbol returns false until snapshot clears it. The same lost-snapshot limit applies.

10. What changes by level

This split is my own reading of how the levels differ, not a published rubric.

  • Mid-level: a WebSocket for live prices, REST for history, a local watchlist, throttled UI updates, decimal prices.
  • Senior: ref-counted subscriptions tied to visibility, conflation with a reason, per-symbol seq with gap detection and snapshot resync, stale and market-closed states, closing the socket in the background, not announcing ticks.
  • Staff: which screens may hold a socket at all, a stream module shared by the app, widget and watch, what the kill switch turns off, the feed's cost model (fan-out, subscription limits, real-time versus delayed entitlements), and metrics such as time to first price and gap and resync rate.

Staff answer: the decision and the rollout

Decision: one shared stream module that owns the socket, the subscription ref counts and the seq checks, with each app surface asking it for symbols instead of opening its own connection. The alternative is per-surface sockets, which is simpler to start and multiplies connections and gap bugs. Revisit trigger: a surface with a different freshness need, such as a widget or watch, where snapshots are enough and the shared module is dead weight.

What to measure: time to first price, gap and resync rate, reconnects per session, and battery per session. Guardrail: the resync rate must not rise, and dropped frames on the watchlist must not worsen, while a change rolls out.

Rollback on mobile: you cannot recall a build from installed phones. Rollback is a server-controlled kill switch that tells clients to stop streaming and fall back to snapshot polling, plus a staged rollout you can halt. Halting does not uninstall the update. The server should keep serving old clients the same snapshot and tick formats for as long as they are installed.

Opinion vs verified: the API behaviors above were read from vendor docs, listed in the notes below. The module split, the metrics and the kill switch are my opinion. See the staff mobile loop guide and the native vs cross-platform decision guide for the shape of the decision.

11. Follow-up questions worth practising

  1. How would you add a home screen widget? (Widgets do not hold a socket; use snapshot timelines. Verify platform refresh limits before promising a frequency.)
  2. How do you handle delayed versus real-time data? (The server decides per user and tags each quote; the client labels it.)
  3. How do you test this? (A fake socket emitting ordered, duplicate, late and gapped sequences; a fake clock for stale transitions.)
  4. The market opens and 2,000 symbols tick at once. What gives first? (Practise naming it: parsing, the in-memory map, the main thread, or the server's send buffer. Conflation and per-row state are the levers.)
  5. How do you notice a connection that is open but dead? (A ping on an interval and a missed pong as the signal; compare with a reconnect storm.)
  6. What would make you add a news feed to the same screen? (See the news feed case study for the cache-first contrast with an always-online screen.)
