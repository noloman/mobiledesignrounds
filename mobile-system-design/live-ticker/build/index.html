Draft v1. Companion to the live stock ticker interview case.

This is the implementation material behind the live stock ticker interview case. It covers the money type, wire formats, stream and subscription code, sequence numbers, charts, stale and closed states, alerts, accessibility, platform limits and the iOS version. None of it belongs in the 45 minutes; I draw it only if asked.

The Kotlin snippets use plain coroutines and StateFlow. The Swift one uses an actor and AsyncStream. Both are sketches. Event, QuoteSocket and MarketState are app-defined, and the snippets leave out injection of the repository, the ViewModel and the dispatchers.

1. Money is a decimal

Never use Double or Float for a price. Binary floating point cannot represent most decimal fractions exactly, so sums and comparisons drift.

On Android use BigDecimal, which stores an integer unscaled value plus a scale (java.math.BigDecimal, which Android ships too). On iOS use Decimal, a base-10 number type. On the wire, send prices as strings ("187.42"), so JSON number parsing never touches a float.

One trap: BigDecimal equality includes scale, so 1.0 and 1.00 are not equals. Compare with compareTo, and normalize scale at the parse boundary.

data class Quote(
    val symbol: String,
    val price: BigDecimal,
    val seq: Long,               // per-symbol sequence from the server
    val serverTime: Instant,     // when the exchange or feed produced it
    val marketState: MarketState // OPEN, CLOSED, PRE, POST, HALTED
)

serverTime drives the "last updated" label. seq is assigned per symbol and, in this design, is contiguous: that is what lets the client detect a gap by counting. It is a promise from my gateway to each client, not something an exchange feed hands you.

Chat's seq is different, because gaps there are allowed and healed by a cursor sync, and the analytics page uses a client-side counter with the same name. See the chat case study.

2. REST and WebSocket messages

GET  /v1/quotes?symbols=AAPL,MSFT      → [{ symbol, price, seq, serverTime, marketState }]   (snapshot)
GET  /v1/symbols/{s}/history?range=1D&points=300   → { open, points: [[t, price], ...] }
PUT  /v1/watchlist/{symbol}                          (idempotent)
POST /v1/alerts   { symbol, condition, price, clientId }   (idempotent on clientId)
client → server:  subscribe { symbols }, unsubscribe { symbols }
server → client:  snapshot { symbol, price, seq, ts }
                  tick     { symbol, price, seq, ts }
                  market   { exchange, state }

The history call asks for a point count so the server downsamples and the client never receives more points than pixels.

3. The stream: apply every tick, render the latest

A busy symbol can tick many times per frame (about 16 ms at 60 Hz). Rendering per tick wastes CPU and battery, because nobody can read the intermediate values. The rule is: process every tick, render the latest.

Pipeline on Android: socket frames are parsed on a background dispatcher, applied to an in-memory map, and exposed as a StateFlow. The kotlinx.coroutines docs state that a StateFlow always conflates updates. A slow collector skips intermediate values and gets the most recent one. Equal consecutive values are suppressed using equals.

For a plain Flow, conflate() does the same thing. The emitter is never suspended by a slow collector, and the collector always gets the most recent value.

The sample(period) operator emits at most the latest value per period. It is marked @FlowPreview, and its docs say the latest element is not emitted if it does not fit into the sampling window. For prices that matters. The last value of a burst can be dropped, and a row can sit on a stale number.

// Sketch: applying ticks. Single collector coroutine, so book.value and resyncing are only touched from it.
class QuoteStream(private val socket: QuoteSocket) {
    private val book = MutableStateFlow<Map<String, Quote>>(emptyMap())
    val quotes: StateFlow<Map<String, Quote>> = book.asStateFlow()
    private val resyncing = HashSet<String>()   // symbols waiting for a snapshot

    suspend fun run() = socket.events().collect { e ->
        when (e) {
            is Event.Snapshot -> {
                resyncing.remove(e.quote.symbol)
                book.update { it + (e.quote.symbol to e.quote) }
            }
            is Event.Tick -> onTick(e)
        }
    }

    private fun onTick(t: Event.Tick) {
        val cur = book.value[t.symbol]
        when {
            t.symbol in resyncing -> Unit                                  // waiting for the snapshot
            cur != null && t.seq <= cur.seq -> Unit                        // duplicate or old
            cur == null || t.seq != cur.seq + 1 -> {                       // no snapshot yet, or a gap
                resyncing += t.symbol
                socket.requestSnapshot(t.symbol)                           // asked once per gap
            }
            else -> book.update { it + (t.symbol to cur.copy(price = t.price, seq = t.seq, serverTime = t.ts)) }
        }
    }
}

The resyncing set is what makes step 3 in section 5 true. Without it, every later tick of a gapped symbol also fails the seq check and asks for another snapshot, so one gap turns into a burst of requests.

A snapshot overwrites the entry unconditionally, which is what a reconnect needs. It also means a late snapshot can move seq backwards, so the server should only send one in answer to a request.

One limit of the sketch: if a requested snapshot never arrives, that symbol stays in resyncing and ignores ticks. A reconnect, or a timeout on the request, has to clear the set, and I left that out.

The ViewModel exposes one immutable uiState, built from the repository's flows with stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), initial), so the pipeline stops shortly after the screen stops collecting.

The data layer owns the socket loop. It runs QuoteStream.run() in an injected external CoroutineScope, started on the first subscriber. Not viewModelScope, and not WorkManager, because nothing here needs to survive the process dying.

In Compose, collect with collectAsStateWithLifecycle(), which by default starts collecting at STARTED and stops at STOPPED, so the UI stops observing in the background. Compose applies state changes once per frame, so extra writes between frames should cost little. That is my reading, not something I measured, so I would profile before relying on it.

If a list still recomposes too often, hand each row only its own symbol's value, so one tick recomposes one row. Avoid .sample(100) on prices for the reason above. If you cap the rate, prefer conflate() plus a short delay in the collector (my suggestion, not documented). Keep the age label so a stale row is visible. The delay is a tuning knob.

Replacing the whole map on every tick allocates. That is fine at tens of symbols; say that you chose the simple form.

4. Subscriptions: only what is visible

A socket subscribed to everything burns data and CPU. Subscribe to the union of (a) symbols on the visible screen and (b) the watchlist if it is on screen. Use a reference count per symbol, so two screens showing AAPL cause one subscribe, and the unsubscribe happens only when both are gone.

// Sketch: ref-counted subscriptions, a data layer class; screens reach it only through the ViewModel and repository
class Subscriptions(private val socket: QuoteSocket) {
    private val refs = mutableMapOf<String, Int>()

    @Synchronized fun acquire(symbol: String) {
        val n = (refs[symbol] ?: 0) + 1
        refs[symbol] = n
        if (n == 1) socket.subscribe(symbol)
    }

    @Synchronized fun release(symbol: String) {
        val n = (refs[symbol] ?: return) - 1
        if (n == 0) { refs.remove(symbol); socket.unsubscribe(symbol) } else refs[symbol] = n
    }

    @Synchronized fun active(): Set<String> = refs.keys.toSet()   // for re-subscribing after a reconnect
}

Tie acquire and release to visibility, not to object creation. On Android the screen calls ViewModel methods (for example onSymbolsVisible) from a DisposableEffect or lifecycle effect. The ViewModel calls the repository, never Subscriptions directly. On iOS use onAppear and onDisappear.

Delay the release briefly so a quick back-and-forth does not thrash the server. After a reconnect, re-send the whole current set, which active() returns. The sketch calls the socket while holding the lock. That is fine at this size; I would move the socket calls out of the lock if they could block.

5. Sequence numbers, gaps, resync and a dead link

A reconnect loses whatever was in flight. Each symbol carries a seq that increases by one per update:

  1. A tick with seq <= last is a duplicate or late packet. Drop it.
  2. A tick with seq == last + 1 is applied.
  3. A tick with seq > last + 1 is a gap. Do not apply it. Request a snapshot for that symbol, once, and ignore deltas for it until the snapshot arrives.
  4. On reconnect, re-subscribe; the server replies with a snapshot per symbol, and the client resets seq from it.

The client never replays history; a snapshot is cheap and self-healing. Reconnect with exponential backoff and jitter, so a server restart does not produce a thundering herd. The chat case study gives an example schedule (1 s up to about 30 s, randomized).

For a plain last-price display, a missed tick is harmless, because the next one carries the whole truth. The gap check matters when the stream carries state that is not self-contained. The live candle's high, low and volume are accumulated from ticks, so a missed tick can leave them wrong until the next snapshot. State which case you are in.

An open socket is not a live one. A connection can stay open while nothing arrives, for example behind a flaky network or a proxy. Send a ping on an interval and treat a missing pong as a dead connection: rebuild it, re-send the subscriptions and take snapshots.

OkHttp has a pingInterval setting for this and URLSessionWebSocketTask has sendPing. I did not check how OkHttp reports a missed pong, so test that on your version. Android's network-state guide says a captive-portal network has the internet capability but is not validated, so a connectivity callback alone does not prove the stream is alive.

A long-lived socket also outlives its auth token. Refresh the token and re-authenticate without dropping the subscription set. Let the server tag each quote as real-time or delayed (see follow-up 4 on the interview page).

6. Charts, stale data, time zones, derived values

Charts. Fetch the history for the selected range, already downsampled by the server (a 1Y daily chart needs a few hundred points). Append live ticks to the last candle in memory; do not refetch.

On Android, draw with the Compose Canvas composable, which wraps Modifier.drawBehind. Build the Path once and cache it with Modifier.drawWithCache, which keeps objects until the size or read state changes. Do the downsampling and point math off the main thread.

On iOS, Swift Charts (iOS 16 and later) with LineMark covers a standard line chart. For thousands of points or a custom crosshair, draw with Core Graphics or a Canvas in SwiftUI.

Stale data. Keep two clocks apart. The connection is live while heartbeats keep arriving, and stale when they stop or when the prices came from the cache. Each row also has its own age, shown next to the price ("Updated 14:03:21" or "2 min ago").

A quiet symbol with a healthy connection is old, not stale. An illiquid name can go minutes without a tick, and graying it would tell the user the app is broken. When the connection is stale, gray every price.

Closed comes from the market state. A closed market is not an error: show the close price and "Market closed", and stop expecting ticks.

Time zones. Exchanges trade in their own zones. Store instants in UTC, and format with the device zone for "last updated" and the exchange zone for "opens 9:30 ET". Never hard-code offsets; DST changes them. Use IANA identifiers like America/New_York (ZoneId on Android, TimeZone on iOS), never raw offsets. Let the server send marketState and the next open time, so holidays and half days are not client logic.

Derived values. Half of a ticker UI is numbers computed from the price.

  • The day change is the price minus the previous close.
  • The percent is that change divided by the previous close.

I would take the previous close from the server rather than derive it from ticks. It needs a field on the snapshot; the listing in section 2 leaves it out. Compute both values with the decimal type, not a double.

Format with the user's locale, but keep the decimal places the exchange sends. Show direction with an arrow or sign. Treat halted and auction states as their own display state instead of a frozen live price.

Always-online stance. Offline, show the cached watchlist from the last snapshot, every row marked stale with its age, and a banner. Disable alert creation, since the server holds the rules. Nothing is queued, so creating an alert fails fast instead of waiting.

A watchlist edit is saved locally first and synced with a plain PUT. Quotes are fetched as snapshots on demand, with deltas streaming in only while the screen is visible.

7. Lifecycle, alerts and accessibility

Backgrounding. On the way to the background, close the socket and clear subscriptions. On return, reconnect, re-subscribe, and take snapshots; do not try to replay missed ticks.

Price alerts. The server evaluates alert rules against the feed, so alerts fire when the app is closed. When one triggers, the server sends a push. Treat the push as a hint plus a short text ("AAPL crossed 190.00"); tapping opens the symbol, which loads a fresh snapshot. APNs limits payloads to 4 KB for most notifications, so send identifiers, not data.

Creating the alert is a POST. If it fails, retry with the same clientId when the cause is transient (an I/O error, 408, 429 honouring Retry-After when present, or 5xx). Treat other 4xx as permanent. The push SDK case study covers the alert delivery path in more depth.

Accessibility. Do not announce ticks. Android's accessibility guidance says live regions shouldn't be used on content that updates frequently, such as countdown timers, so as not to overwhelm users with feedback.

  • Leave the price as plain readable text.
  • Use a polite live region only for rare state changes such as "Market closed" or "Alert triggered".
  • On iOS, the updatesFrequently trait tells assistive technology to poll for changes instead of expecting notifications.
  • Show movement with a sign or arrow, not color alone.

9. Doing it on iOS (Swift)

The design is the same. Only the primitives change.

What is genuinely different:

  • Conflation is an explicit buffering choice. AsyncStream buffers without limit by default. A fast feed with a slow consumer then grows memory. Choose .bufferingNewest(1): when the buffer is full, the oldest element is discarded, so the consumer sees the latest state.
  • Apple documents no reconnect behavior for URLSessionWebSocketTask. Treat a failed receive as the end of the task, then rebuild it and resubscribe yourself. It supports ping (sendPing) for liveness checks and maximumMessageSize as a safety limit. Apple's docs describe the receive API as returning a message once all of its frames are available.
  • Backgrounding is driven by scenePhase. Close the socket with cancel(with:reason:) when the phase leaves .active; .background means the scene is not visible.
  • Money. Decimal is a base-10 type. Initialize it from a string, not a Double, or you import the binary error you were avoiding. That is also why the wire format uses strings: JSONDecoder reads a JSON number through a Double. I have not verified either point against Apple's docs. If you use Decimal(string:), pass Locale(identifier: "en_US_POSIX"), since some overloads are locale-sensitive (also unverified).
// Sketch: sequence-checked book exposed as a conflated stream.
// AsyncStream.makeStream is listed on Apple's page for iOS 13+ (back-deployed before iOS 17).
struct Quote: Sendable { let symbol: String; var price: Decimal; var seq: Int; var ts: Date }

actor QuoteBook {
    let updates: AsyncStream<[String: Quote]>
    private let out: AsyncStream<[String: Quote]>.Continuation
    private var book: [String: Quote] = [:]
    private var resyncing = Set<String>()   // symbols waiting for a snapshot

    init() {
        let pair = AsyncStream.makeStream(of: [String: Quote].self, bufferingPolicy: .bufferingNewest(1))
        updates = pair.stream
        out = pair.continuation
    }

    func snapshot(_ q: Quote) { resyncing.remove(q.symbol); book[q.symbol] = q; out.yield(book) }

    /// Returns true to request a snapshot: once per gap, or when there is no snapshot yet.
    /// Ticks for a symbol that is waiting for its snapshot are ignored.
    func tick(_ q: Quote) -> Bool {
        if resyncing.contains(q.symbol) { return false }
        let cur = book[q.symbol]
        if let cur, q.seq <= cur.seq { return false }            // duplicate or old
        guard let cur, q.seq == cur.seq + 1 else {               // no snapshot yet, or a gap
            resyncing.insert(q.symbol)
            return true
        }
        book[q.symbol] = q
        out.yield(book)
        return false
    }
}

// Consumer, e.g. in a @MainActor view model. The sleep caps the render rate.
// for await latest in quoteBook.updates { self.quotes = latest; try? await Task.sleep(for: .milliseconds(100)) }

The actor keeps the same resyncing set as the Kotlin version. tick returns true only when the caller should send requestSnapshot for that symbol. That is once per gap. Every later tick of that symbol returns false until snapshot clears it. The same lost-snapshot limit applies.
