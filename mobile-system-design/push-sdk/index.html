Design a push notification SDK (Android and iOS): tokens, payloads and delivery

Build it. The database schema, API, code and platform limits for a push notification SDK are on a separate page: Build it: a push notification SDK on Android and iOS (20 min read).

How to read this. This page is the 45 minutes, in the order I would spend them. The API, server calls, Swift code and platform limits are in the build guide. The follow-up questions are my reconstruction of challenges that public prep material reports. They are not transcripts of real rounds.

TL;DR. My answer: the SDK (the push code library) keeps one correct record per device. A push is a hint, a signal that something changed. The host app (the app with the SDK) owns the permission prompt, the messaging service and the screens. The push address (the ID for the phone) can change. The SDK links it to a user, uploads it on change, and unlinks it at logout.

1. Scope and constraints (minutes 0 to 4)

In short: Keep registration, logout and sync. Leave the sender backend, rich content and consent for later.

A prompt I would expect: "Design a push notification SDK for our mobile apps." I ask five questions, each with a default:

  • Who uses it? Five of our apps now, outside developers later.
  • Is the user logged in? Yes. A device is linked to a user until logout.
  • Do other SDKs use push? Yes.
  • Who shows the notification? The host app.
  • Who owns the backend? We do. I design the device registry, not the sender.

The phone adds four risks.

Your decision. The scope grows to iOS and an inbox list. Do you build one design with two thin platform layers, or two separate SDKs?

First idea, and why it fails. Two SDKs, because the platforms look different. After a month, they handle logout in different ways. The server then supports two contracts, and each bug is fixed twice.

What I would say. I reject two SDKs. I use one record and one server contract. Each platform layer only reads the push address and asks permission.

Say this. "One design, two thin layers. The device record and the server calls are the same on both platforms. I skip the sender and the inbox screen. Tell me if you want them earlier."

The follow-up question I expect:

"A campaign hits two million devices in one minute."

That is follow-up 1. The other later items return as follow-ups 2, 3, 4 and 6.

2. Data and contracts (minutes 4 to 14)

In short: The SDK makes its own device ID. The push address is only a value on that record.

Your decision. What identifies one device on the server? The push address, the user ID, or an ID that the SDK makes?

First idea, and why it fails. Use the push address as the key, and register it once. But the address changes after a restore, a reinstall or a new phone. The server then holds two rows and the user gets two pushes. Also, when user A logs out and user B logs in, the row is still linked to A.

What I would say. The SDK makes installId, a random UUID (a unique ID) saved on the device. The server uses it as the key. The push address is only a value on that row. Each upload is an upsert: insert the row, or update it if it exists. I reject the push address as the key. It looks simple, but it has no answer for logout.

The follow-up question I expect:

"The same phone sends two uploads at the same time."

Two uploads can overlap. The upload job records the version it sent, not the latest version.

  • Every local change adds one to localVersion.
  • If a change happens during the call, the versions differ, so the job uploads again.
  • The server keeps the higher version.

The contract has four calls (details in the build guide):

  • Put a device: installId, push address and kind, user, topics.
  • Delete a device.
  • Post events: delivered and opened, each with a messageId.
  • Get the inbox after a cursor (a saved position that the server returns).

These numbers are assumptions, not measurements:

AssumptionArithmeticWhat it decides
10 million installs, 2 launches a day eachUpload on every launch: 20 million calls a day, about 230 a second. Upload every 7 days: 10 million / 7 is about 1.4 million a day, about 17 a secondUpload only on change, or when the last upload is old
Host app: 2 million installs, 5 percent on versions older than the kill switch2,000,000 x 0.05 is 100,000 installsThe server stays compatible first. The switch comes second

For old-style tokens, Firebase advises a refresh about once a month, with no gain above once a week. Its sample cleanup removes rows after 30 days. A 7-day refresh gives a row about 4 chances (30 / 7) before cleanup.

3. Client structure (minutes 14 to 22)

In short: The host app owns the one messaging service. The SDK owns a durable job and a local record.

Your decision. Who owns the messaging service and the long-lived work? The SDK, the host app, or an object that belongs to a screen?

First idea, and why it fails. The SDK declares its own messaging service (the Android part that receives pushes). Or the ViewModel of a screen (the object that holds screen state) starts the upload. The first fails when the host app or another SDK also declares a service. I found no documentation on which one Android calls, so the SDK may never run.

The second fails when the screen closes for good. Android then clears the ViewModel (ViewModel), and the upload is cancelled.

What I would say. The host app declares the one service. It forwards two calls to the SDK: a new push address, and a new message. The SDK answers "handled" or "not handled", so the host can pass the message on.

The work is a unique WorkManager job (the Android tool for work that must survive restarts). Its work persists across restarts and reboots (persistent work). I reject a service declared by the SDK. Some vendors choose it because it needs no setup, but two services can conflict.

The follow-up question I expect:

"Host teams do not want to write the forwarding code."

I offer an optional base class to extend. The default stays explicit.

On iOS, the app has one notification delegate (an object that receives notification events). So the SDK installs a proxy that forwards to the host's delegate. Three rules:

  • Everything is internal until a user needs it.
  • No screen toolkit types in the public API.
  • The SDK never opens a screen. It gives the host a link.

4. Make the hard part work (minutes 22 to 40)

In short: Logout must be safe offline. A push says only "something changed", and a sync fetches the content.

4.1 Logout and the shared phone (minutes 22 to 31)

Your decision. The user logs out, and the phone has no network. What does the SDK do with the device record?

First idea, and why it fails. Delete the push address, call the server, and wait. Offline, the call fails, so the old user stays linked to the phone and the next user gets the old pushes.

What I would say.

Say this. "On logout I clear the user on the device first and add one to the version. Then I queue the unlink call, and I clear the local inbox. Offline logout cannot leak, because the server also unlinks when a new user claims the same installId. And the client ignores any push whose user does not match."

I reject waiting for the server before I clear local state. It can expose the next user until the phone is online again.

The follow-up question I expect:

"Two people share one phone."

This is logout again, with two real people. The same three guards apply.

  • Clear local state first, then queue the unlink.
  • The server relinks when a new user claims the same installId.
  • The client shows nothing for a push that belongs to another user.

4.2 Push is a hint (minutes 31 to 40)

Your decision. The app is closed. How does the message reach the user, and what does the push carry?

First idea, and why it fails. Put the whole message in the push and show it. But a push can be lost. One cause is a force-stop at delivery time (delivery post). Others are more than 100 waiting pushes, or a month offline (receive messages). Doze (the deep-sleep mode of an idle phone) can delay pushes of normal priority (priority).

What I would say.

Say this. "A push carries only a hint: a message ID, a type and an entity ID. The client then asks the inbox for everything after its last cursor. That sync repairs any gap, so a dropped push costs a delay, not a message. I ignore repeats by message ID."

I reject silent push (a push with no visible alert) as the way to get correctness. The host shows the permission prompt. The SDK only reads the permission state at each foreground.

If I am interrupted, I answer first, then return:

Say this. "Yes, the same message twice is normal here. The message ID makes the second copy change nothing, so the user sees one entry. Now back to the push path, where I was."

The follow-up question I expect:

"A user says the push never arrived."

The SDK sees only part of the path. I go through a list, and I say which checks the SDK can make.

  • It can see: permission state, the channel setting, and the time of the last sync.
  • It cannot see: losses inside the push service, force-stop, and phone-maker battery limits.
  • The sender side adds priority, collapse key (which replaces an older waiting message) and time to live. Firebase also warns that "delivered" does not mean "shown".

4.3 Where iOS changes the design

The Swift code is in the build guide.

  • iOS has no WorkManager. The SDK keeps its own outbox (a saved list of work the server has not confirmed) and sends it at launch, at foreground and on a push.
  • A silent push is low priority and not guaranteed. A waiting one is discarded after a force-quit (Apple). So I send a visible alert.
  • Set the notification delegate before launch ends, or the app can miss incoming notifications.

5. Break it, ship it, roll it back (minutes 40 to 45)

In short: Each failure ends in a late push or a clear state, never in a message for the wrong person.

At release:

  • A store can pause a rollout but not recall it. Play says users who have the update keep it (Play help). Apple allows a pause of up to 30 days (Apple) and says nothing about reverting.
  • Old SDK versions can stay in host apps for a long time, because users update slowly. The server accepts every version. I add fields but never reuse them.
  • The host app's kill switch for the SDK is a remote flag. It works only in versions that already contain it, and it cannot fix a crash at startup.
  • A change to the public API or the local schema cannot be flagged. It waits for a major version.

Say this. "I cannot recall a bad SDK build, so the rollback is the host's kill switch plus a fixed build. I would watch registration success and uploads by SDK version. I left out the sender, rich content and consent."

6. Follow-ups that change a constraint

In short: Each follow-up changes one constraint. A strong answer says what breaks.

Practice prompts, not a claim about what any interviewer asks.

  1. A campaign hits two million devices in one minute. Strong: many devices ask the inbox at once, so I add a random delay to the sync and collapse state-only pushes. Weak: "The server will scale."
  2. Add images and reply buttons. Strong: on iOS, an extension (a separate process) fetches the image within its time limit. A reply must reach the backend with the app closed. Weak: "Put the image in the push."
  3. The user reads a message on the phone, and the tablet still shows it. Strong: read state lives in the inbox. Each device has its own installId, and the tablet learns by a hint and a sync. Weak: "Ignore it."
  4. A user withdraws consent, or asks for erasure. Strong: events stop at once, and the delete call removes the device row. Payloads are never logged. Weak: "Delete the push address."
  5. After an SDK release, registration success drops. Strong: I compare success by SDK version. The kill switch cannot fix a startup crash, so I pause the rollout and ship a fixed build. Weak: "Roll back the release."
  6. The platform moves from tokens to installation IDs while three SDK versions are in use. Strong: the record has an address kind, the server routes by kind, and the SDK accepts both. Weak: "Force everyone to update."

7. What changes by level

In short: The levels differ in who raises the problem.

These levels are my own reading of the bar, drawn from vendor and prep material (courses and books), not any company's rubric. The wording is mine.

  • Mid-level: get the address, upload it on change, ask permission in context, open the right screen on tap. I want to hear: "A push is a hint, so I sync after it."
  • Senior: the upsert by installId, safe offline logout, push as a hint with an inbox, a host-owned service. I want to hear: "Logout clears the inbox and unlinks first, because the unlink call can fail offline."
  • Staff: API stability over years, delivery measurement and its blind spots, a tested kill switch. I want to hear: "I revisit this when too many installs run versions older than the kill switch."

As I read it, the interviewer raises the problem at mid level. The candidate raises it at senior level, and adds a rollout plan at staff level.

Common weak answers. Ten minutes on queues and sending, which is backend work. Only the normal case, with no lost pushes. Naming FCM (Firebase Cloud Messaging, the Google push service) without saying what breaks. The push address as the key. No rollout plan. These patterns repeat across prep material. They are not a dataset.

Staff answer: the decision and the rollout

  • Decision: one SDK with a server-controlled kill switch and a registration protocol that keeps working with old versions, not separate integrations in each app.
  • Alternative: each team builds its own FCM and APNs (the Apple push service) integration. Apps then handle addresses in different ways.
  • Revisit trigger: if most traffic comes from versions without the kill switch, I fix server compatibility first.
  • Rollout: sample app, then one host app, then the rest.
  • Guardrail: test the kill switch in a drill. A new version must not lower registration success.

Opinion vs verified: I read the FCM, Android, Apple and store-rollout facts in official pages. The design, the numbers, the drill and the level text are my opinion. The staff mobile loop guide covers the wider decision.
