Design a push notification SDK (Android and iOS): tokens, payloads and delivery

How to read this. This is a library question. Your users are app developers, and your product is a small public API plus a backend contract. Sections 1 to 8 are the platform-neutral design with Kotlin sketches, and the delegate proxy in section 7 is Swift. Section 9 maps the rest to iOS. The token, permission and delivery primitives differ, the registration record does not. Related: the chat app uses push as a hint for message sync, and the offline-first hub has the write-strategy model this page leans on.

TL;DR. Treat the push address (an FCM registration token or Firebase installation ID on Android, an APNs device token on iOS) as a lease the SDK owns end to end: obtain it, bind it to the current user, re-upload it when it changes, and unbind it on logout. My answer is three rules. Pushes are hints, the SDK owns the registration record, and the host owns permission and navigation. Everything else follows from those three, and a tiny public surface keeps it that way, because every method is a compatibility promise.

1. Clarify the requirements (about 5 min)

Good opening questions:

  • First-party apps only, or third-party developers? (Assume five internal apps now, external later.)
  • Are users logged in? (Yes. A device is bound to a user and unbound on logout.)
  • Do other SDKs in the same app use push? (Assume yes.)

Functional: register a device, bind and unbind a user, ask for permission, show notifications, route taps, subscribe to topics, opt out, report delivered and opened events.

ConcernTarget
CorrectnessNever push to a logged-out user; never lose a change to the push address
ReliabilityPush is best-effort; recover missed content through sync
API stabilityNo source or binary breaks inside a major version
PrivacyCollect the minimum; honor opt-out immediately

Out of scope for now: backend fan-out, campaign tooling, in-app message UI.

2. High-level architecture (about 10 min)

The key decision: the SDK is a state machine around one record, the device registration. Every event (new push address, login, logout, permission change) updates that record, and one worker reconciles it with the backend.

The SDK sits beside the app's layers, and the host wraps it in its own repository so ViewModels never call it directly. Inside, TokenRegistry is a repository over a local record (the source of truth) and the backend. Registration changes are saved locally first and a unique job drains them; analytics events go through a plain queue. This follows the architecture recommendations and the data layer guide. The offline-first hub has the model in one table.

3. Public API and data model

// Sketch: the public surface fits on one screen. login and logout are suspend (one-shot writes);
// onRegistered and handleMessage stay plain because FCM callbacks must return quickly.
object PushSdk {
    fun configure(app: Application, config: PushConfig)
    fun onRegistered(installationId: String)            // host service forwards the FID (FCM's new path)
    @Deprecated("FCM deprecated onNewToken; kept as a bridge for hosts not yet on FIDs")
    fun onToken(token: String)
    fun handleMessage(message: RemoteMessage): Boolean  // true if the SDK consumed it
    suspend fun login(userId: String)
    suspend fun logout()                                // unbind first; platform-side deletion is covered in section 4
    fun setOptIn(topic: String, enabled: Boolean)
    suspend fun requestPermission(activity: Activity): PermissionState  // the host picks the moment
    val permissionState: StateFlow<PermissionState>     // GRANTED, DENIED, NOT_ASKED; refreshed on every foreground
    fun setListener(listener: PushListener)             // taps and foreground messages
}

// Sketch: one immutable row per install, kept in the local DB (source of truth).
data class DeviceRegistration(
    val installId: String,       // SDK-generated UUID, stable across address changes. Not the Firebase installation ID.
    val pushAddress: String?,        // FID or registration token on Android, APNs token on iOS
    val addressKind: AddressKind,    // FID, TOKEN or APNS; the backend routes by kind
    val uploadedAt: Long?,           // epoch ms of the last successful upload; null before the first one
    val environment: String?,        // iOS only: "sandbox" or "production"; null on Android
    val userId: String?,         // null when logged out
    val notificationsEnabled: Boolean,
    val topics: Set<String>,     // opt-ins, mirrored from setOptIn
    val localVersion: Long,      // bumped on every local change
    val uploadedVersion: Long,   // equals localVersion when the backend is current
)

The row keeps only what the SDK must remember between launches. sdkVersion, locale and tz are read fresh at upload time, so they are not stored.

installId is the stable key. Push addresses rotate, so the backend upserts by installId and replaces the address. Without it, every rotation creates a duplicate device row and you push twice. It is a UUID the SDK generates and has nothing to do with the Firebase installation ID, which is one possible value of pushAddress.

The SDK uses WorkManager for the upload, so it must not initialize WorkManager or demand a custom worker factory. The host may already configure it, and on-demand initialization removes the default initializer. Workers take their dependencies from the SDK's own internal graph instead of @HiltWorker.

PUT    /v1/devices/{installId}   { platform, pushAddress, addressKind, environment, userId, enabled, topics, sdkVersion, locale, tz }
DELETE /v1/devices/{installId}
POST   /v1/events                [ { messageId, type: delivered|opened, ts } ]
GET    /v1/inbox?since=<cursor>  (the sync path; the cursor is an opaque string the server returns)

The retry rule for these calls is the same one the chat app uses. Network errors, 408, 429 and 5xx are transient, and Retry-After is honored when present. Any other 4xx is permanent, so the SDK stops and reports it.

4. Hard part one: the token lifecycle

A push address is not an identity. It changes under you and can be revoked without notice.

Android (FCM). FCM is moving from registration tokens to Firebase installation IDs (FIDs), and both are supported during the transition. In firebase-messaging 25.1.0 the release notes mark getToken, deleteToken and onNewToken as deprecated, and the client page says the token flow will be removed in a future release. The FID path is an opt-in: set the manifest flag firebase_messaging_installation_id_enabled to true, override FirebaseMessagingService.onRegistered() and send the FID to your server every time it fires. With auto-init disabled you also call FirebaseMessaging.getInstance().register() on startup. The SDK should accept either kind and record which one it holds, which is what addressKind is for. FCM treats a registration unseen for over a month as stale and expires Android registrations after 270 days of inactivity. With FIDs and auto-init the SDK refreshes the registration itself; with legacy tokens you have to re-send periodically, and Firebase suggests monthly. I did not verify the minimum library version for the manifest flag, or whether onNewToken still fires in FID mode, so test both on the version you ship.

iOS (APNs). Apple says to register on every launch and not to cache the token, because it changes after a restore from backup, an install on a new device or an OS reinstall. The token arrives in application(_:didRegisterForRemoteNotificationsWithDeviceToken:). A SwiftUI app needs a UIApplicationDelegateAdaptor to receive that callback (I have not checked this against Apple's page). The backend must hold many tokens per user.

The SDK flow:

  1. At startup, ask the platform for the current push address (on FID, wait for onRegistered).
  2. If it differs from the stored one, or uploadedAt is older than your refresh interval, bump localVersion.
  3. A unique WorkManager job (it has to survive the app being killed; on iOS I drain my own outbox, meaning any durable record of work the server has not acknowledged yet) calls PUT /v1/devices/{installId} while localVersion is ahead of uploadedVersion, then records the version it sent, not the latest, and sets uploadedAt. Retry transient failures as described in section 3.
  4. Provider feedback closes the loop on the server:
ProviderResponseWhat the server does
FCMUNREGISTERED (404)Delete the registration
FCMINVALID_ARGUMENT (400)Delete only when the payload is known to be valid, since a bad payload gives the same error
APNs410 UnregisteredDelete, unless the body timestamp is older than the token's last registration time
APNs400 BadDeviceTokenDelete; also check for a sandbox/production mismatch
APNs429 TooManyRequestsRetry later with a delay; Apple says not to retry BadDeviceToken, Unregistered or PayloadTooLarge

The 410 timestamp rule matters because a fresh re-registration must not be removed by an old failure.

  1. A scheduled server job removes registrations not refreshed within your staleness window. Firebase's sample uses 30 days.

Logout is where most real bugs live. After user A logs out and B logs in, A's content must never reach B. On logout:

  1. Set userId = null and bump the version first; enqueue the unbind immediately.
  2. Clear the local inbox and cached payloads.
  3. Re-read the push address on the next login and upload it with the new userId.

I would like to say "delete the platform token so a stale push cannot arrive", but I could not find a documented FID equivalent of deleteToken: the current client page does not mention deletion. Check the current reference before you promise that. The guarantee I would actually stand behind is the other half: the unbind can fail offline, so the server also unbinds when a new user claims the same installId, and the client drops any push whose userId does not match the current binding.

5. Hard part two: permission and presentation

Android 13 (API 33) added the runtime permission POST_NOTIFICATIONS. If the app targets 13 or higher, it controls when the dialog appears; with lower targets, the dialog appears the first time an activity starts after a channel is created. Android advises waiting until the user has context. The FCM SDK (23.0.6 and later) declares it in the manifest, but the app still requests it at runtime.

iOS shows the prompt on the first requestAuthorization call and never again. Apple advises asking in context, not at first launch. Provisional authorization (.provisional) skips the prompt: notifications arrive quietly in Notification Center only, with Keep and Turn Off buttons, and the status stays .provisional until the user chooses.

SDK rules:

  • Never prompt automatically. requestPermission(activity) is the only call that shows the dialog, so the host picks the moment, ideally after its own pre-prompt. On iOS the same call wraps requestAuthorization.
  • The SDK refreshes permissionState on every foreground; hosts observe the StateFlow and do not poll. Users change it in Settings, so notificationsEnabled must follow, and the backend should stop high-priority sends to devices that cannot show them. FCM may downgrade high-priority messages that do not produce a visible notification.
  • Create Android channels at startup, not inside the message handler. Firebase's client setup page warns that on 12L and lower, notifications that arrive before the first channel is created in the foreground and the user accepts the permission can be lost.

Channels versus categories. Android 8 and later requires every notification to belong to a channel. After creation you cannot change a channel's importance, sound or vibration in code; the user has the final say, and you can change only the name and description. Design channels around user intent (orders, promotions), so disliking one does not disable all. iOS has no per-channel importance. Categories (UNNotificationCategory) define action buttons, and each notification carries an interruption level: passive, active, timeSensitive or critical. Map one SDK importance enum onto both. timeSensitive and critical need a capability or entitlement the host app must hold (I have not checked the current requirements), so map the SDK's top importance to timeSensitive and never expose critical by default.

6. Payload design and app states

Message types. On Android, FCM displays a notification message itself when the app is in the background, while a data message always goes to your code. A mixed message in the background shows in the tray and delivers data through intent extras after a tap. Both types are limited to 4096 bytes (the Firebase console enforces 1000 characters). An SDK should prefer data messages, because it controls the channel, dedupe and tap target. The cost is that your process must get to run.

KnobFCM (Android)APNs (iOS)
Urgencynormal or high; high tries to deliver immediately, even in Dozeapns-priority: 10 immediate, 5 power-aware, 1 low power
Type(n/a)apns-push-type: alert or background; background always uses apns-priority: 5 (10 is an error)
LifetimeTTL 0 to 28 days; TTL 0 discards if not deliverable nowapns-expiration as a Unix time; 0 tries once, no storage
Replacecollapse_key; four distinct keys held per deviceapns-collapse-id, max 64 bytes

Collapse state where only the latest value matters, never items that each matter, like chat. FCM stores at most 100 non-collapsible messages per Android device. When that limit is reached, or the device has been offline for over a month, the app gets onDeletedMessages() and should run a full sync. Use a short TTL on time-bound content.

StateAndroidiOS
ForegroundonMessageReceived gets everything; the SDK decides on a bannerwillPresent chooses the presentation options
BackgroundData message reaches onMessageReceived; notification message goes to the traySystem shows alert pushes; content-available pushes are best effort
Killed by the systemData messages still reach the app if FCM can start it; tap launches the launcher activityAlerts show; a held background push is discarded on force-quit
Force-stopped by the userCommonly reported as no delivery until the user opens the app again (Firebase's Flutter guide says so; I did not find it on a native Android page)Same as above: a background push is discarded

Apple documents background pushes as low priority, not guaranteed and possibly throttled (two or three per hour advised). Hence: push is a hint. Send {messageId, type, entityId} and let the client fetch content from GET /inbox?since=cursor. The cursor sync heals any gap, including the force-stopped case, because the app catches up when it next launches. On iOS, send a visible alert with mutable-content: 1 so a Notification Service Extension can fetch or decrypt within about 30 seconds; if it runs out, the system shows the original content, so make that text acceptable. The extension is not invoked for silent pushes, sound-or-badge-only pushes, or when alerts are disabled.

7. Taps, tracking and coexistence

Routing a tap. Cold and warm starts must reach the same destination. On Android, put a PendingIntent for the destination activity in setContentIntent(). From Android 12 (API 31) a notification tap has to open the activity directly. Sending the tap through a service or receiver (a trampoline) is blocked, so a "tap handler service" will not work. Pass the deep link and messageId as extras and let the activity report the open. On iOS, UNUserNotificationCenterDelegate.didReceive handles the tap, and the delegate must be set before launch finishes, in willFinishLaunchingWithOptions or didFinishLaunchingWithOptions, or you can miss the notification that launched the app. The SDK hands the parsed link to the host through PushListener and never navigates itself.

Tracking with dedupe. Every push carries a messageId. The SDK records delivered when the handler runs and opened on tap, keeps a table of seen IDs, and drops repeats (the same message can arrive by push and by sync). Queue events and batch them, with messageId plus type as the idempotency key. delivered means "reached our handler", not "seen". On iOS the handler is willPresent, which only runs when the app is in the foreground, so the proxy below undercounts alerts shown while the app is in the background. Counting those needs the Notification Service Extension from section 6.

Multi-SDK coexistence. Several libraries each want a FirebaseMessagingService, and you cannot count on yours being the one invoked. So ship no service. The host declares one, calls PushSdk.onRegistered (or the deprecated onToken) and PushSdk.handleMessage, and passes anything the SDK returns false for (it checks a namespaced payload key) to the next library. On iOS the shared resource is the single notification center delegate, so the SDK provides a proxy that forwards to the host's delegate. The same single-owner problem shows up in the analytics SDK page under multiple SDKs, and that page has the kill-switch side of coexistence.

// Sketch: delegate proxy. `next` is the host's delegate. Call install() before launch finishes.
// The center holds its delegate weakly, so the SDK must retain the proxy: hence the singleton.
// @unchecked Sendable: `next` is written once at setup, on the main thread, before any callback.
final class PushDelegateProxy: NSObject, UNUserNotificationCenterDelegate, @unchecked Sendable {
    static let shared = PushDelegateProxy()
    var next: UNUserNotificationCenterDelegate?

    func install(on center: UNUserNotificationCenter = .current()) {
        if center.delegate !== self { next = center.delegate }  // keep a delegate the host set first
        center.delegate = self
    }

    func userNotificationCenter(_ center: UNUserNotificationCenter,
                                willPresent notification: UNNotification,
                                withCompletionHandler completionHandler:
                                    @escaping @Sendable (UNNotificationPresentationOptions) -> Void) {
        PushSdk.shared.recordDelivered(notification.request.content.userInfo)
        if next?.userNotificationCenter?(center, willPresent: notification,
                                         withCompletionHandler: completionHandler) == nil {
            completionHandler([])  // what the system does when a delegate has no willPresent
        }
    }

    func userNotificationCenter(_ center: UNUserNotificationCenter,
                                didReceive response: UNNotificationResponse,
                                withCompletionHandler completionHandler: @escaping @Sendable () -> Void) {
        PushSdk.shared.recordOpened(response.notification.request.content.userInfo)
        if next?.userNotificationCenter?(center, didReceive: response,
                                         withCompletionHandler: completionHandler) == nil {
            completionHandler()
        }
    }
}

configure calls install(), which puts the proxy in place and keeps any delegate the host set earlier in next. A host that assigns center.delegate after that replaces the proxy and the SDK stops seeing taps, so the host sets PushDelegateProxy.shared.next instead. When the host has no willPresent, the proxy completes with [], which is what iOS does with no delegate method, so nothing shows in the foreground. Defaulting to a banner and sound would change host behavior, which a proxy must not do.

Opt-out, topics, throttling, quiet hours. Topic subscriptions are server state keyed by installId, mirrored locally, and changes ride the same reconciliation worker. Opt-out is a version bump the server checks at send time. Frequency caps and quiet hours belong on the server, which sees everything sent to the user; the client can only hold banners during local quiet hours.

8. Failure modes, testing, versioning, privacy

ScenarioHandling
Push address rotates while offlineVersion bump persists; upload retries when the network returns
Logout with no networkLocal binding cleared at once; server unbinds on the next claim of the installId
Push arrives for a logged-out userDrop it when userId mismatches; never render
UNREGISTERED or APNs 410Server deletes the registration; the client re-registers on next launch
Over 100 stored messages, or offline for a month (Android)onDeletedMessages() triggers a full inbox sync
User disables notifications in SettingsForeground check updates notificationsEnabled; server stops high-priority sends
Same message twicemessageId dedupe; one event recorded

Testing. Hide the platform behind thin interfaces (TokenProvider, DeviceApi) and test with fakes rather than mocks, so the registry state machine runs in plain unit tests: token change, login, logout, offline retry. Use TestListenableWorkerBuilder for the worker.

Versioning. Keep internals internal, run binary-compatibility validation in CI, and never rename payload keys, only add. The backend must tolerate old SDK versions for years, because app updates are slow. Send sdkVersion on every upload to see the long tail.

Privacy. Store only installId, push address and its kind, upload time, iOS environment, user id, topics, locale and time zone. Never log payloads. Logout sets userId to null on the server's device row and keeps the row. The row is deleted only on an erasure request, through DELETE /v1/devices/{installId}.

9. How to build a push notification SDK on iOS (Swift)

The Swift delegate proxy is in section 7. This section lists what else differs.

TapPendingIntent to an activitydidReceive on the delegate
Durable retryWorkManagerNone; drain your own outbox on launch, foreground and push

What is genuinely different:

  • The extension is a separate target that the host must add, with its own time limit (about 30 seconds) and tighter memory than the app (Apple publishes no figure, so keep it small). It cannot share live objects with the app, so keep it tiny and share config through an App Group.
  • Silent pushes cannot carry correctness. Use content-available only on top of sync-on-foreground, send it with apns-push-type: background and priority 5, and expect Apple's advised two or three per hour.
  • Tokens are per environment. A sandbox token sent to production fails as BadDeviceToken, so record the environment on upload.

10. What changes by level

The split below is my own reading of the levels, not a published rubric.

  • Mid-level: get the push address, upload on change, ask for permission, deep link on tap, and know push may not arrive.
  • Senior: the registration state machine with idempotent upsert by installId, logout semantics, provider feedback and stale-token cleanup, data versus notification messages, collapse and TTL, trampoline limits, and the host-owned service for coexistence. A senior might say: "Logout clears the inbox and unbinds first, because the unbind call can fail offline."
  • Staff: API stability across years of app versions, delivery observability and its blind spots, cross-sender rate limits on the server, consent, remote kill switches, and how teams extend the SDK without forking it.

Staff answer: the decision and the rollout

Decision: ship a single SDK with a server-controlled kill switch and a registration protocol that never breaks, rather than per-app integrations. Alternative: each team wires FCM and APNs directly, leaving hundreds of app versions with divergent token handling. Revisit trigger: if most traffic comes from versions that predate the kill switch, invest in server-side compatibility before new features.

Version skew: the server must treat every SDK version since the first as live. Add fields, never repurpose them, and have the server tolerate unknown or missing ones.

What to measure: active installs per SDK version, token-registration success, and delivery and tap rates by version, remembering that delivery is not directly observable. FCM keeps an undelivered message up to four weeks by default, so a late tap is not necessarily a bug. Guardrail: the kill switch must be exercised in a drill before it is needed, and a new SDK version must not lower registration success against the previous one.

Rollback on mobile: the kill switch stops sending or processing for clients that already fetched the config. It cannot fix a crash at startup, and a store rollout can be paused but not undone on devices that installed it, so the fix is a new build. Google's staged rollout help says users who already have the version stay on it; Apple's phased release page lets you pause for up to 30 days. The native vs cross-platform guide covers the build-versus-share side of this decision.

Opinion vs verified: FCM lifespan was read from Firebase docs, and the Play and App Store rollout facts from the two help pages linked above; the design above and the drill requirement are my opinion. See the staff mobile loop guide.

11. Follow-up questions worth practising

I picked these because they are where I would expect the design to be pushed. They are not a list of what any company asks.

  1. A user says the push never arrived. Walk through it: valid address, permission, channel, Doze, collapse key, TTL, force-stop, and OEM battery managers. Say which of these the SDK can observe and which it cannot.
  2. Two users share one phone. What stops user A seeing user B's notification? (Unbind and clear the inbox on logout, server rebinding by installId, client drop on userId mismatch.)
  3. How do you add reply actions? (Categories on iOS, RemoteInput on Android; the action must reach the backend while the app is not running.)
  4. How do you measure delivery? (Sent, handled, displayed, opened; say which gaps are unobservable.)
  5. How do you roll out a new payload format? (Additive keys, capability flags on upload, server picks the format per sdkVersion.)
  6. How would you test against real FCM and APNs? (Fakes for unit tests, then a staging project per platform and a device farm run for the pieces that only exist on a phone.)
