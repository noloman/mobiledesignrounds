Draft v1. Companion to the chat app interview case.

This is the implementation material behind the chat app interview case: schema, REST, events, the send worker, the receive path, history, receipts, platform limits and the iOS version. None of it belongs in the 45 minutes; I draw it only if asked. The snippets use Room 2.x (androidx.room); the official Room guide now shows Room 3 (androidx.room3, KSP only, SQLiteDriver required), and the architecture is the same either way.

1. Local schema (Room)

@Entity(
    tableName = "messages",
    indices = [
        Index(value = ["clientId"], unique = true),
        Index(value = ["conversationId", "seq"]),
    ],
)
data class MessageEntity(
    @PrimaryKey(autoGenerate = true) val localId: Long = 0,
    val clientId: String,          // UUID generated on device; the idempotency key
    val serverId: String? = null,  // null until acked
    val conversationId: String,
    val senderId: String,
    val body: String,
    val seq: Long? = null,         // per-conversation sequence assigned by server; gaps are allowed
    val createdAt: Long,           // device clock; used only for ordering pending messages
    val status: Status,
) {
    enum class Status { PENDING, SENT, DELIVERED, READ, FAILED }
}
  • clientId is the whole dedupe story. The same message may arrive via WebSocket, FCM-triggered sync, and the REST response to our own send. The unique index stops a second row from being inserted, and the DAO below turns the collision into an update of the first row, so all three collapse into one.
  • seq comes from the server and gives a total order within a conversation. It does not have to be contiguous; a gap is healed by a cursor sync, not treated as an error (the live ticker uses a stricter, gap-detecting seq). Never order by device timestamps alone; clocks drift.
  • I do not use Room's @Upsert for this. It only falls back to an update when the primary key (localId) matches, and an incoming copy has no localId, so a clientId collision would update nothing and the ack data would be lost. I insert with IGNORE and, if that was ignored, update by clientId:
@Dao interface MsgDao {
    @Insert(onConflict = OnConflictStrategy.IGNORE) suspend fun insertIgnore(m: MessageEntity): Long
    // the server copy fills in serverId and seq; a PENDING row becomes the server's status, any later status stays
    @Query("""UPDATE messages SET serverId = :serverId, seq = :seq,
        status = CASE WHEN status = 'PENDING' THEN :status ELSE status END
        WHERE clientId = :clientId""")
    suspend fun applyServerCopy(clientId: String, serverId: String, seq: Long, status: String)

    @Transaction suspend fun upsertByClientId(m: MessageEntity) {
        if (insertIgnore(m) == -1L) applyServerCopy(m.clientId, m.serverId!!, m.seq!!, m.status.name)
    }
}
  • The sync cursor in this design is simply the last seq the device has seen. I call it after_seq here; other cases use an opaque cursor for the same idea.

2. REST

POST /v1/conversations/{id}/messages      body: { clientId, body }
     → 200 { serverId, seq, createdAt }   (idempotent on clientId)
GET  /v1/conversations/{id}/messages?after_seq=123&limit=50
GET  /v1/sync?since=<cursor>              (conversation list changes; used on cold start)

3. WebSocket events

server → client:  message.new, message.status, conversation.updated
client → server:  ack(seq), typing   (send itself goes via REST/Worker for retry guarantees)

ack(seq) tells the server how far this device has read, so it can stop holding older events for it.

I send through REST plus WorkManager rather than the socket, on purpose: the Worker gives you retries, constraints and survival across process death for free.

4. The send worker

I write to the local database first and send later, so for a moment two versions of the truth exist. The server's seq settles which message comes first, not a last-write-wins race. The send has to survive the app being killed, so it runs in WorkManager, not in viewModelScope.

  1. User taps send. The ViewModel calls repository.send(...), which inserts a row with status = PENDING and a fresh clientId, in one Room transaction. The UI shows it immediately because it observes Room.
  2. The repository enqueues a unique SendMessageWorker per message (or per conversation, to preserve order).
  3. The worker calls repository.sendPending(clientId), which reads the pending row and calls POST /messages.
  4. On success, update the row with serverId, seq, status = SENT.
  5. On a transient failure (IOException, 5xx), return Result.retry(); WorkManager applies backoff. After 8 attempts the worker gives up and marks the row FAILED, so one message that always gets a 5xx cannot hold up the rest of the conversation's chain.
  6. On a permanent failure, mark FAILED and show "Tap to retry". My rule across these cases: IOException, 408, 429 and 5xx are transient; any other 4xx is permanent. Honouring Retry-After would mean re-enqueuing with an initial delay, because the backoff policy is fixed; the worker below does not do that.

The define-work page describes no jitter in WorkManager's backoff, so I assume none. That is fine for one device's sends; jitter matters for socket reconnects (section 5), where millions of clients can retry at once.

With the 10 s base the delays double (10, 20, 40 ... 1,280 s). The worker above checks runAttemptCount >= 8 at the start of a run, so there are eight sends over about 21 minutes, and the ninth run, which marks the row FAILED, starts about 42 minutes after the first failure. The androidx source caps backoff at 5 hours (the define-work page does not state a cap), so the cap never applies here. These are my arithmetic on the library's documented defaults and its source, not measurements; backoff delays are inexact by several seconds.

@HiltWorker
class SendMessageWorker @AssistedInject constructor(
    @Assisted ctx: Context, @Assisted params: WorkerParameters,
    private val repository: ChatRepository,   // workers go through the repository, never the DAO or API
) : CoroutineWorker(ctx, params) {

    override suspend fun doWork(): Result {
        val id = inputData.getString("clientId") ?: return Result.failure()
        if (runAttemptCount >= 8) { repository.markFailed(id); return Result.success() }   // stop retrying; the row shows "Tap to retry"
        return when (repository.sendPending(id)) {
            SendOutcome.Done, SendOutcome.NothingToSend -> Result.success()
            SendOutcome.Retry -> Result.retry()   // IOException, 5xx, 429
            // permanent 4xx: the row is already FAILED in Room, so end this work as success().
            // (With APPEND a failed parent would cancel later sends; APPEND_OR_REPLACE avoids that, and success() keeps WorkInfo clean.)
            SendOutcome.PermanentFailure -> Result.success()
        }
    }
}

// enqueue
WorkManager.getInstance(ctx).enqueueUniqueWork(
    "send-${conversationId}",            // one chain per conversation keeps order
    ExistingWorkPolicy.APPEND_OR_REPLACE,
    OneTimeWorkRequestBuilder<SendMessageWorker>()
        .setInputData(workDataOf("clientId" to clientId))
        .setConstraints(
            Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build()
        )
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.SECONDS)   // 10 s is the minimum; the default is 30 s
        .build(),
)

Why this is safe against duplicates: if the request reaches the server but the response is lost, the retry sends the same clientId, and the server returns the original serverId/seq instead of creating a second message. This is idempotency in practice; the same pattern carries the payment in the booking app, and the staff guide walks this exact lost-acknowledgement case at staff depth.

Ordering note: pending messages have no seq yet. Render confirmed messages by seq, then pending ones by createdAt at the bottom. When an ack assigns seq, the row slots into place.

5. The receive path in detail

The socket and FCM only tell the device that something changed; the actual data always comes from a cursor fetch.

Foreground: hold one OkHttp WebSocket while the app is visible (tie it to the process lifecycle with ProcessLifecycleOwner). Each incoming message.new is upserted into Room by clientId. The UI updates on its own.

Background: do not keep the socket open. Doze (the deep-sleep mode of an idle phone) suspends network access and App Standby defers background network activity (Doze and App Standby), so an idle socket stops being useful, and a foreground service just to keep it alive costs battery. In my opinion it also invites Play policy trouble. Instead:

  1. The server sends a high-priority FCM data message containing only a hint (conversationId, maybe the seq), not the full content.
  2. FirebaseMessagingService.onMessageReceived enqueues a SyncWorker as expedited work. Expedited work has a quota, so I set RUN_AS_NON_EXPEDITED_WORK_REQUEST to fall back to ordinary work when the quota runs out. The worker must implement getForegroundInfo() or setExpedited can crash on devices below Android 12 (WorkManager docs). Enqueue it straight from onMessageReceived; FCM's exemption for expedited work after a high-priority message is brief.
  3. The worker calls GET /messages?after_seq=<last seq in Room>, upserts the results, then posts a notification. On a cold start I call /sync first for the conversation list, then after_seq for each open thread.

It is a hint plus a sync for the reasons in the push SDK case, which goes deeper on the push side.

Why not put the message in the push? FCM caps a payload at 4 KB (message types), can collapse or drop queued messages (delivery) and documents no ordering, and a sync-by-cursor is self-healing: if you missed three pushes, one sync still fetches all three. One catch: if high-priority FCM messages repeatedly don't result in a user-visible notification, FCM may downgrade them to normal priority, so post the notification from the worker.

Reconnect: when the socket drops, reconnect with exponential backoff plus jitter (for example 1s, 2s, 4s up to about 30s, each randomized ±50%), and always do a cursor sync (after_seq) on reconnect to fill gaps. Jitter matters: without it, a server restart makes millions of clients reconnect at the same instant.

6. Reading history efficiently

Use Paging 3 with a Room PagingSource, plus a RemoteMediator that fetches older pages from the API when the user scrolls past the cached range. The conversation list is also a Room query, so it renders instantly from cache on cold start and refreshes in the background.

The snippet exposes the Room entity for brevity; in a larger app, map it to a UI model in the repository.

@Query("SELECT * FROM messages WHERE conversationId = :id ORDER BY COALESCE(seq, 9223372036854775807), createdAt")
fun pagingSource(id: String): PagingSource<Int, MessageEntity>

7. Delivery and read receipts

  • Server-to-sender: message.status events (DELIVERED, READ) update the row's status. Statuses only move forward; ignore out-of-order downgrades.
  • Receiver-to-server: batch read receipts (for example, send the highest seq read, not one call per message) and debounce them. If READ arrives before DELIVERED, keep READ; the forward-only rule makes the late DELIVERED a no-op.
  • Groups: store counts or a per-user map server-side; the client mostly needs "delivered to all / read by N".

  • Constrain sync work to a network connection; for large media, add unmetered or battery-not-low constraints.

9. How to build a chat app on iOS (Swift)

The design carries over: local database as the source of truth, an outbox, a client-generated clientId for idempotency, server seq for ordering, and cursor-based sync. The primitives are what move.

ConcernAndroidiOS

What really changes:

  • The outbox is a table you drain yourself. Trigger it on send, on app foreground, on network recovery (NWPathMonitor), and on push. Those triggers overlap, and an actor is re-entered at every await, so a second drain would send every message twice. The sketch keeps one drain running and a flag that makes it do one more pass, so a message saved mid-drain is not left waiting for the next trigger. If the user force-quits the app, nothing runs in the background until the next launch, so pending messages may wait. Say so in the interview: it's a weaker guarantee than WorkManager gives you.
  • Silent pushes are unreliable. Apple documents them as low priority, not guaranteed, and throttled (it advises no more than two or three per hour); a held one is discarded if the app is force-quit. For chat, send a visible alert push with mutable-content: 1, and let a Notification Service Extension fetch or decrypt the message within its time limit (Apple's guide says about 30 seconds; when time is nearly up the expiry callback must hand back whatever it has, and the system shows the original content only if the handler is never called), falling back to generic text. The "push is a hint, sync fills the gap" rule still applies.
  • No socket in the background. Close the WebSocket when the app leaves the foreground; use beginBackgroundTask to finish an in-flight send.
  • Dedupe is the same. A unique clientId constraint makes duplicate inserts collapse (in SwiftData, @Attribute(.unique) upserts on save for primitive-typed properties, per WWDC23 session 10195; adding it to an existing store needs a custom migration stage that deduplicates first, and I would check CloudKit support before relying on it; test on your target OS).
// Sketch: outbox drain on iOS (trigger it from send, foreground, reachability, push)
actor Outbox {
    private var draining = false, rerun = false     // reentrancy guard: triggers overlap
    // `store` is a @ModelActor (or a GRDB/Core Data actor); do not share a ModelContext across isolation domains.
    func drain() async {
        if draining { rerun = true; return }        // a trigger during a drain asks for one more pass
        draining = true
        defer { draining = false }
        repeat {
            rerun = false
            for msg in await store.pending() {      // ordered by createdAt
                do {
                    let ack = try await api.send(msg.conversationId, clientId: msg.clientId, body: msg.body)
                    await store.markSent(msg.clientId, serverId: ack.serverId, seq: ack.seq)
                } catch where error.isTransient {
                    return                          // keep order; retry on the next trigger
                } catch {
                    await store.markFailed(msg.clientId)
                }
            }
        } while rerun
    }
}
