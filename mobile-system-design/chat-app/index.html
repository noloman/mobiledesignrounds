Design a chat app (Android and iOS): outbox, idempotent sends and sync

Build it. The database schema, API, code and platform limits for a chat app are on a separate page: Build it: a chat app on Android and iOS (14 min read).

How to read this. This page is the 45 minutes, in the order I would spend them. Schema, API, code and platform tables are in the build guide. The follow-up questions below are my reconstruction of the challenges that public prep material reports: offline, retries, old data, battery, rollout. They are not transcripts of real rounds.

TL;DR. Room (Android's on-device database) is the source of truth, the one copy the app trusts. The screen only reads it. A send is a PENDING row that WorkManager (Android's scheduler for work that survives restarts) delivers. Messages come by WebSocket (a two-way open connection) on screen, and as an FCM (Google's push service) hint when it is closed. A message may arrive twice. A client-generated ID makes that harmless.

1. Scope and constraints (minutes 0 to 4)

In short: Keep groups, delay images and a second phone, and say what the phone does to the design.

A prompt I would expect: "Design the chat feature for our app. People message each other, one to one and in small groups." I ask five questions and give a default for each:

  • How much is the phone? The app and its API contract.
  • Groups? Yes, up to about 200 members.
  • Offline? Yes, read and write with no signal.
  • Receipts? Sent, delivered, read.
  • Media and devices? Text only, one phone each.

Your decision. The interviewer says: "Groups, images and two devices too." Which of the three do you keep?

First idea, and why it fails. Say yes to all three. The time runs out before I draw the offline send path.

What I would say. Groups stay, because they mostly change receipts. Images and a second phone each change the whole send path, so they wait.

Say this. "Groups are in. Images, a second phone and encryption each change the send path, so they wait. Tell me if you want one earlier."

The follow-up question I expect: "Everyone sends photos."

They return as follow-up 2.

2. Data and contracts (minutes 4 to 14)

In short: The local database is the source of truth. Each message gets an ID made on the device. The server sets the order.

Your decision. Where does a message live? In memory behind the ViewModel (the class that holds a screen's state), on the server with a disk cache, or in a local database that the screen watches?

First idea, and why it fails. Hold messages in memory and fetch them when the screen opens. When Android stops the process, the list and every unsent message are lost. A disk cache beside a server list is better, but they can disagree.

What I would say. The screen reads the local database and nothing else. The network writes into it, and the screen follows. It gives offline reading and instant sends.

The follow-up question I expect: "The same message can arrive by socket, by a push-triggered sync, and in the response to your own send. How many rows?"

One. Each message gets a clientId, a UUID (a random unique ID) made on the device. A unique index (a database rule that refuses a repeated value) blocks a second row. The code then does an upsert: insert the row, or update it if it exists. The schema and code are in the build guide.

  • The order comes from seq, a sequence number that the server assigns in each conversation. Device clocks never set the order.
  • A pending message stays at the bottom until its ack (short for acknowledgement, the server's confirmation) brings a seq.

The contract:

  • Send: clientId and body in, serverId and seq out. The same clientId always gets the same answer.
  • Catch up: everything in a conversation after a given seq.
  • Cold start (the app starts fresh): which conversations changed since a cursor (a saved position).
  • Socket: the server pushes messages and status changes. The client sends ack(seq) and typing.

3. Client structure (minutes 14 to 22)

In short: Sending and the socket sit below the screen: an outbox for sends, and one engine for the socket.

Your decision. Who owns sending and the socket? The chat screen's ViewModel, a service, or a component that lives as long as the app?

First idea, and why it fails. The ViewModel. It holds the screen state, so it opens the socket and starts each send in viewModelScope. But Android clears a ViewModel when its screen leaves the back stack, the list of opened screens (ViewModel). The socket and any send in progress are lost, and a stopped process leaves nothing. SavedStateHandle survives process death, but holds only small UI state (saved state).

What I would say. Ownership goes below the screen:

  • The socket belongs to a sync engine, a class that lives as long as the app. It keeps the socket open while the app is on screen.
  • Sends belong to the outbox, a table of waiting messages. It holds PENDING rows in Room, and a WorkManager worker (a class that does one task) sends them. Its queued work is documented to survive app restarts (persistent work).
  • The ViewModel only asks the repository (the class that reads and writes data) to insert a row.

I reject a service. On Android 12 and later, an app in the background mostly cannot start a foreground service (restrictions).

The follow-up question I expect: "Two screens both want the socket. Who closes it?"

The sync engine closes it, not a screen, when the app is no longer on screen. Screens share one socket.

The screen and ViewModel are the UI layer, and ChatRepository is the data layer. I skip a domain layer until two ViewModels share logic (recommendations). Three rules:

  • The UI never talks to the network. It observes Room.
  • Socket and push handlers write into Room through the sync engine, never to the screen.
  • Workers call ChatRepository, never the DAO (the class with the database queries) or the API.

4. Make the hard part work (minutes 22 to 40)

In short: A send is a saved row first. A receive is a push hint that starts a sync.

4.1 The send path (minutes 22 to 33)

Your decision. The user taps send. What happens next, and when does the bubble appear?

First idea, and why it fails. Start a coroutine (a Kotlin background task) from the ViewModel, call the API, and add the bubble when the server answers. Three things fail:

  • The bubble waits for a round trip.
  • If the user leaves the screen or the process stops, the call is cancelled.
  • If the response is lost, a plain retry sends the message twice.

What I would say.

Say this. "A send is a row before it is a request. In one transaction, I insert the row as PENDING with a new clientId, so the bubble shows. A WorkManager worker sends it, one chain per conversation to keep order. Success fills in serverId and seq. Temporary failures retry with backoff, a longer wait after each failure. A permanent failure marks the row FAILED: tap to retry."

Those pending rows are my outbox: work that the server has not acknowledged. A transaction means all steps succeed or none do. I send through REST and WorkManager, not the socket, because they give retries and survive process death. The code is in the build guide.

The follow-up question I expect: "The request reached the server, but the response never came back."

The retry carries the same clientId, and the server returns the original serverId and seq. This is idempotency: doing it twice has the same result as doing it once.

The follow-up question I expect: "What do you retry?"

  • Retried: IOException, 408, 429 and 5xx. Other 4xx errors are permanent.
  • WorkManager defaults to exponential backoff (the wait doubles) from 30 s. I set 10 s, its minimum (define work).

The follow-up question I expect: "And a message that always gets a 500?"

After eight attempts, the row becomes FAILED. It then cannot block the chain of that conversation.

4.2 The receive path (minutes 33 to 40)

Your decision. The app is in the background and a message arrives. How does the phone find out?

First idea, and why it fails. Keep the socket open in a foreground service, or poll. Both fail:

  • Doze (the deep-sleep mode of an idle phone) stops network access, so a background socket is useless.
  • A foreground service kept only for chat costs battery. In my opinion, it also risks a Play policy problem.
  • Polling wastes the radio.

What I would say.

Say this. "While the app is on screen, I hold one WebSocket and upsert each event by clientId. In the background there is no socket. The server sends a high-priority push with only a hint: the conversation, and maybe the seq. The hint starts a sync worker. It fetches everything after my last seq, writes it to Room, then shows the notification. Three missed pushes need only one sync."

The follow-up question I expect: "Why not put the message in the push?"

A hint says only that something changed. A sync by cursor repairs itself, and a payload cannot.

  • FCM limits a payload to 4 KB (limit).
  • FCM can merge or drop queued messages (delivery).

The follow-up question I expect: "And when the socket drops?"

I reconnect with exponential backoff plus jitter (a random change in each delay). For example, wait 1 s, 2 s, 4 s, up to about 30 s, and randomize each wait. Then I run a cursor sync to fill the gap.

  • Without jitter, a server restart brings every client back at once.

If I am cut off, I answer first. Then I say where I was:

Say this. "Yes, a duplicate sync is harmless. Every write is an upsert by clientId, so the second copy changes nothing. I was in the middle of the receive path. I will finish it, and we can return to this."

4.3 Where iOS changes the design

The design is the same, but the guarantees are weaker, and I say so. The Swift outbox is in the build guide.

  • I send the outbox myself, because iOS has no WorkManager equivalent. After a force-quit, nothing runs until the next launch, so pending messages may wait. I say so.
  • Silent pushes (pushes with no visible alert) are low priority, not guaranteed, limited in number, and discarded after a force-quit (Apple). For chat, I send a visible push and let a notification extension (code iOS runs before a push shows) fetch the message.
  • There is no socket in the background. I close it when the app leaves the screen. I also ask the system for a little time to finish a send.

5. Break it, ship it, roll it back (minutes 40 to 45)

In short: Each failure ends in a delivered message, a clear error, or a late notification, never a lost message.

Releases:

  • A Play staged rollout (a release to a growing share of users) can be halted. Users who have the build keep it (Play Console).
  • An App Store phased release can be paused for up to 30 days (Apple). The page does not say anything about reverting installed copies.
  • Old versions stay installed for months, so the server keeps accepting the old request shape.
  • The new send path ships behind a remote flag (a setting the server can change). It is my kill switch, the only rollback that reaches installed apps.
  • A schema migration (a database layout change) cannot be flagged off. It ships one release before the code that needs it.

Say this. "I cannot recall a bad build, so the rollback is the flag plus a fixed build. I would watch tap-to-ack time, failed sends, duplicate rows and reconnects. I left out encryption, media and search."

6. Follow-ups that change a constraint

In short: Each follow-up changes one constraint. A strong answer says what breaks.

Practice prompts, not a claim about what any interviewer asks.

  1. Sixty messages queued offline, then signal returns. Strong: the bubbles stay in order (pending rows sort by creation time). The chain sends one by one (about 18 s of network time). A 429 means slow down. Weak: "WorkManager handles it."
  2. Add photos and video. Strong: the message row stays small. The file is a separate resumable upload, as in photo and file sync. The message follows once it has a server reference. Weak: bytes in the send request.
  3. A second phone. Strong: each device has its own cursor. The server decides the order. The new phone first loads past history. Unread counts come from a read cursor on the server. Weak: copying the database file between phones.
  4. End-to-end encryption. Strong: each device has its own keys. Name what breaks: search on the server and push previews written by the server. My push is already only a hint. Weak: "just encrypt the body."
  5. A send-path bug is live for some users. Strong: switch the flag to the old path, pause the staged release, read the failed-send and duplicate-row rates, and ship a fix. Weak: "roll back the release."
  6. The backend wants to change the acknowledgement response. Strong: old versions stay in use for months, so the server answers in both shapes. Any migration ships one release earlier. Weak: assuming that everyone updates.

7. What changes by level

In short: As I read it, the levels differ in who raises the problem: the interviewer, the candidate, or the candidate with a rollout plan.

These levels are my own reading of the bar, drawn from vendor and prep material (courses and books), not any company's rubric. The wording below is mine.

  • Mid-level: Room as the source of truth, a send flow with retry, basic offline handling. I want to hear: "A sent message is a row before it is a request."
  • Senior: idempotency via clientId, ordering by the server's seq, FCM as a hint, backoff with jitter, and Doze raised without a question. I want to hear: "If the response is lost, the retry carries the same clientId, so the server returns the original seq."
  • Staff: multi-device sync, what encryption does to sync and search, delivery-time metrics, rollout behind flags, and a module plan (staff guide). I want to hear: "Here is what I would watch, and here is the flag that undoes it."

Common weak answers. These repeat across public prep material. They are not a dataset.

  • Ten minutes on load balancers for a phone question.
  • Only the normal case, with no failure behavior.
  • Naming Room or WorkManager without saying what breaks otherwise.
  • The UI calling the network directly.
  • Writes with no client ID, so a retry makes doubles.
  • No kill switch.

Staff answer: the decision and the rollout

  • Decision: split the feature into send, sync and render modules, with one owner each. Keep the contract between them small: clientId, seq, and a status that only moves forward.
  • Alternative: one module that every team edits. It is faster for a quarter. After that, every change crosses teams.
  • Revisit trigger: if two teams keep changing the same module in one release, the boundary is wrong.
  • Rollout: the new send path goes behind the section 5 flag, then a staged release.
  • Guardrail: send success must not drop against the previous version.

Opinion vs verified: I read the WorkManager, FCM, APNs (Apple's push service) and store-rollout facts in official docs. The module split, metrics, rollback plan, numbers and level text are my opinion. The native vs cross-platform guide covers shared code versus modules.
