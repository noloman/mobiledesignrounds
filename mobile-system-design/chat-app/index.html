How to read this. This page is the 45 minutes, in the order I would spend them. Schema, API, code and platform tables are in the build guide. The pushes below are my reconstruction of the kinds of challenges public prep material reports (offline, retries, stale data, battery, rollout), not transcripts of real rounds.

TL;DR. My answer: Room is the single source of truth and the UI only reads from it. A send is a PENDING row that WorkManager delivers later. Receives arrive over a WebSocket in the foreground and as an FCM hint in the background, and a client-generated ID collapses duplicates. I assume a message can arrive twice and make that harmless.

1. Scope and constraints (minutes 0 to 4)

A prompt I would expect: "Design the chat feature for our app. People message each other, one to one and in small groups." I ask five things and give my default:

  • How much is the phone? The app and its API contract.
  • Groups? Yes, up to about 200 members.
  • Offline? Yes, read and compose with no signal.
  • Receipts? Sent, delivered, read.
  • Media and devices? Text only, one phone each.

Your call. The scope push I would expect: "Groups, images and two devices too." Which do you keep?

First instinct, and why it breaks. Say yes to all three. The time runs out before I draw the offline send path.

What I'd say. Groups stay, because they mostly change receipts. I reject images and a second phone for now: each rewrites the send path.

Say it. "Groups are in. Images, a second phone and encryption each rewrite the send, so I'm parking them. Tell me if you want one earlier and I'll move it up."

The push I would expect: "Everyone sends photos." Parked, and it returns as follow-up 2.

2. Data and contracts (minutes 4 to 14)

Your call. Where does a message live: in memory behind the ViewModel, on the server with a disk cache, or in a local database the screen observes?

First instinct, and why it breaks. Hold messages in memory and fetch on open. When Android kills the process, the list and every unsent message vanish. A disk cache beside a server list is better, but the two can disagree.

What I'd say. The UI reads the local database and nothing else. The network writes into it and the screen follows. That buys offline reading and instant sends.

The push I would expect: "The same message can arrive by socket, by a push-triggered sync, and in the response to your own send. How many rows?" One. Each message gets a clientId, a UUID made on the device, and a unique index refuses a second row. Order comes from seq, a per-conversation number the server assigns, never from device clocks; a pending message sits at the bottom until its ack brings one. The schema and the insert-then-update code are in the build guide.

The contract fits in four lines on the board:

  • Send: clientId and body in, serverId and seq out. The same clientId always gets the same answer.
  • Catch up: everything in a conversation after a given seq.
  • Cold start: which conversations changed since a cursor.
  • Socket: the server pushes messages and status changes. The client sends ack(seq) and typing.

3. Client structure (minutes 14 to 22)

Your call. Who owns sending and the socket: the chat screen's ViewModel, a service, or a component that lives as long as the app?

First instinct, and why it breaks. The ViewModel. It holds the screen state, so it opens the socket and launches each send in viewModelScope. But a ViewModel is cleared when its screen leaves the back stack (ViewModel), taking the socket and any in-flight send with it, and a killed process leaves nothing. SavedStateHandle survives process death but holds only small UI state (saved state).

What I'd say. Ownership goes below the screen. The socket belongs to an app-scoped sync engine, open while the app is visible. Sends belong to the outbox: PENDING rows in Room that WorkManager delivers, since its queued work is documented to survive app restarts (persistent work). The ViewModel only asks the repository to insert a row. I reject a service: on Android 12 and later an app in the background mostly cannot start a foreground service (restrictions).

The push I would expect: "Two screens both want the socket. Who closes it?" The sync engine, not a screen, closes it when the app leaves the foreground, so screens share one socket and none leaks it.

In Android's terms, screen and ViewModel are the UI layer and ChatRepository is the data layer. I skip a domain layer until two ViewModels share logic (recommendations). Three rules:

  • The UI never talks to the network. It observes Room.
  • Socket and push handlers write into Room through the sync engine, never to the screen.
  • Workers call ChatRepository, never the DAO or the API.

4. Make the hard part work (minutes 22 to 40)

Two deep dives, both forced by the table in section 1.

4.1 The send path (minutes 22 to 33)

Your call. The user taps send. What happens next, and when does the bubble appear?

First instinct, and why it breaks. Launch a coroutine from the ViewModel, call the API, add the bubble when the server answers. The bubble waits a round trip, leaving the screen or losing the process cancels the call, and a lost response makes a naive retry send twice.

What I'd say.

Say it. "A send is a row before it is a request. I insert it as PENDING with a fresh clientId in one transaction, so the bubble shows at once. A WorkManager job, one chain per conversation to keep order, sends it with that clientId. Success fills in the server ID and seq. Transient failures retry with backoff; a permanent one marks the row FAILED, and the bubble says tap to retry."

That pending row is my outbox, a durable record of work the server has not acknowledged. I send through REST and WorkManager, not the socket, for retries and survival across process death. The worker code is in the build guide.

The push I would expect: "The request reached the server, but the response never came back." The retry carries the same clientId, and the server returns the original serverId and seq.

"What do you retry?" IOException, 408, 429 and 5xx; any other 4xx is permanent. WorkManager defaults to exponential backoff from 30 s; I set 10 s, its minimum (define work). "And a message that always gets a 500?" After eight attempts the row becomes FAILED, so it cannot block that conversation's chain.

4.2 The receive path (minutes 33 to 40)

Your call. The app is in the background and a message arrives. How does the phone find out?

First instinct, and why it breaks. Keep the socket open in a foreground service, or poll. Doze (the deep-sleep mode of an idle phone) suspends network access, so a background socket goes useless; a foreground service held only for chat costs battery and, in my opinion, invites Play policy trouble; polling wastes the radio.

What I'd say.

Say it. "In the foreground I hold one WebSocket and upsert every event by clientId. In the background there is no socket. The server sends a high-priority push carrying only a hint, the conversation and maybe the seq. The hint starts a sync job that asks for everything after my last seq, writes it to Room, then posts the notification. If I missed three pushes, one sync fetches all three."

The push I would expect: "Why not put the message in the push?" FCM caps a payload at 4 KB (limit) and can collapse or drop queued messages (delivery); a cursor sync heals itself. "And when the socket drops?" Reconnect with exponential backoff plus jitter, say 1 s, 2 s, 4 s up to about 30 s, each randomized, then a cursor sync to fill the gap. Without jitter a server restart brings every client back at once.

If I am cut off mid-answer, I answer first, then say where I was:

Say it. "Yes, a duplicate sync is harmless, because every write upserts by clientId and the second copy changes nothing. I was partway through the receive path, so I'll finish that and you can pull me back."

4.3 Where iOS changes the design

Same architecture, weaker guarantees, and I state them as the cost. The Swift outbox is in the build guide.

  • The outbox is a table I drain myself, since there is no WorkManager equivalent. After a force-quit nothing runs until the next launch, so pending messages may wait. I say so.
  • Silent pushes are low priority, not guaranteed, throttled, and discarded after a force-quit (Apple). For chat I send a visible push and let a notification extension fetch the message.
  • No socket in the background: I close it on leaving the foreground and ask the system for a little time to finish a send.

Release reality:

  • A Play staged rollout can be halted, and users who already have the build keep it (Play Console). An App Store phased release can be paused for up to 30 days (Apple); the page does not mention reverting installed copies.
  • Old versions stay installed for months, so the server keeps accepting the old request shape.
  • The new send path ships behind a remote flag, my kill switch and the only rollback that reaches installed apps.
  • A schema migration cannot be flagged off, so it ships one release ahead of the code that needs it.

Say it. "I can't recall a bad build, so the rollback is the flag plus a fixed build. I'd watch tap-to-ack time, failed sends, duplicate rows and reconnects. Left out: encryption, media, search."

6. Follow-ups that change a constraint

Practice prompts, not a claim about what any interviewer asks. Each changes a constraint, and they get harder.

  1. Sixty messages queued offline, then signal returns. Strong: bubbles stay in order (pending rows sort by creation time), the chain sends one at a time (about 18 s of network time), and a 429 means slow down. Weak: "WorkManager handles it."
  2. Add photos and video. Strong: the message row stays small; the file is a separate resumable upload, as in photo and file sync, and the message follows once it has a server reference. Weak: bytes in the send request.
  3. A second phone. Strong: per-device cursors, the server as ordering authority, a history bootstrap, and unread counts from a server-side read cursor. Weak: syncing the database file.
  4. End-to-end encryption. Strong: per-device keys, and name what breaks: server-side search and server-written push previews. My push is already a hint. Weak: "just encrypt the body."
  5. A send-path bug is live for a slice of users. Strong: flip the flag to the old path, pause the staged release, read failed-send and duplicate-row rates, ship a fix. Weak: "roll back the release."
  6. The backend wants to change the acknowledgement response. Strong: old versions stay in the field for months, so the server answers both shapes and any migration ships a release ahead. Weak: assuming everyone updates.

7. What changes by level

These levels are my own reading of the bar, drawn from vendor and prep material (courses and books), not any company's rubric. The wording below is mine.

  • Mid-level: Room as the source of truth, a send flow with retry, basic offline handling. I want to hear: "A sent message is a row before it is a request."
  • Senior: idempotency via clientId, server seq ordering, FCM as a hint, backoff with jitter, and Doze raised unasked. I want to hear: "If the response is lost, the retry carries the same clientId, so the server returns the original seq."
  • Staff: multi-device sync, what encryption does to sync and search, delivery-latency metrics, rollout behind flags, and a module plan (staff guide). I want to hear: "Here is what I would watch, and here is the flag that undoes it."

As I read it, the levels differ in who raises the problem: the interviewer at mid, the candidate at senior, the candidate with a rollout plan at staff.

Common weak answers. Ten minutes on load balancers for a phone question. A happy path with no failure behavior. Naming Room or WorkManager without saying what breaks otherwise. The UI calling the network directly. Writes with no client ID, so a retry doubles them. No kill switch. These repeat across public prep material; they are not a dataset.

Staff answer: the decision and the rollout

Decision: split the feature into send, sync and render modules with one owner each, and keep the contract between them small: clientId, seq, and a status that only moves forward. Alternative: one module every team edits, faster for a quarter, then every change crosses teams. Revisit trigger: if two teams keep changing the same module in one release, the boundary is wrong.

Rollout: the new send path goes behind the section 5 flag, then a staged release. Guardrail: send success must not drop against the previous version.

Opinion vs verified: the WorkManager, FCM, APNs and store-rollout facts were read from official docs. The module split, metrics, rollback plan, numbers and level text are my opinion; the native vs cross-platform guide covers shared code versus modules.
