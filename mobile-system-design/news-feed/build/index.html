Draft v1. Companion to the news feed interview case.

This is the implementation material behind the news feed interview case: the tables, the REST shape, the mediator and loader code, the like flow in full, freshness, images, failure handling and the iOS differences. None of it belongs in the 45 minutes; I draw it only if asked. The snippets use Room 2.x (androidx.room); the official Room guide now shows Room 3 (androidx.room3, KSP only), whose release notes replace runInTransaction with withWriteTransaction. The architecture is the same either way.

1. Data model and API

The key modeling decision: separate posts from feed order

The feed is server-ranked, so the same post can move between refreshes. If you store order on the post row itself (or sort by createdAt), then an update to one post can reorder the list, and the user sees things jump.

Use two tables:

@Entity(tableName = "posts")
data class PostEntity(
    @PrimaryKey val id: String,
    val authorName: String,
    val body: String,
    val imageUrl: String?,
    val likeCount: Int,
    val likedByMe: Boolean,
    val pendingLike: Boolean? = null,   // local intent not yet confirmed by the server
)

@Entity(tableName = "feed_items", primaryKeys = ["feedId", "postId"])
data class FeedItemEntity(
    val feedId: String,        // "home"
    val postId: String,
    val position: Int,         // the server's rank order, assigned when the page is stored
    val nextCursor: String?,   // cursor that follows this item's page (remote key)
)

Updating a post changes only posts. The list order comes from feed_items.position, which changes only when a page is stored.

REST

GET  /v1/feed?cursor=<opaque>&limit=20     → { items: [...], nextCursor: "..." | null }
GET  /v1/feed/head?since=<newestPostId>    → { newCount: 3 }       (head check for the "New posts" pill, not the paging cursor)
PUT  /v1/posts/{id}/like                   → { likeCount, likedByMe: true }   (idempotent)
DELETE /v1/posts/{id}/like                 → { likeCount, likedByMe: false }  (idempotent)

Two details I'd make sure to say:

  • Opaque cursors, not offsets. If new posts arrive between page fetches, offset paging skips or repeats items. A cursor anchors to a position, so a new post at the top doesn't shift page 2, and the client just stores nextCursor and sends it back. It does not stop a re-rank from repeating posts. For a ranked feed the server has to pin the ranked list behind the cursor, or the client has to dedupe by post ID. I'd ask which one the backend does, and dedupe anyway.
  • PUT and DELETE for likes, not a toggle. A toggle endpoint is unsafe to retry: if the response is lost and the client retries, the like flips back. Setting an explicit state is idempotent, so retries are always safe.

2. Loading pages

Android: use Paging 3 with a RemoteMediator. Room supplies the PagingSource, and the mediator fetches from the network only when the cache runs out. The mediator is data layer code: FeedRepository builds the Pager, and the ViewModel exposes pagingData.cachedIn(viewModelScope) as its screen state. The Paging overview describes the Pager as part of the ViewModel layer, and building it in the repository is a common variant. Snippets use Room rows (FeedRow) directly for brevity; map them to UI models in the repository in a larger app. The library side of this contract is in the pagination library case study.

// Shape adapted from the Paging 3 network-and-database sample (Apache License 2.0),
// https://developer.android.com/topic/libraries/architecture/paging/v3-network-db
@OptIn(ExperimentalPagingApi::class)
class FeedMediator(
    private val db: AppDatabase, private val api: FeedApi,
) : RemoteMediator<Int, FeedRow>() {

    override suspend fun initialize(): InitializeAction =
        if (System.currentTimeMillis() - db.feedDao().lastUpdated() < TimeUnit.MINUTES.toMillis(10))
            InitializeAction.SKIP_INITIAL_REFRESH      // show the cache, no spinner
        else InitializeAction.LAUNCH_INITIAL_REFRESH   // stale: refresh, appends wait for it

    override suspend fun load(type: LoadType, state: PagingState<Int, FeedRow>): MediatorResult {
        val cursor = when (type) {
            LoadType.REFRESH -> null
            LoadType.PREPEND -> return MediatorResult.Success(endOfPaginationReached = true)
            LoadType.APPEND -> db.feedDao().lastCursor("home")
                ?: return MediatorResult.Success(endOfPaginationReached = true)
        }
        return try {
            val page = api.feed(cursor, limit = 20)
            db.withTransaction {
                if (type == LoadType.REFRESH) db.feedDao().clearFeed("home")   // after the network succeeded
                db.postDao().upsertKeepingLocalIntent(page.items)
                db.feedDao().insertItems(page.toFeedItems("home"))
            }
            MediatorResult.Success(endOfPaginationReached = page.nextCursor == null)
        } catch (e: IOException) { MediatorResult.Error(e) }
          catch (e: HttpException) { MediatorResult.Error(e) }
    }
}

What I'd point out:

  • Refresh clears only after the network succeeds, inside one transaction. If the request fails, the user keeps the old feed instead of an empty screen.
  • initialize() is where I decide between showing the cache as is, or showing it and refreshing behind it (stale-while-revalidate). Per the Paging guide, LAUNCH_INITIAL_REFRESH also holds back prepend and append until the refresh succeeds. The guide's own sample uses a one-hour window; my ten minutes is an example.
  • Prefetch distance: PagingConfig(pageSize = 20, prefetchDistance = 10), so the next page starts loading before the user reaches the end. Both numbers are examples, and I'd tune the distance against how fast people scroll.

iOS: Apple has no paging library like Paging 3. You write a small loader that keeps one in-flight task, stores nextCursor, and triggers when the user is within about 5 to 10 rows of the end:

// Sketch: cursor loader (call loadMoreIfNeeded from each row's onAppear, or from UIKit prefetching)
@MainActor final class FeedLoader {
    private var task: Task<Void, Never>?
    func loadMoreIfNeeded(currentIndex: Int, total: Int) {
        guard task == nil, total - currentIndex <= 8, let cursor = store.nextCursor else { return }
        task = Task {
            defer { task = nil }
            if let page = try? await api.feed(cursor: cursor) { await store.append(page) }  // dedupe by post ID
        }
    }
}

3. Optimistic likes

  1. The user taps like. In one transaction, set likedByMe = true, likeCount + 1, and pendingLike = true. The UI updates instantly.
  2. Queue the network write (PUT /like) so it survives the process dying. On Android that is WorkManager, and the worker calls FeedRepository, never the DAO. On iOS it is a small persisted outbox, drained when you enqueue, on foreground, and when the network comes back. By outbox I mean any durable record of work the server hasn't acknowledged yet. Here that is the pendingLike flag plus the queued write. The chat app case study builds the same pattern for messages.
  3. On success, store the server's returned likeCount and clear pendingLike.
  4. On a permanent failure (a 4xx other than 408 and 429), roll back the local change and show a small error.
  5. On a transient failure (an IOException, 408, 429 or 5xx), retry with backoff, and honour Retry-After when the server sends it. Because the call is idempotent, retries are safe.

The subtle bug: a refresh arrives while a like is still pending. If the server snapshot simply overwrites the row, the like visually flips off, then back on when the write lands. The fix is upsertKeepingLocalIntent: when storing server data, any row with pendingLike != null keeps its local likedByMe until the write is confirmed.

Rapid taps: collapse them. Keep one pending intent per post (last state wins) instead of queueing like, unlike, like.

Keep likedByMe and likeCount together while pendingLike is set, or the count flips while the flag holds.

4. Cache invalidation and freshness

SituationBehavior
App opens, cache fresher than the window (10 min here, an example value)Show cache, no refresh
App opens, cache olderShow cache, refresh in the background, swap when done
Pull to refreshFetch page 1 with no cursor, replace the feed in one transaction
New posts existPoll or push a hint, show a "New posts" pill, insert only when tapped
Post edited or deleted elsewhereNext page fetch overwrites that post row; a delete arrives as a "this post is gone" marker (a tombstone), or just disappears on the next refresh

I wouldn't auto-insert at the top while the user is reading. It shifts content under their thumb. Show the pill instead.

5. Images and scroll performance

Images are usually the bottleneck, not the feed logic.

  • Three tiers: memory cache, disk cache (LRU), network. I'd use a proven library (Coil or Glide on Android; Nuke or Kingfisher on iOS, check their current major versions) rather than write one. The image loading case study covers what is inside one.
  • Request the right size. Ask the CDN for a size that matches the view, and downsample on decode. Never decode a full-resolution image to show a thumbnail.
  • Decode off the main thread. A frame is about 16ms at 60Hz (8ms at 120Hz); decoding on the main thread drops frames.
  • Prefetch by position, not by page. Start image loads for rows a couple of screens ahead, and cancel loads for rows the user already scrolled past. On iOS, UICollectionViewDataSourcePrefetching does this (UITableViewDataSourcePrefetching for tables), with cancelPrefetchingForItemsAt for the cancel. Apple says prefetch isn't called for every cell, so cellForItemAt has to cope with an image that isn't there yet. The same idea is in section 4 of the image loading build guide.
  • Respect data. Skip background image prefetch on cellular or in data-saver mode. Prefetching makes scroll feel instant, but it spends the user's data plan.
  • Stable IDs. Key list items by post ID so that appends and refreshes keep scroll position.

6. Failure modes

ScenarioHandling
Page request fails mid-scrollShow a retry row at the end of the list; do not silently stop
Offline on launchShow cached feed with an "Offline" banner; likes queue
Duplicate post across pagesUpsert by post ID; feed order keyed by (feedId, postId)
Refresh while a like is pendingKeep local intent until confirmed (section 3)
Cursor expiresServer returns an error code; client restarts from page 1
Process killed mid-likePending flag and queued write are persisted; they resume on next launch
Huge cacheCap rows (for example, keep the latest few hundred) and evict the oldest

8. More practice prompts

These are the ones I'd rehearse, not a list of what any company asks.

  1. How would you add comments inline? (Nested paged list, same pattern, separate remote keys per post.)
  2. How do you show new posts without disrupting scroll? (Pill, anchor on the first visible item.)
  3. The server re-ranks mid-session. What does the user see? (Keep the loaded list stable, offer the new order behind the pill or on refresh, dedupe by post ID.)
  4. How do you count an impression? (A post is visible long enough, say a set fraction on screen for a set time; batch the events and send them lazily to save battery. The thresholds are product decisions.)
  5. The user opens a post and comes back, or the process is killed. Where do they land? (Restore the position from the last visible post ID and the stored feed order, not from a pixel offset.)
