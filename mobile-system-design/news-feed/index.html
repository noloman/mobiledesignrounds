Design a news feed on Android and iOS: paging, optimistic likes and fresh cache data

How to read this. This page follows the 45 minutes in the order I would spend them. The schema, API and code are in the build guide. In a round I would draw them only if asked. The follow-up questions below are my reconstruction of the kinds of challenges that public prep material reports. They are not transcripts of real rounds.

TL;DR. My answer in four points.

  • The local database is the source of truth (the one copy the app trusts). The screen only reads from it.
  • Pages come by cursor (a saved place in the list, given by the server). The feed order lives in its own table, so an edited post never moves.
  • A like sets a state and shows at once. It stays pending until the server confirms it. The outbox (a saved list of unconfirmed work) sends it later.
  • A refresh must never undo a pending like.

1. Scope and constraints (minutes 0 to 4)

In short: Fix the scope early, leave video and accounts for later, and name what the phone does.

A prompt I would expect: "Design the home feed for a social app." I ask five questions, each with a default:

  • What is in a post? Text, images, author, counts.
  • Who sets the order? The server ranks the posts, so the app cannot sort them.
  • Which actions? Scroll, pull to refresh, like and unlike.
  • Offline? Yes: the last feed, and likes wait in the outbox.
  • New posts live? A pill (a small "New posts" button), never an insert that moves the list.

Your decision. The scope follow-up I expect: "Make new posts appear live, and add comments and video." Which do you keep?

First idea, and why it fails. Say yes to all three.

  • A live insert moves the list while the user reads.
  • Comments need their own paged list.
  • Video needs different loading code than images.

What I would say. The pill stays. It shows a count and inserts nothing until the user taps it. I set comments and video aside and say why. I reject live insertion.

The follow-up question I expect: "Live is the point of a feed."

I keep the pill. Only the insert waits for a tap.

Say this. "The feed, paging and likes are in. Video, a second phone and switching accounts each change the data shape or the write path, so I leave them for later. Tell me if you want one earlier."

2. Data and contracts (minutes 4 to 14)

In short: Posts and order sit in separate tables. Load pages by cursor, never by offset (a page number).

Your decision. The server ranks the feed, and posts change while the user reads. What do you store, and how do you ask for the next page? One option is a rank on each post with offset paging. The other is post data and order apart, with a cursor.

First idea, and why it fails. Put a rank on the post row and ask for page two with an offset. This fails in two ways:

  • The server changes the ranking, so an update to a post changes its position and the user sees it jump.
  • When new posts arrive between two requests, an offset skips some posts and repeats others.

What I would say. The screen reads only the local database. I keep two tables:

  • Posts hold content and like state.
  • Feed items hold only the position in the server's order, written when a page is stored.

Updating a post never changes the order. The app sends the cursor back unread for the next page. I reject sorting by time, because a ranked feed is not in time order.

The follow-up question I expect: "The server changes the ranking between page one and page two. Does the cursor save you?"

Not by itself. A cursor stops a new top post from moving page two. It does not stop a new ranking from repeating a post. The tables are in the build guide.

  • Either the server keeps the ranked list fixed behind the cursor, or the app removes repeats by post ID. I ask which one the backend does, and remove repeats anyway.

The contract in three lines:

  • Page: a cursor and a limit in, items and the next cursor out. No cursor means the first page.
  • Head check: the newest post ID I hold in, a count of newer posts out. It feeds the pill.
  • Like: PUT sets liked, and DELETE sets not liked. Both are safe to retry (doing either twice has the same result as doing it once).

3. Client structure (minutes 14 to 22)

In short: A repository below the screen owns the like and the list.

Your decision. Who owns the like and the paged list? Three choices: the feed screen's ViewModel (the object that holds screen state), a service, or a repository (the code that owns the data) below the screen.

First idea, and why it fails. The ViewModel. It holds the screen state, so it calls the API from viewModelScope and keeps the posts in memory. But a ViewModel lives only as long as its screen. When the user leaves the feed, it is cleared, and that cancels a like still in progress. When the OS stops the process, nothing remains.

Android's docs answer process death with SavedStateHandle for small UI state (saved state).

What I would say. Ownership goes below the screen. A like is a write to Room (Android's database library) plus a WorkManager job (Android's tool for work that outlives the screen).

Scheduled work is documented to persist across app restarts and device reboots (persistent work). The ViewModel only asks the repository to record the like.

I reject a service and an app-wide coroutine scope: both end with the process and keep nothing saved.

The follow-up question I expect: "Two screens show the same post and one likes it. How does the other know?"

Both watch the one posts table, so the row change reaches both.

The screen and ViewModel are the UI layer, and FeedRepository is the data layer. A domain layer is recommended in big apps, for logic that several ViewModels share (recommendations). With one feed I skip it.

The rule: workers call FeedRepository, not the DAO (the database access object) or the API.

4. Solve the hard part (minutes 22 to 40)

In short: Refresh loads new data before it replaces old data. A pending like wins over server data.

4.1 Refresh and paging (minutes 22 to 31)

Your decision. The user pulls down to refresh, or opens the app with an old cache (the saved copy of the feed). What happens to the list on screen until the new page arrives?

First idea, and why it fails. Clear the table, show a spinner, then fetch. If the request then fails, in a tunnel or with a server error (a 5xx code), the user sees an empty screen.

What I would say.

Say this. "Refresh fetches first and replaces second. The old feed stays on screen. When page one arrives, one transaction (all its changes succeed, or none do) clears the old order. It upserts the posts (inserts them, or updates them if they exist) and stores the new order. So nobody sees half a list."

The Paging 3 (Android's paging library) network-and-database sample uses this order. The network call comes first. Then one transaction clears the data on a refresh and inserts the new data (guide).

On open, I show a cache under ten minutes old as it is and refresh an older one in the background. Ten minutes is my example; the guide's sample uses one hour.

The follow-up question I expect: "The cache is two hours old when the app opens. Spinner or old feed?"

The old feed, refreshing in the background.

If a page request fails halfway down, the list ends with a retry row, never a silent stop.

4.2 The pending like (minutes 31 to 40)

Your decision. A refresh arrives while a like still waits for the server. Does the server's copy of the data win, or the user's tap?

First idea, and why it fails. Let the server's copy replace the row. But the server made that copy before the like arrived. The heart turns off, then turns on again when the write finishes.

A toggle endpoint is worse. If the response is lost and the app retries, the like flips back.

What I would say.

Say this. "A like sets a state, never a toggle. In one transaction I set liked, change the count and mark it pending, so the heart fills at once. I add a PUT to the outbox. Server data never replaces a pending row. The local change wins until the server confirms it. Then I store the server's count. Rapid taps merge: one pending change per post, last state wins."

A temporary failure is retried with backoff (wait longer after each failure). A permanent rejection undoes the like. That split is my own classification. A retry is safe because the call sets a state. The merge code and the retry rules are in the build guide.

The follow-up question I expect: "The OS stops the process right after the tap."

The pending flag and the outbox entry are saved, so the like continues on the next launch, as in the chat app.

If I am cut off, I answer first:

Say this. "Yes, a second refresh while the like is pending is harmless, because pending rows keep their local state. I was in the middle of the write path, and I will finish it."

4.3 Where iOS changes the design

The data model and API stay the same. The Swift loader is in the build guide.

  • There is no Paging library, so I write a loader that starts near the end of the list.
  • There is no WorkManager, so I send the outbox myself. I do not count on a background run after a force-quit (the user closes the app), and I say so.
  • Apple says prefetch is not called for every cell, so a row must work when its image is missing.

Release facts:

  • A Play staged rollout (a release to a growing share of users) can be halted. Users who have the update keep it. The remedy is a new release with a fix (Play help).
  • An App Store phased release can be paused for up to 30 days (Apple).
  • Neither page describes removing a build that is already installed.
  • Old versions stay installed, so the server keeps accepting their cursors and requests.
  • The new feed code ships behind a server-controlled flag (a setting the server can change without a new release). That flag is my kill switch (it turns the new code off), the only rollback that reaches installed apps.
  • A database schema change cannot be turned off with a flag, so it ships one release before the code that needs it.

Say this. "I cannot remove a bad build from phones, so the rollback is the flag plus a fixed build. I would watch time to first content, failed likes, and repeated or missing posts. I left out ranking, ads, video and stories."

6. Follow-ups that change a constraint

In short: Six prompts, each with a strong and a weak answer.

They are practice prompts, not a claim about what any interviewer asks.

  1. Someone swipes through 300 posts on a weak connection. - Strong: one page request at a time, a retry row on failure, and prefetch ten rows ahead. No image prefetch on cellular, and a row limit that removes the oldest. - Weak: "load everything faster."
  2. Add video to posts. - Strong: autoplay follows the most visible item and pauses off screen, as in the autoplay section of the video app. - Weak: the video as one more image.
  3. A second phone. - Strong: the server is the authority for the count and the liked state. The pending flag covers only this phone's unconfirmed tap. A refresh brings in the other phone's like. - Weak: copying the database file between phones.
  4. Someone signs out and another signs in. - Strong: the cache and pending likes belong to the old account, so I send or delete them before the switch. - Weak: clearing the feed and forgetting the outbox.
  5. After release, users report repeated posts. - Strong: switch the flag back to the old code, pause the staged release, read the rates of repeated and missing posts, and ship a fix. - Weak: "remove the release."
  6. The backend changes the cursor format. - Strong: the app never reads the cursor. But old cursors are saved in the database, and old apps still send theirs. The server accepts both, or the app deletes stored cursors when it updates. - Weak: assuming that everyone updates.

7. What changes by level

In short: The levels differ in who raises the problem first.

These levels are my own reading of the standard, drawn from vendor and prep material, not any company's rubric.

  • Mid-level: the database as the source of truth, cursor paging, basic image caching. I want to hear: "I will cache the feed in Room."
  • Senior: feed order in its own table, optimistic likes (shown at once) that are safe to repeat, a refresh that clears only after success, and the pending-like merge. I want to hear: "I will keep order in its own table so an edited post never moves."
  • Staff: ranking changes in a session, matching data across devices, flags, metrics, and a plan to share the feed module across screens. I want to hear: "I would ship the shared module behind a flag and watch time to first content before the second screen."

Common weak answers. They come from public prep material, not a dataset.

  • Ten minutes on ranking.
  • Naming Paging 3 without saying why.
  • A like endpoint that toggles.
  • No kill switch.

Staff answer: the decision and the rollout

Decision: one shared feed module, a paging and like layer with a small contract: watch the feed, load more, like, report impressions (a post was seen). Each screen owns its row design.

Alternative: every screen keeps its own feed code. That is faster at first, but the copies later differ.

Revisit trigger: a screen needs rules the contract can only express by checking which screen asks.

Rollout: behind the section 5 flag, then a staged release.

Guardrail: no rise in repeated or missing posts, no drop in like success. Watch time to first content, scroll stutter (dropped frames) and failed likes.

Opinion vs verified: I read the Paging, WorkManager and prefetch facts in the official docs. The ownership model, metrics, rollout order, assumed numbers and level signals are my opinion.
