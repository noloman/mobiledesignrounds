Design a news feed on Android and iOS: paging, optimistic likes, cache freshness

How to read this. This page is the 45 minutes, in the order I would spend them. Schema, API and code are in the build guide; in a round I would draw them only if asked. The pushes below are my reconstruction of the kinds of challenges public prep material reports (offline, retries, stale data, battery, rollout), not transcripts of real rounds.

TL;DR. My answer: the database is the source of truth and the UI only reads from it. Pages come by opaque cursor, and feed order lives in its own table, so an edited post never moves. A like sets a state, shows at once, and is delivered later from a persisted queue. A refresh must never undo a pending like.

1. Scope and constraints (minutes 0 to 4)

A prompt I would expect: "Design the home feed for a social app." I ask five things and give a default:

  • What is in a post? Text, images, author, counts.
  • Who orders it? The server ranks, so the client cannot sort.
  • Which interactions? Scroll, pull to refresh, like and unlike.
  • Offline? Yes: the last feed, and likes queue.
  • New posts live? A pill, never a shifting insert.

Your call. The scope push I would expect: "Make new posts appear live, and add comments and video." Which do you keep?

First instinct, and why it breaks. Say yes to all three. A live insert moves the list under the thumb, so the user loses their place; comments need their own paged list; video rewrites the image pipeline.

What I'd say. The pill stays: it shows a count and inserts nothing until the tap. Comments and video are parked, with the reason said out loud. I reject live insertion.

The push I would expect: "Live is the point of a feed." I keep the pill; the count updates at once and only the insert waits for a tap.

Say it. "The feed, paging and likes are in. Video, a second phone and switching accounts each change the data shape or the write path, so I'm parking them. Say if you want one earlier."

2. Data and contracts (minutes 4 to 14)

Your call. The server ranks the feed and posts change under you. What do you store, and how do you ask for the next page: a rank on each post with offset paging, or post data and order apart with a cursor?

First instinct, and why it breaks. Put a rank on the post row and ask for page two with an offset. The server re-ranks, so an update to one post rewrites its position and the user watches it jump. When posts arrive between two requests, an offset skips some and repeats others.

What I'd say. The UI reads the local database and nothing else. Two tables: posts hold content and like state; feed items hold only the position in the server's order, written when a page is stored. Updating a post never touches order. The next page comes from an opaque cursor the client returns unread. I reject sorting by time, since a ranked feed is not in time order.

The push I would expect: "The server re-ranks between page one and page two. Does the cursor save you?" Not by itself. A cursor stops a new top post from shifting page two, but not a re-rank from repeating a post. Either the server pins the ranked list behind the cursor, or the client dedupes by post ID. I ask which, and dedupe anyway. The tables are in the build guide.

The contract in three lines:

  • Page: a cursor and a limit in, items and the next cursor out. No cursor means the first page.
  • Head check: the newest post ID I hold in, a count of newer posts out. It feeds the pill.
  • Like: PUT sets liked, DELETE sets not liked. Both are safe to retry.

3. Client structure (minutes 14 to 22)

Your call. Who owns the like and the paged list: the feed screen's ViewModel, a service, or a repository below the screen backed by the database?

First instinct, and why it breaks. The ViewModel. It holds the screen state, so it calls the API from viewModelScope and keeps the posts in memory. But a ViewModel lives as long as its screen. Leave the feed and it is cleared, cancelling the in-flight like; when the OS kills the process nothing remains. Android's docs treat process death as its own case, answered by SavedStateHandle for small UI state (saved state).

What I'd say. Ownership goes below the screen. A like is a write to Room plus a queued WorkManager job, since scheduled work is documented to persist across app restarts and device reboots (persistent work). The ViewModel only asks the repository to record the like. I reject a service and an app-wide coroutine scope: both die with the process and hold nothing durable.

The push I would expect: "Two screens show the same post and one of them likes it. How does the other know?" Both observe the one posts table, so the row change reaches both.

In Android's terms, screen and ViewModel are the UI layer and FeedRepository is the data layer. The recommendations page calls a domain layer recommended in big apps, for logic reused across ViewModels (recommendations); with one feed I skip it. The rules: the UI observes the database and never the network, network results go to the database and not the screen, and workers call FeedRepository, not the DAO or the API.

4. Make the hard part work (minutes 22 to 40)

4.1 Refresh and paging (minutes 22 to 31)

Your call. The user pulls to refresh, or opens the app on a stale cache. What happens to the list on screen until the new page arrives?

First instinct, and why it breaks. Clear the table, show a spinner, fetch. If the request fails after the clear, in a tunnel or on a 5xx, the user faces an empty screen, which is what the cache existed to prevent.

What I'd say.

Say it. "Refresh fetches first and replaces second. The old feed stays on screen. When page one arrives, one transaction clears the old order, upserts the posts and stores the new order, so nobody sees half a list. If the request fails, the old feed stays."

This is the order in the Paging 3 network-and-database sample: the call first, then one transaction that clears on a refresh and inserts (guide). On open I show a cache under ten minutes old as is and refresh an older one behind it. Ten minutes is my example; the guide's own sample uses an hour.

The push I would expect: "The cache is two hours old when the app opens. Spinner or old feed?" The old feed, with a refresh behind it. "And a page request fails halfway down?" A retry row at the end of the list, never a silent stop.

4.2 The pending like (minutes 31 to 40)

Your call. A refresh lands while a like is still waiting for the server. Does the server's snapshot win, or the user's tap?

First instinct, and why it breaks. Let the snapshot overwrite the row. But it was taken before the write landed, so the heart flips off, then on again when the write completes. A toggle endpoint is worse: if the response is lost and the client retries, the like flips back.

What I'd say.

Say it. "A like sets a state, never a toggle. In one transaction I set liked, move the count and mark the post pending, so the heart fills at once, and I queue a PUT. Server data never overwrites a pending row; local intent wins until the write is confirmed, then I store the server's count. Rapid taps collapse: one pending intent per post, last state wins."

Transient failures retry with backoff; a permanent rejection rolls the like back. That split is my classification, and because the call sets a state, a retry is safe. The merge code and the retry rules are in the build guide.

The push I would expect: "You kill the process right after the tap." The flag and the queued write are both persisted, so the like resumes on the next launch, as in the chat app.

If I am cut off mid-answer, I answer first:

Say it. "Yes, a second refresh while the like is pending is harmless, because pending rows keep their local state. I was partway through the write path; I'll finish."

4.3 Where iOS changes the design

Same data model and API, more plumbing of my own. The Swift loader is in the build guide.

  • No Paging library, so I write the loader and trigger it near the end of the list.
  • No WorkManager, so the pending like sits in a persisted outbox. I do not count on a background run after a force-quit, and I say so.
  • Apple says prefetch is not called for every cell, so a row must cope with a missing image.

Release reality:

  • A Play staged rollout can be halted, and users who already have the update keep it; the help page's remedy is a new release with a fix (Play help). An App Store phased release can be paused for up to 30 days (Apple). Neither page describes recalling an installed build.
  • Old versions stay installed, so the server keeps accepting their cursors and request shapes.
  • The new feed path ships behind a server-controlled flag, my kill switch and the only rollback that reaches installed apps.
  • A schema migration cannot be flagged off, so it ships one release ahead of the code that needs it.

Say it. "I can't recall a bad build, so the rollback is the flag plus a fixed build. I'd watch time to first content, failed likes, and duplicate or missing posts. Left out: ranking, ads, video, stories."

6. Follow-ups that change a constraint

Practice prompts, not a claim about what any interviewer asks. They get harder.

  1. Someone flicks through 300 posts on a weak connection. Strong: one page request in flight, a retry row on failure, prefetch ten rows ahead, no image prefetch on cellular, and a row cap that evicts the oldest. Weak: "load everything faster."
  2. Add video to posts. Strong: autoplay follows the most visible item and pauses off screen, as in the autoplay section of the video app. Weak: the video as one more image.
  3. A second phone. Strong: the server is the authority for count and liked state; the pending flag covers only this phone's unconfirmed tap, and a refresh brings the other phone's like in. Weak: syncing the database file.
  4. Someone signs out and another signs in. Strong: cache and pending likes belong to the old account, so I drain or discard them before the switch. Weak: clearing the feed and forgetting the queue.
  5. After release, users report repeated posts. Strong: flip the flag to the old path, pause the staged release, read the duplicate and missing post rates, ship a fix. Weak: "roll back the release."
  6. The backend changes the cursor format. Strong: the cursor is opaque, so the app does not parse it, but old cursors sit in the database and old apps still send theirs. The server accepts both, or the app drops stored cursors on upgrade. Weak: assuming everyone updates.

7. What changes by level

These levels are my own reading of the bar, drawn from vendor and prep material, not any company's rubric.

  • Mid-level: database as the source of truth, cursor paging, basic image caching. I want to hear: "I'll cache the feed in Room."
  • Senior: feed order in its own table, idempotent optimistic likes, refresh that clears only after success, the pending-intent merge. I want to hear: "I'll keep order in its own table so an edited post never moves."
  • Staff: ranking changes mid-session, consistency across devices, flags, metrics, and a plan to share the feed module across surfaces. I want to hear: "I'd ship the shared module behind a flag and watch time to first content before moving the second surface."

As I read it, the levels differ in who raises the problem: the interviewer at mid, the candidate at senior, the candidate with a rollout plan at staff.

Common weak answers. Ten minutes on ranking. A happy path with no failure behavior. Naming Paging 3 without saying why. The UI calling the network directly. A like endpoint that toggles. No kill switch. They come from public prep material and are not a dataset.

Staff answer: the decision and the rollout

Decision: one shared feed module, a paging and like-sync layer with a small contract (observe the feed, load more, like, report impressions); each surface owns its cell UI. Alternative: every surface keeps its own feed code, faster for the first team, then drifting apart on cursor handling and pending-like merging. Revisit trigger: a surface needs rules the contract can only express by branching on the surface.

Rollout: behind the section 5 flag, then a staged release. Guardrail: no rise in duplicate or missing posts, no drop in like success. Watch time to first content, scroll jank and failed likes.

Opinion vs verified: the Paging, WorkManager and prefetch facts were read from the official docs. The ownership model, metrics, rollout order, assumed numbers and level signals are my opinion. The native vs cross-platform guide shows how I weigh shared against separate code.
