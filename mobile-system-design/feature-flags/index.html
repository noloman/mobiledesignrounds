Design feature flags and remote config (Android and iOS)

Build it. The database schema, API, code and platform limits for feature flags and remote config are on a separate page: Build it: feature flags and remote config on Android and iOS (28 min read).

How to read this. This page is the 45 minutes, in the order I would spend them. Code, the contract and platform tables are in the build guide. The follow-up questions are my reconstruction from public prep material, not transcripts of real rounds.

TL;DR. My answer: the phone decides once per session, from values saved on disk. Every flag has a safe default in the code. A session starts when the app process starts. On a long return to the foreground (say after 30 minutes away), I start a new one. New values wait for the next session. Only kill switches (flags that turn a feature off) change at once. They also have a fallback that works when the flag service does not. On iOS the store is a @MainActor object with UserDefaults, and the kill switch uses the Remote Config real-time listener.

Patterns in this round.

  • Facade and adapter (the vendor sits behind a small flag interface)
  • Strategy (when new values apply: at the next start, or live for a kill switch)
  • Scoped owner (one store lives as long as the app)
  • Layered cache (a saved copy that is read before the network)

1. Scope and constraints (minutes 0 to 4)

In short: Design the phone side and the contract. Experiments and personal data wait.

A prompt I would expect: "Design feature flags and remote config for our mobile app. Teams ship features behind flags and change settings without a release." I ask five questions, with a default for each:

  • Who runs the flag server? Either. I design the phone and the contract.
  • What values? On or off, plus short text values.
  • Who gets what? A share of users, by platform and version.
  • Offline? Yes. The app must start with no network.
  • Experiments and personal data? Not now.
In scopeOut of scopeLeft out until you ask
On/off flags and short valuesThe flag dashboardLarge JSON config
Percentage rollout, platform, app versionThe server rule engineThe same user on two phones
Saved copy, safe defaults, kill switchExperiment statisticsTargeting with personal data

The phone does four things to this design:

What the phone doesRequirement at riskDeep dive
Stops the app process and starts it againFlags ready at the first screenSection 2
Stops background network accessA change reaches users who are awaySection 4.1
Loses the signal or hangs during a fetchThe app works with no answerSections 2 and 4.2
Runs on a battery and a data planNo polling loopSection 4.1

Your decision. The scope grows: "Also run A/B tests, and target by email domain." Which do you keep?

First idea, and why it fails. Say yes to both. An experiment needs a fixed group and a record of who saw what. Email targeting needs a privacy decision. Time runs out before the cold start path.

What I would say. Both change the data we send and save, so they wait.

Say this. "I build the flag path first: saved values, defaults, rollout and a kill switch. A/B tests and personal data each change what we send, so they come after. Tell me if you want one earlier."

The follow-up question I expect: "The paywall needs a JSON config, not just flags."

It returns as follow-up 2.

2. Data and contracts (minutes 4 to 14)

In short: The phone starts from the last saved answer. The code holds a safe default. The server picks the group.

Your decision. At app start, where do flag values come from? Wait for the network, use defaults from the code, or read the last saved answer from disk?

First idea, and why it fails. Fetch on launch and show a spinner until the answer arrives. With no signal, the user waits for a timeout. Firebase says its one-minute timeout may be too long for a good start (Firebase loading strategies). Android's splash screen guide says to hold the splash only for short local work (Android splash screen).

What I would say.

Say this. "At start I read the last saved answer from disk. It needs no network. If there is none, each flag uses its default from the code. Then I fetch in the background. The new answer is saved for the next session."

The follow-up question I expect: "A new install, no network. What does the user get?"

The defaults. A default is not a guess. It is the behavior that already shipped and worked.

  • A risky new feature defaults to off.
  • A proven feature with a kill switch defaults to on.
  • Firebase also says to set in-app defaults (loading strategies).

The follow-up question I expect: "You raise a rollout from 10 to 20 percent. How do the first 10 percent stay in?"

The server hashes a stable ID with the flag key into a rollout bucket. A bigger percentage only adds buckets.

  • LaunchDarkly hashes the context key and kind into 100,000 buckets. Raising the share adds buckets (LaunchDarkly).
  • Each flag picks its people on its own.
  • The ID is the account ID when signed in. Firebase's percent rule maps each app instance, so a reinstall can change the group (Firebase client templates).

The contract, in four lines:

  • Fetch: app version, platform and a stable ID in. Evaluated values and a version out.
  • Values: a key to a boolean or a short string. The app ignores keys it does not know.
  • Rules stay on the server. The phone gets answers, not rules (best practices).
  • Users can read any fetched value, so no secrets in flags (Firebase get started).

These are my own assumptions, not measurements:

AssumptionArithmeticWhat it decides
40 flags, about 60 bytes each40 x 60 = 2,400 bytesOne small saved record, not a database table

Firebase's default minimum fetch interval is 12 hours (Firebase get started).

3. Client structure (minutes 14 to 22)

In short: One app-wide store owns the flags. A screen takes a view when it opens and keeps it.

Your decision. Who owns the flag state? Each screen's ViewModel (the class that holds a screen's state) asking the SDK, a service, or one store that lives as long as the app?

First idea, and why it fails. Each ViewModel asks the SDK whenever it needs a value. Two problems:

  • A fetch can land between two reads. Two screens then disagree, or one screen changes while the user looks at it. Firebase says to avoid changing the UI while the user uses it (loading strategies).
  • Android clears a ViewModel when its screen leaves the back stack, the list of opened screens (ViewModel).

What I would say. An app-wide store loads the saved copy before the first screen and hands out views. I reject a service, because nothing here must run in the background.

Say this. "One store lives as long as the app. It loads the saved values before the first frame. A screen takes a view when it opens, and every answer in that view stays the same. A kill switch is the one exception, and it is read each time."

The follow-up question I expect: "Two screens both read the same flag. Which answer wins?"

The same one. Both views come from the same session copy.

On Android the store starts in the Application class and saves to DataStore (a Jetpack store for small settings). On iOS it is a main-actor object with UserDefaults. Three rules:

  • Screens never call the vendor SDK.
  • The code never asks for a flag without a default.
  • Only a kill switch changes while a screen is open.

4. Make the hard part work (minutes 22 to 40)

In short: New values wait for the next session. A kill switch is the one change that cannot wait.

4.1 When the app reads and applies values (minutes 22 to 32)

Your decision. When does the app fetch, and when do new values start to apply? On every launch and at once, on a timer, or in the background for the next session?

First idea, and why it fails. Fetch and activate at every launch, with a short cache. Two problems:

  • The values flip while the user is on the screen.
  • Ten opens a day make ten fetches. Firebase calls this a pattern to avoid (optimize fetch frequency).

What I would say.

Say this. "I use the values from the last session at once. In the background I fetch new values and save them for the next start. On a return to the foreground I fetch only if the saved copy is old. Kill switches are different: they change while the app runs."

Firebase documents this as the next-startup strategy (loading strategies).

The follow-up question I expect: "Product wants a change on every phone within an hour."

The limits:

  • A new value only reaches users at the next session. A process can live for days, so the session also restarts after a long time away. The kill switch is the only value that changes sooner.
  • The 15-minute check only avoids a pointless call. The real limit is Firebase's 12-hour minimum fetch interval. Kill switches skip it through live updates.
  • Live updates open one HTTP connection, and only in the foreground (Firebase real-time). LaunchDarkly mobile SDKs stream in the foreground and poll about once an hour in the background (SDK types).
  • A push can start a fetch. But Apple calls background pushes low priority and not guaranteed, and advises two or three an hour at most (Apple). A push is an extra.
  • Doze suspends network access on an idle Android phone (Doze). So the change waits for the next foreground.

The follow-up after that: "The user updates the app. The saved copy was written by the old version."

  • The new build reads that copy at its first start. It may not know a key, or a key may have a new type.
  • I store a schema version with the snapshot. If the version does not match, or a value has the wrong type, that flag uses its default from the code.
  • Unknown keys are ignored. A bad value must never crash the read.

4.2 The kill switch (minutes 32 to 40)

Your decision. A new feature crashes for 5% of users. How does the off switch reach them? The same config path, a faster path, or one that works even when the flag service fails?

First idea, and why it fails. Put the switch in the same config, with the default on, and use the normal timing.

  • The saved copy can be up to 12 hours old, and the next-session rule means one more restart.
  • A crash at start happens before any fetch can fix it.
  • A new install offline gets the default. If it is on, the broken feature is on.

What I would say. The kill switch has four layers. Each covers a gap in the one before.

Say this. "New code defaults to off. A kill switch is read live, and a live update changes it in the foreground. If the app crashes twice at start, it ignores the saved copy and uses the defaults. And the server can refuse the new request, so it works even when the flag service is down."

The follow-up question I expect: "The bad value is already saved, and the app crashes at launch."

Count starts that never finish. After two, use the defaults and delete the saved copy.

  • Limit 1: the count is only a guard. If the user force-quits in the first seconds, that start counts as a failure too.
  • Limit 2: it only catches crashes that happen early. A bad value that crashes a screen later needs the kill switch or a server rollback.
  • The next fetch can bring the bad value back, so fix the server value too. Firebase lets you roll the template back (client templates).

4.3 Where iOS changes the design

The design is the same. The Swift store is in the build guide. What changes:

  • The store is a @MainActor class. A view reads a flag without await, and the disk and the vendor stay behind async protocols.
  • The live kill switch uses the Firebase Remote Config real-time listener (addOnConfigUpdateListener). Without it, the iOS kill switch waits for the 12-hour fetch interval.
  • UserDefaults is on Apple's list of required-reason APIs. Declare the reason in your app's privacy manifest. The Firebase SDK ships its own manifest for its own use.
  • If a widget or extension needs flags, save the snapshot in a shared App Group suite, not in the app's own standard defaults.
  • A new install with no network reads no snapshot and uses the code defaults, as on Android.
  • The foreground signal is the scene phase. The active phase means the scene is in the foreground and interactive (Apple ScenePhase).
  • UserDefaults writes to disk asynchronously (Apple UserDefaults). If one write is missed, the next fetch repairs it.

In short: Each failure ends with the last good values or the defaults, never a blank screen or a stranger's flags.

Releases:

  • A Play staged rollout can be halted. Users who have the build keep it (Play Console help). An App Store phased release can be paused for up to 30 days (Apple).
  • Old versions stay installed. Never change a flag's type in place. Add a new key and keep the old one.
  • The flag is the kill switch, and it is the only rollback that reaches installed apps.
  • The flag client itself cannot be flagged. Ship it one release before the first flag that needs it. Apple wants new features described to App Review, not hidden or dormant (App Review Guidelines 2.3.1).

Say this. "I cannot recall a bad build, so the rollback is a flag plus a fixed build. I would watch crash-free users per flag group, fetch failures and flags past their date. I left out experiments, JSON config and personal data."

6. Follow-ups that change a constraint

In short: Each follow-up changes one constraint. A strong answer says what breaks.

Practice prompts, not a claim about what any interviewer asks.

  1. A campaign sends ten million users to the app at 9 a.m. Strong: the next-session rule and the fetch interval keep most opens off the network. Add random delay to retries. Live connections have a quota, so check the Firebase quotas before you rely on them for everyone. Weak: "poll every minute."
  2. The paywall needs a JSON config. Strong: parse it into a typed object, use the default on any error, carry a schema version. Keep it small: Firebase limits the size of values (see parameters). Weak: "parse it where it is used."
  3. One user, two devices, same experience. Strong: bucket by account ID, not by install. Firebase maps each app instance, so send an account bucket as a custom signal (client templates). Tests may need sticky assignment (sticky bucketing). Weak: "random per device."
  4. Legal says no email or location may leave the phone. Strong: send a bucket number or a coarse group, and keep the rules on the server. Name the cost: no targeting by those fields. IDs sent to a vendor are third-party data to declare to Apple (App privacy details). Weak: "hash the email."
  5. A bad value went live at 10:00 and 8% of users crash at start. Strong: roll the template back, use the kill switch, and rely on the crash guard for phones that saved the value. Weak: "roll back the release."
  6. The backend renames a flag and changes its type. Strong: old versions stay for months, so keep serving the old key and add a new one. Weak: assuming everyone updates.

7. What changes by level

In short: As I read it, the levels differ in who raises the problem.

These levels are my own reading of public prep material, not any company's rubric.

  • Mid-level: a flag client, defaults, a saved copy, a percentage rollout. I want to hear: "With no network the app uses the default from the code."
  • Senior: one decision per session, a stable bucket, a kill switch that works when config fails, and privacy of what is sent. I want to hear: "A new value waits for the next session, except a kill switch."
  • Staff: flags with owners and expiry dates, cleanup as a rule, testing, and a rollout plan for the flag system itself (staff guide). I want to hear: "Every flag has an owner and a date, and the build fails when the date passes."

Common weak answers. A fetch that blocks the first screen. No default for offline. A new value applied in the middle of a screen. A random group per launch. A kill switch that needs a working config. No plan to remove flags. These repeat across public prep material. They are not a dataset.

Staff answer: the decision and the rollout

  • Decision: one app-wide store, a list of flags declared in code (key, default, owner, expiry date, kill-switch mark), and the vendor behind a small interface. Unleash suggests lifetimes by type, such as 40 days for a release flag (feature flags). I would set my own.
  • Alternative: call the vendor SDK from every screen. It is faster for a quarter. Then cleanup means a search across the whole app.
  • Revisit trigger: a second app needs flags, or the vendor becomes a risk.
  • Rollout: the store ships first with no flags. Then each flag goes out at 1%, 5%, 25% and 100%.
  • Guardrail: crash-free users in the flag group must not drop against the control group. A flag past its date fails the build. After an archive, LaunchDarkly serves the fallback value from the code, so remove the code first (archiving).

What I read and what is my view: I read the cited pages on 14 October 2026. The store design, numbers, kill switch layers, crash guard and level text are my opinion.

Test yourself

In short: Seven questions from this case. Answer each one out loud first, then open the answer.

1. At app start, where do flag values come from, and why not the network?

From the last saved answer on disk, which needs no network. With no saved answer, each flag uses its default from the code. A fetch in the background saves new values for the next session. Waiting for the network would leave a spinner on a bad connection.

2. What is a safe default for a flag?

The behavior that already shipped and worked. A risky new feature defaults to off. A proven feature with a kill switch defaults to on. A new install with no network gets the defaults.

3. You raise a rollout from 10 to 20 percent. How do the first 10 percent stay in?

The server hashes a stable ID with the flag key into a rollout bucket. A bigger percentage only adds buckets, so nobody who was in drops out. Use the account ID when signed in, because an install-based ID can change on a reinstall.

4. Two screens read the same flag. Which answer wins, and when do new values apply?

The same one. Both take a view of one session copy, and a screen keeps its view while it is open. New values wait for the next session. Only a kill switch changes while the app runs.

5. A new feature crashes for 5 percent of users. How does the off switch reach them?

In four layers: new code defaults to off, a kill switch is read live, two failed starts make the app ignore the saved copy, and the server can refuse the new request. Each layer covers a gap in the one before.

6. The bad value is saved and the app crashes at launch. What now?

Count starts that never finish. After two, use the defaults and delete the saved copy. Also fix the server value, because the next fetch can bring the bad value back.

7. How does the kill switch reach a running iOS app quickly?

With the Firebase Remote Config real-time listener, addOnConfigUpdateListener. Without it, the iOS kill switch waits for the 12-hour fetch interval.

Words on this page (15)
Captive portal
A login page that a Wi-Fi network shows before it gives access to the internet. The phone looks online, but requests fail.
Cold start
A start of the app when it was not running. It is slower than a start from the background.
Crash-free rate
The share of sessions that end without a crash.
Doze
The deep-sleep mode of an idle Android phone. It pauses network access and delays background work.
Hash
A function that turns text, such as a flag key and a user ID, into the same number every time.
Kill switch
A remote flag that turns a feature off at once. It is the one rollback that reaches apps that are already installed.
Polling
Asking the server again and again if there is news. It costs battery and data.
Remote config
Settings that live on a server, and the app downloads them. The team can change a value without a new release.
Remote flag
A setting that the server can change. It can turn a feature on or off without a new release.
Rollback
Going back to the old behavior after a problem. A build on a user's phone cannot be taken back, so teams use a kill switch.
Rollout bucket
A number that the server works out from a user ID and a flag key. A flag set to 10% is on for the users with the lowest 10% of the numbers.
SDK
Software development kit. Code that other developers add to their own apps.
Snapshot
A copy of the data as it was at one moment. It is not a list of changes.
Staged rollout
A release to a growing share of users, not to everyone at once. It limits the harm of a bad release.
ViewModel
A class that holds the state of one screen. It survives a screen rotation.

What I checked (official pages, read on 14 Oct 2026):

  • Firebase Remote Config: loading strategies, the one-minute fetch timeout, set in-app defaults, avoid changing the UI while the user is in it, the 12-hour default fetch interval, throttling, no secrets in values, the random percent rule maps app instances, rollback of template versions.
