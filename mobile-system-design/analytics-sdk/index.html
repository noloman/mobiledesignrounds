How to read this. This page is a 45-minute round (the length I assume), in the order I would spend it. The code is in the build guide. The follow-up questions are my reconstruction from public prep material, not transcripts of real rounds.

TL;DR. My answer: the SDK (a code library that other apps add) promises to take the event, not to deliver it. It saves the event to disk and sends it later in a batch that never changes. It deletes the batch only after the server says yes. The server removes repeats. The SDK never blocks or crashes the host app.

1. Scope and constraints (minutes 0 to 4)

In short: Say what the SDK promises, keep money out of it, and leave some topics for later.

A prompt I would expect: "Design an analytics SDK for mobile apps." It is vague on purpose. I ask five questions, with a default for each:

  • Who uses the SDK? Several host apps (the apps that contain it), each with a start-up budget.
  • Who reads the data? A data team that wants counts and funnels (the steps users take, in order). A repeat is cheaper than a lost event.
  • Which privacy rules apply? EU and US state rules, so the SDK must stop collecting and delete data on request.
  • What does the server accept? A batch endpoint, an event ID and a batch ID.
  • Must any number be exact, such as money? No. The server keeps its own record of purchases.

Your decision. Finance says: "Count purchases from your analytics events." Do you accept, refuse, or keep the record on the server?

First idea, and why it fails. Accept, because the data is already there. But events are lost when the app is killed, repeated when a send is retried, and deleted when the user opts out. Money counted from them would be wrong.

What I would say.

Say this. "Events can be lost or repeated. Money cannot. So the server keeps the record of purchases, and events are for analysis only. If finance wants a check, we compare the two and look at the gap."

I reject using events as the record.

The follow-up question I expect:

"Then what are events good for?"

Trends and funnels. A small error does not change those decisions.

2. Data and contracts (minutes 4 to 14)

In short: An accepted event is on disk, has two IDs and two times, and the server can safely see it twice.

Your decision. The host calls track on the main thread (the thread that draws the screen). Does track promise delivery, a place on disk, or only that the SDK took the event?

First idea, and why it fails. Send the event at once with a network call and report the result. This fails when the phone is offline, or when the app is killed before the answer arrives.

What I would say. track promises only that the SDK took the event. It returns nothing to wait on. The event reaches disk within about one second. I reject sending each event as it happens.

The follow-up question I expect:

"The app is killed before the commit. What did you lose?"

At most one commit group (events written to disk together in one transaction). I document it.

  • At 5 events a second, that is about 5 events.
  • A count rule of 20 events caps a sudden spike.

Your decision. The device clock can be wrong. Which time do you store and send?

First idea, and why it fails. One timestamp from the device clock. It fails when the user sets the clock back a year.

What I would say. Each event stores the device time and a monotonic offset (time since boot, which the user cannot change). The batch carries its send time. The server adds its receive time and estimates the true event time. I reject trusting the device clock.

The follow-up question I expect:

"What if the user changes the clock while the app runs?"

The offset keeps the order inside one run. Across runs, a counter that belongs to the install keeps the order.

The contract has four lines. The build guide has the fields.

  • An event gets a random ID when track is called.
  • A batch gets an ID the first time its events are picked. It never changes.
  • The server ignores any batch ID or event ID it has seen.
  • The event keeps the identity it had at track time.

3. Client structure (minutes 14 to 22)

In short: The SDK owns its queue and its worker. It does not depend on the host's screens or app object.

Your decision. Who owns the disk queue and the work that sends it? The host's app object, a screen, a service, or an engine that the SDK creates and owns?

First idea, and why it fails. Start the SDK in a content provider (an Android component that runs at app start) so hosts write no code. App Startup says these are expensive to start and start in no set order (App Startup). So the SDK may start before consent is known. Also, work in a caller's scope ends with its screen, and the flush (sending queued events) stops.

What I would say. The host calls init once. It does no disk work. The SDK creates one engine with its own scope (the lifetime of its work), so its work can live longer than any screen (data layer). I reject three other owners:

  • The host's ViewModel, which ends with its screen.
  • A service, which adds a second lifetime for the host to manage.
  • A global singleton that the host does not control.

The follow-up question I expect:

"The host has a widget in a second process. Where does one writer break?"

One writer holds only inside one process. Give the store one owner process, or use SQLite locks with short transactions. This returns as follow-up 3.

On iOS, an actor (a Swift type that runs one task at a time) is the writer, and an async stream is the inbox. Three rules:

  • No disk or network work on the caller's thread.
  • Every entry point catches errors.
  • The SDK keeps only the application context, never an activity.

4. Make the hard part work (minutes 22 to 40)

In short: Fix each batch with an ID (a lease) and never change it. Check consent before anything is saved.

4.1 Batches, retry and background limits (minutes 22 to 31)

Your decision. The server is slow, or does not answer. How do you resend so that nothing is lost and nothing is counted twice?

First idea, and why it fails. Delete the events when you send them. On a retry, pick the newest events again. This fails when the response is lost. The server saved the first batch, the client sends a different one, and some events are counted twice.

What I would say.

Say this. "The first time I pick events, I give them a batch ID and record which events belong to it. A retry sends the same batch, even if newer events arrived. I delete it only when the server says yes. If the server has seen the ID, it skips the batch."

A permanent error, such as a 400, deletes the batch and counts it. A bad write key (the secret the SDK sends with data; 401 or 403) keeps the batch. Retries use backoff (wait longer after each failure) and a random delay. I reject picking events again on a retry.

The follow-up question I expect:

"The app is rarely opened. How does the queue empty?"

I flush when the app goes to the background and at the next launch. WorkManager (Android's scheduler for work that survives restarts) is only a backup. I promise no delivery time.

  • Periodic work repeats at most every 15 minutes, and can be delayed (define work).
  • A restricted app (unused for 8 days on Android 13 and later) may run jobs about once a day (App Standby Buckets).
  • So the next foreground flush is the real recovery.

When the disk is full, I drop the oldest events and count them. This keeps the newest data, and I document the choice.

4.2 Consent and privacy (minutes 31 to 40)

Your decision. Where does the SDK check consent: when the event is created, when it is saved, or when it is sent?

First idea, and why it fails. Save everything and filter at upload. This fails when the user says no after events are on disk.

What I would say. Consent is granted, denied or unknown, and unknown acts as denied. The gate sits at track, before the inbox. Opt-out stops collection, deletes the queue and cancels uploads. The host owns the prompt, and the SDK reads the host's choice, as Google asks (SDK safety). I reject filtering at upload.

Say this. "Short answer first: nothing is written before consent, so there is nothing to filter later. Now back to the batch lease, which keeps a retry from counting an event twice. Next I show the status codes."

The follow-up question I expect:

"What does iOS require from the SDK itself?"

Its own privacy manifest (a file that lists the data and the system APIs the SDK uses) (Apple).

  • It is needed if the SDK uses a required reasons API (a system API that Apple lists), collects data, helps the app collect data, or contacts tracking domains.
  • Requests to tracking domains fail without permission. I treat that as a network error.

4.3 Where iOS changes the design

  • A flush that must survive suspension is a file uploaded by a background URL session. It does not survive a force quit.
  • The writer is the only reader of the inbox stream.

5. Break it, ship it, roll it back (minutes 40 to 45)

In short: Every failure keeps the data safe. Rollback is the host app's kill switch plus a new release.

At release:

  • A Play staged rollout can be halted, but users who have the build keep it (Play help). A bad SDK version stays until users update.
  • Old SDK versions stay in the field. The server accepts every format version.
  • The host app's kill switch for the SDK is a remote flag that stops collection and upload. It reaches only devices that fetched it.
  • A flag cannot change the disk schema, the public API or the privacy manifest. Those need a new release.

Say this. "I start with a small share of one host app. Its crash-free rate (the share of sessions without a crash) and start time must not move. I turn off sampling and auto-capture. I cannot take a build back from users, so the kill switch comes first."

6. Follow-ups that change a constraint

In short: Each follow-up changes one constraint. These are practice prompts, not a claim about real interviews.

  1. The host calls track 10,000 times in a loop at launch. Strong: the bounded inbox drops the oldest events, a per-name limit stops the loop, and counters show it. Weak: "make the queue bigger."
  2. The host wants screens and taps recorded without code. Strong: off by default, because it adds volume and can capture text the host never meant to send. Weak: "capture everything and filter later."
  3. The host has a widget or service in another process. Strong: one lock works only inside one process. Give the store one owner process, or use short SQLite transactions. Weak: "one writer, so no problem."
  4. A user withdraws consent, or asks for erasure, with events queued and others already sent. Strong: opt-out deletes the queue, and a deletion hook asks the server to erase sent data. Weak: "stop sending."
  5. After a release, upload volume doubles and the host's crash-free rate drops. Strong: use the kill switch first, then compare delivery by SDK version. Weak: "roll back the release."
  6. The server changes the event shape while three old SDK versions are in the field. Strong: the server reads all versions, and new fields are added, not changed. Weak: "force an update."

7. What changes by level

In short: Mid builds the queue, senior makes it safe, staff adds the decision and the rollout.

These levels are my own reading of the bar, drawn from vendor and prep material (courses and books), not any company's rubric.

  • Mid-level: a small public API, a SQLite queue, batching, retry, opt-out. "I save the event first and delete it after the server says yes."
  • Senior: track never blocks, one writer, fixed batches, two timestamps, a counted drop policy, consent before disk. "A retry must send the same batch, or the server cannot tell it is a repeat."
  • Staff: build or buy, a host kill switch, version adoption, the SDK's own cost in the host. "The host's crash-free rate and start time are my guardrails, not my drop rate."

Common weak answers. Spending the time on the server. Never testing a kill between track and send. Naming a vendor SDK without saying why. Leaving consent to the end. Forgetting that an SDK crash counts against the host. These repeat across public prep material. They are not a dataset.

Staff answer: the decision and the rollout

Decision: a platform team owns the SDK and provides a host kill switch. Alternative: a vendor SDK. It starts faster but gives up control of the data format. Revisit trigger (the sign to decide again): the SDK costs more to keep than the control is worth. Then buy one and hide it behind our API.

Measure: drop counters by reason, delivery by SDK version, and the SDK's start-up cost. Guardrail (a number that must not get worse): the host's crash-free rate and start time, when a new SDK version is released.

Rollback on mobile: the kill switch reaches only devices that fetched the config. A bad build cannot be taken back. The push SDK case is similar.

Opinion vs verified: the design and the metrics are my opinion. The WorkManager timing, App Standby limits and privacy manifest rules were read on the linked pages. See also the native vs cross-platform guide.
