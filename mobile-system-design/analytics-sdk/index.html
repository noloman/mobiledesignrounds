Design an analytics SDK (Android and iOS): queue, batching, retry and consent

How to read this. A library question with a data pipeline inside it. Sections 1 to 9 use Kotlin; section 10 maps to iOS.

TL;DR. The SDK is a durable, bounded on-disk queue behind a thin public API. track validates, stamps an event ID and client time, and hands the event to one background worker that writes it to disk. A flush loop reads a stable batch, sends it with a batch ID, and deletes it only after the server accepts it. Retries are safe because event IDs and batch IDs let the server dedupe. Never block the host app, never crash it, never collect before consent, and cap the queue with a documented drop policy.

1. Clarify the requirements (about 5 min)

Ask the app developers:

  • Do hosts embed other SDKs, and is there a startup budget? (Assume yes to both: init does no I/O.)
  • Which consent regimes apply? (Assume EU and US states, so collection must be gateable and erasable.)

Ask the data team:

  • Is a duplicate worse than a lost event? (Assume at-least-once delivery with server dedupe on event ID.)
  • Do they need ordering, and can they tolerate wrong clocks? (Order per device with a client-side counter. They can't tolerate wrong clocks, so we send two timestamps.)

Non-functional:

ConcernTarget
Main thread and startupTiny bounded work per call; no I/O; nothing at process start unless asked
DurabilityAn accepted event survives a crash, within a stated sync policy
DeliveryAt least once, deduped by the server
Safety and privacyNever throws into the host; nothing collected before consent
FootprintFew dependencies, small binary, capped disk and memory

Out of scope: the backend pipeline, attribution, crash reporting.

2. High-level architecture (about 10 min)

Two decisions carry the design. One writer: appends go through a single worker (a single-threaded dispatcher on Android, an actor on iOS), not scattered locks. Uploads run on their own coroutine, one at a time, so a slow network never holds up the writer. Disk is the source of truth: events leave the store only after the server confirms the batch, and flush policy is a small object driven by remote config.

Where it sits. The SDK lives beside the host's layers. Host repositories or ViewModels call it, not composables, and it needs only the application context. Inside, the SQLite queue is the single source of truth, and the uploader drains it the way the offline-first guide describes for queued work. The same drain-and-retry shape shows up in the chat app send path and the photo backup upload queue.

3. Public API and data model

Keep the surface small. Every public method is a contract for years.

// Sketch: public surface (Kotlin)
class Analytics private constructor(/* internal wiring */) {
    companion object {
        fun init(context: Context, config: AnalyticsConfig): Analytics   // cheap; no I/O; keeps only applicationContext
    }
    fun track(name: String, properties: Map<String, Any?> = emptyMap())   // main-safe, non-suspend
    fun screen(name: String)
    fun identify(userId: String, traits: Map<String, Any?> = emptyMap())
    fun flush()                       // a request, returns immediately
    fun reset()                       // new anonymous ID, clear user ID
    fun setConsent(consent: Consent)  // GRANTED, DENIED, UNKNOWN (default)
    fun optOut()                      // stop collecting, drop the queue
}

Choices to defend:

  • No return value that invites waiting. track returns Unit; an awaitable flush lives in the test module.
  • Properties are a restricted map. The Kotlin type is Map<String, Any?>, so the compiler admits anything; validation lets through only strings, numbers, booleans, null and bounded nested maps and lists, and rejects the rest at the boundary. The Swift PropertyValue enum makes the same list a type.

The stored event:

FieldPurpose
eventIdRandom UUID created at track; the dedupe key
localSeqClient-side per-install counter for ordering; not the server's seq as in the chat and ticker cases. schemaVersion versions the envelope
name, propertiesPayload after validation and PII scrubbing
clientTimeWall-clock time at track, plus a monotonic offset
anonymousId, userId, sessionIdIdentity captured at track time, not send time

Validation. Check name format, property count, value types and encoded size. In release, drop the event and count it by reason; in debug, log loudly. Never throw to the caller.

4. Threading and startup

The host's main thread is not ours.

  • track allocates and hands off without blocking: a bounded Channel with trySend on Android, AsyncStream.Continuation.yield on iOS.
  • Wrap every entry point in a catch-all. A bug in our code becomes a dropped event and a counter, not a host crash. The engine below does this in guard, with a CoroutineExceptionHandler behind it for anything else.

Auto-init. Many SDKs initialize through a ContentProvider so hosts write no code. The App Startup docs say content providers are expensive to instantiate, can slow startup, and initialize in an undetermined order. App Startup shares one InitializationProvider and supports lazy initialization with AppInitializer.initializeComponent after disabling automatic init with tools:node="remove". For an SDK the better default is explicit: the host calls Analytics.init and the SDK ships no provider. An SDK that collects before consent is a privacy bug, not a convenience.

5. The hard part: queue, batching, retry and clocks

Durable queue

Use SQLite directly or Room as an internal detail. One table for events, one for batches.

// Sketch: write path and flush (Kotlin, simplified)
internal class Engine(
    scope: CoroutineScope,                 // SDK-owned external scope; injected single-threaded dispatcher + SupervisorJob
    private val store: EventStore,
    private val uploader: Uploader,
    private val policy: FlushPolicy,
) {
    private val dropped = AtomicLong()        // inbox overflow, one of the drop counters
    private val internalErrors = AtomicLong() // bugs of ours that we swallowed
    private val inbox = Channel<Event>(
        capacity = 1_000,
        onBufferOverflow = BufferOverflow.DROP_OLDEST,
        onUndeliveredElement = { dropped.incrementAndGet() },
    )
    private val flushRequests = Channel<Unit>(Channel.CONFLATED)
    private val flushLock = Mutex()

    init {
        val guarded = scope + CoroutineExceptionHandler { _, _ -> internalErrors.incrementAndGet() }
        guarded.launch {                      // the writer: appends only, never waits on the network
            for (event in inbox) guard {
                store.append(event)
                if (store.pendingCount() >= policy.flushAt) requestFlush()   // COUNT(*) per event; keep a counter in real code
            }
        }
        guarded.launch {                      // the uploader: one flush at a time
            for (request in flushRequests) guard { flushOnce() }
        }
    }

    fun enqueue(event: Event) { inbox.trySend(event) }   // never suspends, never throws
    fun requestFlush() { flushRequests.trySend(Unit) }   // timer, background and flush() land here

    // WorkManager calls this too, so the lock covers both callers
    suspend fun flushOnce() = flushLock.withLock {
        val batch = store.leaseBatch(policy.maxBatchSize) ?: return@withLock   // reuses an open lease first
        when (uploader.send(batch)) {                                          // enum SendResult
            SendResult.OK, SendResult.REJECTED -> store.delete(batch.id)       // REJECTED: a permanent 4xx other than 408 and 429
            SendResult.RETRY -> store.release(batch.id)                        // same batch next time
        }
    }

    private suspend fun guard(block: suspend () -> Unit) {
        try { block() }
        catch (e: CancellationException) { throw e }
        catch (e: Exception) { internalErrors.incrementAndGet() }
    }
}

Three things in that sketch are fixes to my first draft. The writer and the uploader are separate coroutines, so a slow upload cannot back up the inbox (in a small JVM test, 2,500 events arrived during a one second upload and all were either stored or counted as dropped). flushOnce takes a Mutex, so the in-process trigger and the WorkManager worker never upload at the same time. And every loop body runs inside guard, which counts an exception and keeps the loop alive instead of letting it end the only consumer; it rethrows CancellationException so cancellation still works. If send throws, the batch stays leased and the next flush reuses it.

What the sketch leaves out: the T-seconds timer and the background trigger, which would just call requestFlush(); the per-reason drop counters beyond the inbox one; and the status mapping inside Uploader, which returns REJECTED only for the permanent 4xx codes in the retry section and RETRY for 401 and 403.

The detail that matters is leaseBatch. The first time events are selected, the store assigns a batchId and records which event IDs belong to it. A retry resends the same batch with the same ID and events, even if newer events arrived. The server can then ignore any batch ID it has seen.

Crash safety. SQLite commits are atomic, so a half-written row never ships. Committing every event is safest and slowest; grouping appends into one transaction is the usual compromise, and a kill before the commit loses that group. State the trade-off.

Flush policy

TriggerWhy
Pending count reaches NBounds batch size and latency under load
T seconds since the oldest pending eventBounds latency at low traffic
App moves to backgroundThe process may die soon
App launchDeliver what an earlier process could not

N, T and the batch cap come from remote config with bundled defaults; any number you quote is illustrative.

I don't rely on the process staying alive. The queue is on disk, so a flush can happen later. While the process runs, the engine flushes on count, on time and when the app goes to the background, using its own scope rather than the caller's. When the process is gone, WorkManager takes over: one unique periodic job and one retry job, each needing a network, each just calling flushOnce. The Android docs list analytics events as a fit for this kind of queue drained with exponential backoff.

Result.retry() backs off exponentially (30 seconds by default, 10 at minimum) and can run late, so I promise nobody a delivery time. Periodic work also cannot repeat faster than 15 minutes, and constraints can delay or skip a run, so the "T seconds" row in the table above is the in-process timer's job, never periodic work. Use a worker the default factory can build, so a host's custom WorkerFactory cannot break it (that one is my design advice, not from the docs). WorkManager itself initializes through App Startup, so depending on it means inheriting that init.

Backoff and retry

  • Transient: network errors, timeouts, 408, 429 and 5xx. Retry them, and honor Retry-After when the server sends it.
  • Permanent: any other 4xx, such as a 400. Delete the batch and count it; a poison batch must not block the queue. The exception is 401 and 403: those mean our write key is wrong, so I keep the batch, back off and raise a counter instead of deleting data.
  • Use exponential backoff with jitter and a cap, one upload in flight, and a persisted failure count. A start I'd try is a few seconds, doubling to a cap of a few minutes, but those numbers are illustrative. The chat app case has the same transient/permanent split for sends.

Idempotency. The server dedupes on event ID within a retention window and can short-circuit on batch ID. Exactly-once is not on offer; at-least-once plus dedupe is.

Clock skew

Device clocks are wrong. Send clientTime on each event and sentAt on the batch, both from the device clock; the server records receivedAt. Then receivedAt - (sentAt - clientTime) estimates the true event time, assuming a constant offset and small latency. A monotonic delta per event keeps in-process order if the user changes the clock.

Backpressure and drop policy

  • Inbox: bounded, drop oldest.
  • Disk: cap by count and bytes; when full, drop the oldest.
  • A per-name rate limit and size cap stop a runaway loop in app code.
  • Expose counters: drops by reason, queue depth, oldest event age.

Dropping oldest favors fresh data; dropping newest keeps a coherent prefix. Document the choice.

6. Network, sessions and sampling

Network. Send one gzip-compressed body per batch, with shared context (app, OS and SDK version) once. Keep call count low, since radio wakeups cost more than bytes. Assume anyone can pull the write key out of the APK. It should only be able to write events, never read data, and the server should rate-limit by it.

Sessions. A new session starts at first launch or when the app returns to the foreground after a configurable idle gap, stamped at track time because the SDK sees lifecycle events.

Auto-capture. I'd ship it off by default. Automatic screen and tap events inflate volume, can scoop up text the host never meant to send, and the host cannot see what the SDK decides to record. Lifecycle events for sessions are the exception, since the SDK needs them anyway.

Identity. The anonymous ID is a random UUID, not derived from hardware. identify labels later events only; the server stitches identities.

Sampling. Decide once per install or session from a hash of the anonymous ID against a remote-config rate, and stamp the rate on events so analysts can reweight. Per-event sampling breaks funnels.

7. Privacy and consent

Make the safe behavior the default.

  • No collection before consent. Consent is UNKNOWN, GRANTED or DENIED; UNKNOWN acts like DENIED. Persist it, and never write pre-consent events to disk.
  • Opt-out must act: stop collecting, delete the queue, and offer a deletion hook for erasure requests.
  • Data minimization: no advertising ID by default, no fingerprinting, no automatic text capture. Scrub known PII keys and accept a host redaction callback.
  • Advertising ID on Android. The docs say users can reset it and opt out, and apps should not cache it. For apps targeting Android 13 (API 33) or higher, the Play services ID needs the AD_ID permission or the ID is replaced with zeros, and an SDK that declares the permission has it merged into the host manifest. An SDK that does not need the ad ID should not declare it.
  • ATT on iOS. Apple's rule: if your app combines data about people with other companies' data in order to follow them across apps and sites, you must ask through App Tracking Transparency. The host app owns that prompt, not the SDK.
  • Disclosure. Google Play says developers must reflect data collected or shared through third-party SDKs in the Data safety form, so ship a field-by-field description.

Who is legally responsible under GDPR or CCPA is a question for a lawyer. The SDK's job is to make the compliant path the easy one.

8. Versioning, remote config and multiple SDKs

Versioning. Semantic versions cover the public API and the wire format. Put schemaVersion on events and sdkVersion on batches; the server must accept old versions while old apps are in the field. Behavior is API: changing a default flush interval or drop policy changes someone's data volumes.

Remote config. A small document fetched at launch carries flush limits, sampling rate and a kill switch. Cache the last good copy, bundle defaults, and limit it to documented keys.

Multiple SDKs. Chain the uncaught-exception handler, namespace your database and work names, and avoid heavy transitive dependencies.

9. Testing and debuggability

Use constructor injection for the clock, dispatcher, network and store (no Hilt forced on the host; if the host uses @HiltWorker, give it a WorkerFactory), and ship FakeEventStore and FakeUploader in a test module, since official guidance prefers fakes to mocks. Test a kill between write and send, duplicate delivery and a clock jump. For debugging, offer a debug flag, a queue dump and a counters snapshot. Android's logging guidance says to minimize sensitive output and strip verbose logs from release builds, so keep logging off by default and redact values.

10. How to build an analytics SDK on iOS (Swift)

The architecture carries over. The differences are lifecycle, background time and the privacy manifest.

// Sketch: iOS facade (Swift 5.9+ for AsyncStream.makeStream; makeStream is back-deployed to iOS 13, OSAllocatedUnfairLock needs iOS 16)
public enum PropertyValue: Sendable {
    case string(String), number(Double), bool(Bool), null
    indirect case array([PropertyValue])
    indirect case object([String: PropertyValue])
}

struct Event: Sendable {
    let id: String, name: String, clientTime: Date   // the real one also carries localSeq, identity and sessionId
    let properties: [String: PropertyValue]
}

public final class Analytics: Sendable {
    private let inbox: AsyncStream<Event>.Continuation
    private let dropped = OSAllocatedUnfairLock(initialState: 0)   // drop counter, by reason in the real one

    public init(config: AnalyticsConfig) {
        let (stream, continuation) = AsyncStream.makeStream(
            of: Event.self, bufferingPolicy: .bufferingNewest(1_000))   // drops the oldest event when full; same choice as the Android inbox
        self.inbox = continuation
        let engine = Engine(config: config)
        Task.detached(priority: .utility) { await engine.run(stream) }
    }

    deinit { inbox.finish() }   // ends the stream, so the engine task ends too

    public func track(_ name: String, properties: [String: PropertyValue] = [:]) {
        let event = Event(id: UUID().uuidString, name: name,
                          clientTime: Date(), properties: properties)
        if case .dropped = inbox.yield(event) { dropped.withLock { $0 += 1 } }   // sync, ordered
    }
}

actor Engine {
    init(config: AnalyticsConfig) { /* store opened lazily */ }
    func run(_ events: AsyncStream<Event>) async {
        for await event in events { /* append to SQLite, maybe flush */ }
    }
}

What is genuinely different:

  • Privacy manifests are part of the SDK. An SDK should ship its own PrivacyInfo.xcprivacy if it uses any of the sensitive APIs Apple lists, collects user data, helps the host app collect it, or contacts tracking domains. Apple's page has the exact list, and it also covers a list of SDKs that need a manifest and signature, which I don't go into here. I'd not count on the host's manifest to cover the SDK.
  • Tracking domains can fail. If NSPrivacyTracking is true, the manifest lists NSPrivacyTrackingDomains, and Apple says requests to them fail without tracking permission. Treat that as a normal network failure.
  • Background time is finite. A beginBackgroundTask task must be ended before time expires or the system kills the app, and the expiration handler runs on the main thread, so keep it tiny. BackgroundTasks does not keep work alive past process death; it only schedules a chance to run later. For a flush that must survive suspension, persist the batch to a file and upload it from a background URLSession, which the system keeps running while the app is suspended (but not after a force-quit).

ScenarioHandling
Kill between track and commitLoss window is the commit group; documented
Upload succeeds, response lostRetry the same batch ID; server dedupes
Server returns 5xx or 429Backoff with jitter, honor Retry-After
Offline for daysDisk cap and drop policy
Opt-out mid-flightCancel uploads, delete the queue
Server returns 400Poison batch: delete it, count it, keep draining
Disk full or at the capDrop oldest, count by reason
User changes the clockMonotonic delta keeps in-process order
Consent revoked after a writeDelete the queued events along with the opt-out
Two processes (a service or widget host)SQLite contention: "one writer" only holds per process, so give the store a single owner process or rely on SQLite locking with short transactions
WorkManager and the in-process flush overlapBoth call flushOnce, which holds a lock, so uploads run one after the other and the second sees the batch already deleted or gets the next one

12. What changes by level

  • Mid-level: a facade, a SQLite queue, batching by count and time, a background thread, simple retry, opt-out.
  • Senior: track never blocks, the write happens on one worker, and a crash costs at most the current commit group. Also batch leases with event and batch IDs, jittered backoff, a counted drop policy, clock-skew timestamps, lazy init, consent gating, never-crash wrappers.
  • Staff: remote config with a kill switch, sampling, privacy manifest and disclosure for both stores, schema governance, SDK health telemetry, wire-format migration, build versus buy.

Staff answer: the decision and the rollout

Decision: I'd run this as a platform-owned SDK with a remote-config kill switch, rather than letting each app team embed its own tracker. Alternative: a vendor SDK, which is faster to start and gives up control of the wire format and privacy behavior. Revisit trigger: when maintaining the SDK costs more than the control is worth, buy and wrap it behind our facade.

What to measure: drop counters by reason, delivery rate by SDK version, queue age at flush, and the SDK's own startup and CPU cost in the host. Guardrail: host crash-free rate and cold-start time must not move when a new SDK version ships.

Rollback on mobile: the kill switch only reaches clients that have fetched the config, and old SDK versions stay in the field for as long as hosts do not update, so the server must keep accepting every wire version. A bad build already installed cannot be pulled back; the fix is a new release. The push SDK has the same shape.

Opinion vs verified: the design and the metrics are my opinion; WorkManager and privacy facts are checked against the linked docs. For how this plays at staff level see the staff mobile loop guide and the native vs cross-platform guide.

13. Follow-up questions worth practising

  1. How do you avoid duplicates? (Not at the client: at-least-once plus server dedupe.)
  2. What if the clock is a year off? (Two timestamps and a monotonic delta; the server corrects.)
  3. What if the user declines consent? (Nothing stored; earlier data is deleted on opt-out.)
  4. How do you debug a data gap? (Drop counters by reason, queue age, last accepted batch ID, delivery rate per SDK version.)
  5. A host calls track 10,000 times in a loop on launch. What happens? (The bounded inbox drops, the per-name rate limit trips, and the counters say so.)
  6. The host app runs a second process. Where does "one writer" break? (SQLite contention; pick a single owner process or accept locking.)
  7. Would you auto-capture taps and screens? (Off by default; see section 6.)
