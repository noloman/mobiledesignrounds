Draft v1. Companion to the image loading interview case.

This is the implementation material behind the image loading interview case: the API sketch, pipeline, cache key and coalescing code, recycling rules, decode, HTTP caching, failure modes, platform limits and the Swift version. None of it belongs in the 45 minutes; I draw it only if asked. The Kotlin snippets are sketches against stubs, and the Coil and Glide behaviour is described from their documentation, not their source.

1. Public API

Design the API first, because it forces the lifecycle questions. The shape I'd use, and the one Coil's ImageRequest follows, is a request value object plus a target. The block below is illustrative API, not Coil's exact names (for example, Coil's rounded-corners transformation takes a pixel radius, not dp):

// Sketch of the public surface
val request = ImageRequest.Builder(context)
    .data("https://cdn.example.com/a.jpg")
    .size(ViewSizeResolver(imageView))        // resolve from the view; fall back to display size
    .transformations(RoundedCorners(8.dp))
    .placeholder(R.drawable.ph)
    .error(R.drawable.err)
    .crossfade(true)
    .target(imageView)                        // binding + lifecycle live here
    .build()

val handle: Disposable = imageLoader.enqueue(request)   // cancel() on recycle

interface ImageLoader {
    fun enqueue(request: ImageRequest): Disposable                // views: cancel() on recycle
    suspend fun execute(request: ImageRequest): ImageResult       // non-view callers and tests
    fun prefetch(request: ImageRequest)                           // no target: warm the caches
    fun trimMemory(level: Int)                                    // host forwards system signals
}

Points to say out loud:

  • A request is a value object. Immutable, comparable, and cheap to build, so a list adapter can create one per bind.
  • The target owns binding. The loader writes to the target only if the request is still the target's current request. This is the fix for the recycled-row bug (section 4).
  • The host owns lifecycle and the memory budget. The library takes a lifecycle and a memory limit; it does not guess either.
  • Inject the loader. Callers depend on an interface, so tests and the app can swap the implementation (constructor injection, Hilt-provided singleton). Call enqueue from the UI layer; prefetch comes from the UI too, or from a data-layer class, never from a ViewModel that holds a Context.

2. Pipeline and architecture

 View / Compose target
    │ enqueue(request)         ▲ result (only if still current)
 ImageLoader  ── Interceptor chain ──────────────────────────────┐
    │                                                            │
 Memory cache (byte-bounded LRU) ──hit──► deliver                │
    │ miss                                                       │
 In-flight map (key → shared Deferred)   ← coalescing            │
    │ first caller only                                          │
 Disk cache (LRU, size-capped) ──hit──► decode                   │
    │ miss                                                       │
 Network (OkHttp / URLSession) → write disk → decode(target size) → transform → memory cache

Official architecture mapping: the loader sits at the UI layer boundary: Composables and Views call it, ViewModels only expose image URLs in uiState, in line with the UI-layer page's advice to keep UI logic involving types like Context out of the ViewModel. Its network and disk code are the library's own data sources. The shared downloads run in a scope I inject, so one caller leaving doesn't cancel them. See UI layer and data layer.

Stage by stage:

  1. Memory cache. Decoded bitmaps, checked synchronously on the calling thread because the lookup is fast. A hit means no frame is lost to async work.
  2. In-flight map. Before starting work for a key, check whether someone is already doing it (section 3).
  3. Disk cache. Encoded bytes (or processed results), checked off the main thread.
  4. Network. Conditional requests, cache headers, bounded concurrency.
  5. Decode. Sample down to the target size, off the main thread.
  6. Transform. Crop, round, blur. Part of the cache key.

Glide's docs describe the same order: it checks active resources (images already displayed in another view), then the memory cache, then the disk cache. Coil keeps a memory cache of decoded bitmaps and a disk cache for images loaded from the network.

3. Cache keys, coalescing and the memory cache

Cache key design

The key must change whenever the output would change. For memory that is (source, target size, transforms, config). Glide's docs say the active-resource, memory and resource-disk keys include the model, width and height, an optional transformation, options and an optional signature; the data-disk key has at least the model and the signature.

  • Include size. A 100px thumbnail and a 1080px hero from the same URL are different bitmaps. Without size in the key, you show a blurry hero or waste memory on a huge thumbnail.
  • Include transforms. Rounded and plain versions are different results.
  • Disk caches can key more loosely. Store the original encoded bytes under the URL key and re-decode per size, or store each processed result. The first costs CPU per decode; the second costs disk. Glide's default for remote images is to store the unmodified original.
  • Version via the URL or a signature, not by guessing. If the server replaces an avatar at the same URL, you need a content hash in the URL or an explicit signature, or the cache serves stale pixels until eviction.

Memory LRU and request coalescing (sketch)

The trim thresholds below are my example values, and the LruCache use follows the sizing idea in the Android cache bitmaps guide (the key object, allocationByteCount and the trim logic are mine).

data class CacheKey(val source: String, val width: Int, val height: Int, val transforms: List<String>)

class MemoryCache(maxBytes: Int) {
    private val lru = object : LruCache<CacheKey, Bitmap>(maxBytes) {
        override fun sizeOf(key: CacheKey, value: Bitmap) = value.allocationByteCount  // bytes, not entry count
    }
    fun get(k: CacheKey) = lru.get(k)
    fun put(k: CacheKey, b: Bitmap) { lru.put(k, b) }
    fun trim(level: Int) {
        if (level >= ComponentCallbacks2.TRIM_MEMORY_BACKGROUND) lru.evictAll()
        else if (level >= ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN) lru.trimToSize(lru.size() / 2)
    }
}

class Coalescer(external: CoroutineScope) {
    // Same context as the injected scope, but a SupervisorJob: one failed fetch must not cancel the others.
    private val scope = CoroutineScope(external.coroutineContext + SupervisorJob(external.coroutineContext[Job]))
    private val inFlight = HashMap<CacheKey, Deferred<Bitmap>>()   // guard with a lock or a single-thread dispatcher
    private val waiters = HashMap<CacheKey, Int>()

    suspend fun load(key: CacheKey, work: suspend () -> Bitmap): Bitmap {
        val job = synchronized(this) {
            waiters.merge(key, 1, Int::plus)
            inFlight.getOrPut(key) {
                scope.async {
                    val me = coroutineContext[Job]
                    try { work() } finally { synchronized(this@Coalescer) { inFlight.remove(key, me) } }   // only our own entry, never a newer one
                }
            }                                                      // first caller starts the work
        }
        try { return job.await() }
        finally {
            synchronized(this) {
                if (waiters.merge(key, -1, Int::plus) == 0) {      // last waiter left: cancel the work
                    waiters.remove(key); inFlight.remove(key)?.cancel()
                }
            }
        }
    }
}

Why this shape:

  • Byte-bounded. The Android docs size the cache in bytes by overriding sizeOf and suggest about one eighth of the app's available memory as an example. Bitmaps vary by orders of magnitude, so an entry-count limit is meaningless.
  • Work is shared, ownership is counted. One download and one decode serve every waiter. Cancelling one row must not cancel the work for the others, so the work is cancelled only when the last waiter leaves.
  • Remove on completion. The worker's finally drops its own entry when the work finishes, success or failure, so a later caller starts a fresh fetch instead of joining a finished one. It removes the entry only if the map still holds this exact job, so a late finally from a cancelled job cannot delete a newer request's entry. Callers still attached when a fetch fails all get that failure; nothing is cached.
  • One failed fetch must not take the others down. The scope the host injects is usually a plain Job, and a failed async child cancels its parent, which would cancel every other load. The coalescer wraps it in a SupervisorJob so a 404 only fails the callers waiting on that key.
  • Do not use weak or soft references as a cache. The Android docs say they are not recommended because the garbage collector clears them aggressively.

4. Views, recycling and cancellation

Lists recycle views. A request for row 3 may finish after the view has been rebound to row 40. The rules:

  1. Bind a request to the target. Setting a new request on a view cancels the old one. Clearing a view (recycle, detach) cancels the current one.
  2. Check before delivering. On completion, compare the request ID to the target's current request. If it differs, drop the result for the view; it still goes in the cache. The Coalescer sketch leaves that put to the work lambda passed to load.
  3. Tie to lifecycle. Start on the started state, cancel on destroyed. In Compose, use the composition scope so leaving the composition cancels.
  4. Resolve the size lazily. A view has no size until it is laid out. Wait for layout rather than loading at full resolution.
  5. Cancel prefetch for rows scrolled past. Prefetch with lower priority than visible loads.

The feed side of this (what to prefetch and when) is in the news feed case study.

A loader without cancellation downloads and decodes images for rows no one will see, which costs battery, data and frame time.

5. Decode, downsample and memory pressure

A decoded bitmap costs width x height x bytes per pixel, regardless of the file size. The Android docs give the example of a 2048x1536 image at ARGB_8888 using about 12 MB, and about 0.75 MB at inSampleSize = 4. So:

  • Downsample to the target size. Read dimensions first (inJustDecodeBounds), pick a sample size, then decode. inSampleSize rounds to a power of two, so you land at or above the target, then scale the last step if exact size matters. ImageDecoder with a target size does the same on newer API levels.
  • Ask the server for the right size too. A CDN resize parameter saves bytes on the wire as well as in memory. Include it in the key.
  • Decode off the main thread, on a bounded dispatcher. Cap concurrent decodes (for example, the CPU count) so a fast scroll cannot spike memory with parallel full decodes.
  • Pick the config deliberately. RGB_565 halves memory for opaque photos at a quality cost; HARDWARE bitmaps live in graphics memory but cannot be read back or mutated.
  • Bitmap pooling. Reusing bitmap memory (inBitmap) cuts allocation churn and GC pauses during fast scrolls. Glide has a BitmapPool that responds to ComponentCallbacks2. Pooling is optional complexity; mention it, and note the trade-off: reuse needs matching sizes and careful ownership.
  • React to memory pressure. The host forwards onTrimMemory. Evict everything on TRIM_MEMORY_BACKGROUND (40) and shrink on TRIM_MEMORY_UI_HIDDEN (20). The RUNNING_*, MODERATE and COMPLETE levels are deprecated and apps are not notified of them on API 34 and later, so handle them only if you support older releases (checked in the ComponentCallbacks2 source). Glide registers itself as a ComponentCallbacks2 and trims its memory cache and bitmap pool from onTrimMemory (read in the Glide source, not its docs).
  • Expect a RAM-scaled ceiling on Android 17. Android 17 introduces app memory limits based on total device RAM. A session killed this way reports REASON_OTHER in ApplicationExitInfo, with a description containing MemoryLimiter:AnonSwap (see the Android 17 behavior changes). My take: log that exit reason next to your OOM metric, and budget the cache against the device's memory class rather than a fixed number; that second part is my suggestion, not documented advice.

6. Network, disk cache and invalidation

Disk cache. An LRU over files with a hard size cap (a fixed byte limit or a percent of free space). Evict oldest-used first. Write to a temp file and rename on success so a killed process never leaves a corrupt entry. All disk work runs off the main thread; the Android docs say disk operations should never run on the UI thread.

HTTP semantics. Do not invent your own expiry when the server already speaks HTTP:

  • Honor Cache-Control: max-age and Expires to decide whether to skip the network.
  • When stale, send a conditional request with If-None-Match (from ETag) or If-Modified-Since. A 304 Not Modified reuses the bytes at the cost of one small round trip.
  • Coil 3 does not respect Cache-Control by default and always saves responses to its disk cache. You opt in with the coil-network-cache-control artifact, and networking itself comes from a separate artifact such as coil-network-okhttp (Coil network docs). That tells you it is a policy decision, not a default everyone wants.
  • Signed or authenticated URLs break the key rule. If the URL carries an expiring token in its query string, the same image gets a new key on every refresh. Key on the stable part of the URL plus a version, keep the token out of the key, and never share cache entries across users: private images need a per-user namespace, and logout must clear them (my design advice, not a library guarantee).
  • Where the CDN serves content-hashed URLs with a long max-age, the URL change is the invalidation mechanism, and the client should do nothing clever.

Explicit invalidation. Expose invalidate(key) and clear() for logout and "profile photo changed" flows. Prefer a signature or version in the key over deleting files.

Network policy. Bounded parallelism per host, retries with backoff for transient errors only, no retry for 404. Skip prefetch on cellular or data saver. Use priorities so visible loads beat prefetch.

Threading model in one line: main thread for memory lookups and delivery, an IO dispatcher for disk and network, a bounded compute dispatcher for decode and transform.

7. Placeholders, animated formats, errors and metrics

  • Placeholder, then image. Show the placeholder immediately on bind. A memory hit should skip the placeholder and the fade.
  • Crossfade only for async loads. Fading in cache hits looks like flicker in a scrolling list. Coil exposes this as crossfade(true) on the request.
  • Progressive loading. Show a low-resolution or blurred preview (a thumbnail URL or a BlurHash-style placeholder) while the full image downloads; progressive JPEGs let the decoder render partial data. Treat both as optional.
  • Animated formats (GIF, animated WebP, APNG). Decode frame by frame into a drawable, never into a list of full bitmaps, and pause when off-screen. In Coil these decoders are in a separate optional artifact (coil-gif), which fits a good library design: keep heavy features out of the core.
  • Errors. Return a typed result (success with source MEMORY, DISK, NETWORK; or error with cause). Show the error image, allow tap to retry, and never crash on a corrupt file. Cache negative results briefly to avoid hammering a 404.
  • Metrics. Memory and disk hit rate, time to first pixel, bytes downloaded, decode time, cancellation rate, and OOM count. Expose an event listener on the loader so the host app can forward them.
  • Testability. Make the loader injectable behind an interface, inject dispatchers and a clock, and put the network behind a fake fetcher. Test coalescing with two concurrent requests and one fetch, cancellation with a suspended fetcher, and eviction with a tiny cache.

9. How to build an image loader on iOS (Swift)

The design is the same: cache by (source, size, transforms), coalesce in-flight work, cancel on reuse, downsample on decode. Only the primitives change.

ConcernAndroidiOS
Memory cacheLruCache (byte-sized)NSCache with totalCostLimit
Disk / HTTP cacheOwn LRU or OkHttp cacheURLCache, or your own file cache
DownsampleinSampleSize / ImageDecoderImageIO CGImageSourceCreateThumbnailAtIndex
Memory signalonTrimMemorydidReceiveMemoryWarningNotification
CancellationDisposable / coroutine JobTask cancellation, prepareForReuse
PoolBitmapPool / inBitmapNone; rely on ImageIO and system decoding
LibrariesCoil, GlideNuke, Kingfisher

What is genuinely different:

  • Downsample with ImageIO, not UIImage. CGImageSourceCreateThumbnailAtIndex with kCGImageSourceThumbnailMaxPixelSize produces a reduced image without building the full-size bitmap first. Without a max pixel size the thumbnail can be as big as the image. Set kCGImageSourceCreateThumbnailFromImageAlways to true, and add kCGImageSourceShouldCacheImmediately so the decode happens on your background queue and not on first draw. Apple documents that flag for other calls, so this part is common practice, not a promise; add kCGImageSourceCreateThumbnailWithTransform to apply EXIF orientation. Size in pixels, not points: multiply by the screen scale.
  • Memory signals are coarser. UIKit posts didReceiveMemoryWarningNotification and calls didReceiveMemoryWarning(). Apple's page for the notification says it has no userInfo dictionary, so it carries no level and I treat it as a single signal: drop most of the cache on warning and when entering the background. A dispatch memory-pressure source can shed earlier; I haven't checked its iOS availability, so verify it before relying on it.
  • NSCache evicts for you, but Apple says the cost limit is not strict: an object may be evicted instantly, later, or never. Its default is 0 (no limit), so set one, and still clear on memory warning.
  • URLCache gives you HTTP caching (including conditional requests) with a configured memory and disk capacity. Default sessions use the shared cache and background sessions default to nil, so a simple iOS loader can lean on it for the encoded bytes and only cache decoded images itself.
  • Reuse. In UICollectionView cells, cancel in prepareForReuse and check the request token before assigning.
// Sketch: memory cache + coalescing in one actor. Not production code.
// Swift 6 needs an SDK where UIImage is Sendable; otherwise wrap it in a Sendable box.
struct CacheKey: Hashable {
    let url: URL; let pixelSize: Int; let transforms: [String]
    var nsKey: NSString { "\(url.absoluteString)|\(pixelSize)|\(transforms.joined(separator: ","))" as NSString }  // stable, unlike hashValue
}

actor ImagePipeline {
    private let memory = NSCache<NSString, UIImage>()
    private var inFlight: [CacheKey: Task<UIImage, Error>] = [:]
    private var waiters: [CacheKey: Set<UUID>] = [:]       // one id per caller, so leaving twice is harmless

    func image(for key: CacheKey) async throws -> UIImage {
        if let hit = memory.object(forKey: key.nsKey) { return hit }
        let me = UUID()
        let task = inFlight[key] ?? Task.detached { try await Self.fetchAndDownsample(key) }
        inFlight[key] = task
        waiters[key, default: []].insert(me)
        defer { leave(key, me) }                           // normal return or error
        let image = try await withTaskCancellationHandler {
            try await task.value
        } onCancel: {
            Task { await self.leave(key, me) }             // caller cancelled: release now, not when the fetch ends
        }
        memory.setObject(image, forKey: key.nsKey, cost: image.cgImage.map { $0.bytesPerRow * $0.height } ?? 0)
        return image
    }

    private func leave(_ key: CacheKey, _ id: UUID) {
        guard waiters[key]?.remove(id) != nil else { return }
        if waiters[key]?.isEmpty == true {                 // last waiter left: cancel the shared fetch
            waiters[key] = nil
            inFlight.removeValue(forKey: key)?.cancel()
        }
    }
}

The actor replaces the lock from the Kotlin version: its isolation serializes access to inFlight and waiters. Actors are reentrant, so the code never assumes inFlight or waiters are unchanged across the await. Awaiting task.value alone would not release a cancelled caller until the fetch ended, so the await sits inside withTaskCancellationHandler, which removes that caller's id at once and cancels the fetch only when the last id is gone. The sketch keys the size as one pixelSize, where the Kotlin key has width and height.

11. More practice prompts

  1. The server changes an image at the same URL. What happens? (Signature or versioned URL; otherwise ETag revalidation; explicit invalidate.)
  2. How do you test and measure it? (Fake fetcher and dispatchers; hit rate, time to first pixel, bytes, cancel rate, OOM rate.)
  3. A product manager wants blur-up placeholders for every image. What does it cost? (A second small request or an embedded hash per image, extra decode work, and a cache entry per placeholder.)

These are practice prompts; I'm not claiming any company asks them.
