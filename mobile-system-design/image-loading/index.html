Design an image loading library (Android and iOS): caches, decoding and cancellation

Build it. The schema, API, code and platform limits for an image loading library are on their own page: Build it: an image loading library on Android and iOS (18 min read).

How to read this. This page is the 45 minutes, in the order I would spend them. Code, HTTP caching and the Swift version are in the build guide. I would not draw them unless asked. The pushes below are my reconstruction of challenges public prep material reports (offline, retries, stale data, battery, rollout), not transcripts of real rounds.

TL;DR. A loader spends memory only on pixels the screen shows. I key every cache by source, target size and transforms, never by URL alone. Identical requests share one download (coalescing), cancelled when its last waiter leaves. I downsample (decode smaller than the file) while decoding. The target decides whether a late result is still wanted. In practice I would adopt Coil or Glide behind a thin wrapper.

1. Scope and constraints (minutes 0 to 4)

In short: Narrow scope, four phone behaviors, everything else parked.

A prompt I would expect: "Design an image loading library for our apps. Other teams will use it to show pictures in lists." I ask five things, with my default:

  • Library or one app's loader? A library other teams adopt.
  • Sources? HTTPS URLs.
  • Bound to views? Yes, one call per ImageView or Compose image.
  • Formats? JPEG, PNG and WebP.
  • Offline? Images seen before still render.

Your call. The scope push I would expect: "Animated images, signed URLs and feed prefetch too." Which do you keep?

First instinct, and why it breaks. Say yes to all three. Then the clock runs out on frame decoding, token handling and prefetch scheduling. The key and the decode never reach the board.

What I'd say. None yet. Each changes the core: decode, the cache key, who starts requests. I reject taking them on silently. Each is parked and returns as a follow-up.

Say it. "Static images over HTTPS, two cache tiers, sized decode, cancellation. Animated formats, signed URLs and feed prefetch are parked. Tell me if you want one earlier."

The push I would expect:

"The feed team needs prefetch next quarter."

I build the core first. Prefetch returns as follow-up 3.

2. Data and contracts (minutes 4 to 14)

In short: Key by source, size and transforms, so one URL never serves the wrong pixels.

Your call. What identifies a cached image: the URL, the URL plus a version, or everything that changes the output pixels?

First instinct, and why it breaks. Key by URL. It breaks when one URL is shown at two sizes.

  • A 100 px thumbnail is cached. Then the hero asks for that URL and gets a blurry upscale.
  • Or a small slot holds a huge bitmap.
  • A rounded and a plain version collide the same way.

What I'd say. The memory key is source, width, height and transforms. Glide's caching page lists the same ingredients: model, size, transformation, options and an optional signature (Glide: caching).

The disk cache may key more loosely. It stores original bytes and re-decodes per size, trading CPU for disk. I reject URL alone.

The push I would expect:

"The server replaces an avatar at the same URL."

The cache serves stale pixels until eviction. I want a content hash in the URL or a signature in the key, not file deletion.

  • With hashed URLs, the URL change is the invalidation.

The contract fits in four lines on the board:

  • A request is an immutable value object: source, size, transforms, placeholder, error, target.
  • enqueue returns a handle; cancel() on recycle (sketch).
  • execute suspends and returns a typed result, for callers without a view and for tests.
  • trimMemory(level): the host forwards system memory signals and owns the budget.

Arithmetic only where it changes a choice. Every input is my assumption:

AssumptionArithmeticWhat it settles
A 2048x1536 image at 4 bytes a pixel2048 x 1536 x 4 is about 12 MB; at a sample size of 4 it is 512 x 384 x 4, about 0.75 MBDecode to the target size, never the file size
A 32 MB memory cache, 360 px square thumbnails, 1080x810 heroesA thumbnail is about 0.5 MB, so about 64 fit; a hero is about 3.5 MB, so about 9 fitBound the cache by bytes, not entries

3. Client structure (minutes 14 to 22)

In short: One app-wide injected loader owns both caches and the shared downloads.

Your call. Who owns the loading work and the caches: each screen or its ViewModel (state holder), one loader per feature, or one injected loader for the whole app?

First instinct, and why it breaks. The screen owns it: each fragment or ViewModel launches its own loads. But the data layer guide says work tied to a screen is canceled when the user leaves it (data layer). So a download dies with the screen, even when the next screen wants the same image.

What I'd say. One injected loader, living as long as the app. It owns both caches and the scope that runs shared downloads. A request's lifetime belongs to its target, which cancels it on detach.

ViewModels only expose URLs. The UI layer calls enqueue, as the UI layer page advises for logic involving Context. I reject a loader per feature, and a service, since nothing here runs without a screen.

The push I would expect:

"Screen A leaves while screen B wants the same image."

The download runs in the injected scope, as the data layer guide shows for work that outlives the screen. It stops when its last waiter leaves.

The loader sits at the edge of the UI layer, with its own network and disk code as data sources. That placement is my inference from the UI layer and data layer pages. Two rules:

  • The host owns lifecycle and memory budget; the library takes both as inputs.
  • Callers depend on an interface, so tests swap in a fake fetcher.

4. Make the hard part work (minutes 22 to 40)

In short: Cancel stale requests, share identical downloads, decode only what the slot needs.

4.1 Recycling and coalescing (minutes 22 to 33)

Your call. Row 3 asked for an image, the user scrolled, and the view now shows row 40. Row 3's response arrives. What happens to it?

First instinct, and why it breaks. The callback captured the view, so it sets the bitmap on that view. But the view was rebound, so row 40 shows row 3's picture. Cancelling nothing is worse. A fling downloads and decodes images for rows no one will see.

What I'd say. A target holds one current request, so a rebind or a recycle cancels the old one. I reject throwing away a late result. The bytes are already paid for, so it skips the view but goes into the cache.

Say it. "Each target holds its current request. A finished request delivers only if it is still current; otherwise the bitmap goes into the cache. Identical requests share one in-flight job, keyed like the cache, cancelled when its last waiter leaves."

The push I would expect:

"Twenty rows ask for the same avatar, and one scrolls away."

One download and one decode serve all twenty. The job counts waiters (the callers still waiting on it), so cancelling one row leaves the other nineteen loading.

  • A failed fetch fails only the callers on that key.
  • The code is in the build guide.
  • I found no Coil or Glide page confirming in-flight coalescing, so this is my design.

If I am cut off mid-answer, I answer first, then say where I was:

Say it. "Yes, a late result still goes into the cache, so scrolling back costs nothing. Back to where I was: twenty rows asking for one avatar share one download, and I was about to say what happens when one scrolls away."

4.2 Decode and memory (minutes 33 to 40)

Your call. A 4000 by 3000 photo must fit a 360 px slot. Decode and scale, or sample while decoding? And what happens when the system wants memory back?

First instinct, and why it breaks. Decode the full image, then scale it down. A decoded bitmap costs width times height times bytes per pixel, whatever the file size. A fast scroll runs several decodes at once. Section 2: eight full decodes pass the whole cache.

What I'd say. Sample while decoding (decode at a half, quarter or eighth of the size), and bound the cache in bytes. I reject decode-then-scale. I also reject weak or soft references for the cache; the cache bitmaps guide advises against them.

Reading the bounds before decoding is the pattern in load large bitmaps.

Say it. "I read the bounds first, then decode at a power-of-two sample size, off the main thread, with a cap on parallel decodes. The cache is sized in bytes. On a trim signal I evict everything once the app is a background candidate, and halve the cache when the UI is hidden."

The push I would expect:

"What does the host forward on a memory signal?"

Only two trim levels are not deprecated: background candidate and UI hidden. Apps are not notified of the other five since API 34 (AOSP source).

  • "And Android 17?" It adds app memory limits based on total device RAM.
  • An affected session reports REASON_OTHER with MemoryLimiter:AnonSwap in the description (behavior changes).
  • My suggestion, not documented advice: log that reason beside the out-of-memory metric.

4.3 Where iOS changes the design

Same pipeline. The Swift sketch is in the build guide.

  • The downsample goes through ImageIO (Apple's image decoding framework) with a maximum pixel size, not through UIImage. The full-size bitmap is never built. Size in pixels, not points.
  • The memory signal is one warning with no level attached. NSCache's cost limit is not strict, so I set one and still clear on warning.
  • Reuse means cancelling in prepareForReuse (the hook that runs when a cell is reused) and checking the request token before assigning.

In short: Name the failures, ship behind a flag, keep the old loader until proven.

Release reality:

  • A Play staged rollout (release to a growing share of users) can be halted. That stops new users receiving the build, but users who already have it keep it (Play help).
  • A new loader ships behind a remote flag. That is my kill switch (a setting that turns the new loader off) and the only rollback that reaches installed apps. The old loader stays in the binary during the migration.
  • A new on-disk cache format cannot be flagged off once files are rewritten. My rule: version the cache folder and rebuild from the network instead of migrating.

Say it. "I can't recall a bad build, so the rollback is the flag plus a fixed build. I'd watch time to first pixel, hit rates, peak bitmap memory and out-of-memory kills. Left out: animated formats, signed URLs, feed prefetch."

6. Follow-ups that change a constraint

In short: Six practice prompts, hardest last.

Practice prompts, not a claim about what any interviewer asks. Each changes a constraint, and they get harder.

  1. A fling through ten thousand images in a few seconds. Strong: cancel everything scrolled past, cap parallel decodes and downloads, give visible loads priority, let the byte-bounded cache evict. Weak: "a bigger cache."
  2. Add animated GIF and WebP. Strong: decode frame by frame into a drawable, never a list of full bitmaps. Pause off screen. Ship it as an optional module. Weak: decoding every frame up front.
  3. The feed wants to prefetch. Strong: prefetch is a request with no target and lower priority than visible loads. Skip it on cellular or data saver, and cancel it when scrolled past. See the news feed case. Weak: prefetching fifty images unconditionally.
  4. Image URLs carry an expiring signature, and some images are private. Strong: key on the stable part of the URL plus a version, and keep the token out. Namespace private images per user and clear them on logout. This is my advice, not a library guarantee. Weak: the full URL as the key, shared across accounts.
  5. After release, out-of-memory kills rise for a slice of users. Strong: flip the flag to the old loader, halt the staged rollout, compare peak bitmap memory against the control group, ship a fix. Weak: "roll back the release."
  6. The CDN changes its resize parameter. Strong: old versions stay in the field, so the CDN answers both shapes. Weak: assuming everyone updates.

7. What changes by level

In short: Staff adds build versus adopt and a rollout plan.

These levels are my own reading of the bar, drawn from vendor and prep material (courses and books), not any company's rubric. The wording below is mine.

  • Mid-level: two cache tiers, background decode, placeholder and error image, cancelling loads for recycled views. I want to hear: "A late result must not land on a reused row."
  • Senior: keys with size and transforms, coalescing with waiter counting, downsampling, trim handling, bounded concurrency. I want to hear: "The key changes whenever the output pixels would."
  • Staff: the library as a product: stable API, per-surface budgets, metrics, flags, build versus adopt, a migration plan (staff guide).

As I read it, levels differ in who raises the problem: the interviewer at mid, the candidate at senior, and at staff the candidate with a rollout plan.

Common weak answers. Ten minutes on CDN architecture when the question was about the phone. A happy path only. Naming Glide or Coil without saying what breaks otherwise. A cache keyed by URL only. No kill switch. These repeat across public prep material; they are not a dataset.

Staff answer: the decision and the rollout

Decision: adopt, do not build. Use Coil or Glide on Android and Nuke or Kingfisher on iOS, behind a thin internal wrapper that owns cache budgets, key rules and metrics.

The READMEs list these features, and none explain how they work:

  • Coil: downsampling and automatic cancellation.
  • Nuke: caches plus request coalescing.
  • Kingfisher: a hybrid cache and cancelable downloads.

Alternative: write our own, and own every edge case on this page.

Revisit trigger: a measured need the wrapper cannot express, such as a custom key rule, or a surface where the library's cost shows up in profiles. For the build-versus-adopt pattern, see the native vs cross-platform decision guide.

Rollout: ship the wrapper first. Move surfaces one team at a time behind the section 5 flag. Keep the old path until a surface has run clean for a full release cycle.

Guardrail: crash-free rate and out-of-memory kills must not move against the control group.

Opinion vs verified: the library descriptions were read from the project READMEs. The migration order, metrics, guardrails and level signals are my opinion.
