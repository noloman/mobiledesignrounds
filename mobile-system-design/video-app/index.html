Design a video streaming app (Android and iOS): adaptive streaming, preload and offline

TL;DR. Stream adaptive formats (HLS or DASH) and let the player pick the bitrate; your job is to constrain it, not replace it. Own one player outside the UI lifecycle so rotation, picture-in-picture and background audio do not restart playback. Spend bandwidth deliberately: preload only a few seconds of the next video, cap the disk cache, and drop quality on cellular or data saver. Measure time to first frame and rebuffer ratio, because those two numbers tell you whether any of this works.

1. Clarify the requirements (about 5 min)

Questions worth asking:

  • Short feed videos, long-form, or both? (Assume both: an autoplaying feed and a watch screen.)
  • Live or on demand only? (Assume on demand; live is a follow-up.)
  • Offline downloads? (Yes, with DRM-protected content.)
  • Resume across devices? (Yes.)
  • Background audio and picture-in-picture? (Yes for long-form.)

Non-functional (the mobile part):

ConcernTarget
StartupFast time to first frame; first frame from a preloaded next video is near instant. I'd agree a number with the interviewer, for example under 2 seconds on Wi-Fi (example value)
SmoothnessRebuffer ratio (stall time divided by watch time) under 1 percent of watch time (example value)
DataRespect cellular limits and data saver; no wasted prefetch

ConsistencySame resume position on every device, within seconds

Out of scope: recommendations, upload and transcoding, ads. Say it out loud.

2. High-level architecture (about 10 min)

Two rules drive the design. The player is not owned by a screen: a player tied to an Activity restarts the video on rotation or backgrounding. Metadata and playback are separate paths: the feed API returns small JSON; the heavy bytes come from the CDN through the player.

Mapping to Android's architecture guidance: Compose screens plus ViewModels form the UI layer and VideoRepository with Room and REST data sources forms the data layer, with ViewModels never touching data sources. The architecture guide does not mention the Player; Media3 puts the Player and MediaSession in a MediaSessionService, and the UI only holds a MediaController. See architecture recommendations and background playback.

The watch ViewModel exposes one immutable uiState StateFlow (WhileSubscribed(5_000)), collected with collectAsStateWithLifecycle. It holds no Context, so the UI builds the MediaController.

3. Data model and API

Local schema (Room sketch)

@Entity(tableName = "videos")
data class VideoEntity(
    @PrimaryKey val id: String,
    val title: String,
    val thumbnailUrl: String,
    val durationMs: Long,
    val manifestUrl: String?,          // fetched lazily
)

@Entity(tableName = "playback_progress")
data class ProgressEntity(
    @PrimaryKey val videoId: String,
    val positionMs: Long,
    val updatedAt: Long,               // server-stamped on every successful PUT
    val dirty: Boolean,                // changed locally, not yet uploaded
)

Downloads are tracked separately (state, bytes, license expiry). The repository maps entities to immutable models, with Flow for observed data.

REST

GET /v1/feed?cursor=<opaque>&limit=10&fields=id,title,channel.name,thumb,durationMs
GET /v1/videos/{id}/playback   → { manifestUrl, drm: {type, licenseUrl}?, resumeMs }
PUT /v1/videos/{id}/progress   → { positionMs, deviceId }   // server stamps updatedAt

Three details that matter:

  • Field selection on the feed. A feed row needs a thumbnail, title, channel and duration. It does not need descriptions, full channel objects, caption lists or manifest URLs. Let the client name the fields (fields=, or a GraphQL selection) so each client asks only for what it renders, and a list of ten items stays small. Feed paging works the way it does in the news feed case.
  • Manifest on demand. Fetch /playback when a video is about to play or be preloaded, not for every row. Signed URLs expire, so fetching late avoids stale links.
  • Progress as a PUT of an absolute position. It is idempotent, so retries are safe. The server stamps updatedAt; I don't send a client time, because device clocks can't be trusted. Section 8 covers the conflict rule.

4. Adaptive streaming and the player (the core of the problem)

HLS and DASH

Both split a video into short segments at several bitrates and describe them in a manifest. HLS uses an .m3u8 playlist; DASH uses an .mpd. Apple documents HLS as supporting multiple alternate streams at different bit rates and switching in response to network bandwidth changes. Media3 plays both once you add the format module (media3-exoplayer-hls, and media3-exoplayer-dash for DASH). Then MediaItem.fromUri(uri) is enough when the URI ends in .m3u8 or .mpd, and for a multivariant HLS playlist the player adapts between variants based on bandwidth and device capabilities. If an HLS URI has no .m3u8 ending, the HLS page says to pass MimeTypes.APPLICATION_M3U8 as the MIME type. On iOS, AVPlayer plays HLS and progressive files, and Apple documents no DASH support, so a cross-platform catalog usually ships HLS and adds DASH only if it needs to.

Startup time versus quality. A low first bitrate gives a fast but blurry start; a high one risks a stall. Do not write your own selection algorithm. Tune the inputs: a small lowest rung, short segments, and quality caps by network type (section 6).

One player, owned outside the UI

On Android, put the ExoPlayer and a MediaSession inside a MediaSessionService. Media3 documents this as the way to keep playing when the app is not in the foreground, and the UI controls the player through a MediaController. The manifest needs the FOREGROUND_SERVICE and FOREGROUND_SERVICE_MEDIA_PLAYBACK permissions, and the service declares foregroundServiceType="mediaPlayback" plus the androidx.media3.session.MediaSessionService intent filter (background playback guide). Leave any of that out and the service fails when it tries to go foreground.

Android 17 tightens this. The Android 17 behavior changes say audio playback and volume APIs fail silently, and audio focus requests return AUDIOFOCUS_REQUEST_FAILED, when the app is not in a valid lifecycle. For apps targeting API 37 the foreground service must also have while-in-use capabilities. In practice I'd start playback from a user action and test on an Android 17 device, since I only read the docs for this.

// Sketch: player owned by a service, backed by a size-capped cache
// Pattern from the Media3 background playback guide (Apache 2.0), with a cache factory added
class PlaybackService : MediaSessionService() {
    private var session: MediaSession? = null

    override fun onCreate() {
        super.onCreate()
        val cacheFactory = CacheDataSource.Factory()
            .setCache(VideoCache.get(this))                       // app-defined singleton SimpleCache
            .setUpstreamDataSourceFactory(DefaultHttpDataSource.Factory())
        val player = ExoPlayer.Builder(this)
            .setMediaSourceFactory(DefaultMediaSourceFactory(this).setDataSourceFactory(cacheFactory))
            .build()
        player.setAudioAttributes(
            AudioAttributes.Builder()
                .setUsage(C.USAGE_MEDIA)
                .setContentType(C.AUDIO_CONTENT_TYPE_MOVIE)
                .build(),
            /* handleAudioFocus= */ true,
        )
        session = MediaSession.Builder(this, player).build()
    }

    override fun onGetSession(controllerInfo: MediaSession.ControllerInfo): MediaSession? = session

    override fun onDestroy() {
        session?.run { player.release(); release() }
        session = null
        super.onDestroy()
    }
}

By default the service keeps running if playback is ongoing when the user swipes the app away. The docs show overriding onTaskRemoved with pauseAllPlayersAndStopSelf() if you want it to stop instead; the sketch above doesn't.

Points to say out loud:

  • Rotation. A new Activity reconnects a MediaController and re-attaches its surface; the player and its buffer are untouched.
  • Picture-in-picture. Android PiP needs API 26. Declare supportsPictureInPicture on the activity (the PiP guide also asks for android:configChanges so the activity doesn't relaunch on the transition), and on API 31 and above call setAutoEnterEnabled(true) in PictureInPictureParams so swiping home enters PiP without code in onUserLeaveHint. An active MediaSession supplies play and pause controls.
  • Audio focus. setAudioAttributes(attributes, true) makes ExoPlayer handle focus for you, so the app has no focus callbacks to write. Media3 guidance is to set attributes that describe your content.

Disk cache for segments (Android)

Media3 caches loaded bytes with a SimpleCache plus CacheDataSource.Factory. The docs show LeastRecentlyUsedCacheEvictor(maxBytes) for on-the-fly caching, so the cache evicts old segments at a size limit, and note that the StandaloneDatabaseProvider should be a singleton. Choose maxBytes from product needs and device storage. Keep downloads in a separate cache with NoOpCacheEvictor, as the downloading docs say a download cache should not evict media.

Preloading the next video

Media3's DefaultPreloadManager preloads items by distance from the playing item, and your app decides how much of each. In the Media3 sample the next and previous items get 3 seconds loaded, the item two away only gets its tracks selected, and items three and four away just have their source prepared. Treat the numbers as starting points.

// Sketch, adapted from the Media3 preloading docs sample (Apache 2.0). The app must keep currentPlayingIndex current.
class FeedPreloadControl(var currentPlayingIndex: Int = 0) :
    TargetPreloadStatusControl<Int, DefaultPreloadManager.PreloadStatus> {

    override fun getTargetPreloadStatus(index: Int): DefaultPreloadManager.PreloadStatus =
        when (abs(index - currentPlayingIndex)) {
            1 -> DefaultPreloadManager.PreloadStatus.specifiedRangeLoaded(3000L)
            2 -> DefaultPreloadManager.PreloadStatus.PRELOAD_STATUS_TRACKS_SELECTED
            3, 4 -> DefaultPreloadManager.PreloadStatus.PRELOAD_STATUS_SOURCE_PREPARED
            else -> DefaultPreloadManager.PreloadStatus.PRELOAD_STATUS_NOT_PRELOADED
        }
}

Build the player with buildExoPlayer() on the same DefaultPreloadManager.Builder (the service sketch above uses a plain builder for brevity). DefaultLoadControl.Builder().setPlayerTargetBufferBytes("preload", ...) caps total preload memory. On cellular or data saver, return a lighter status (or not preloaded) from this control.

On iOS there is no preload manager. Prepare the next item ahead of time, either by loading the AVURLAsset keys or by inserting the item into an AVQueuePlayer behind the current one, and tune preferredForwardBufferDuration if you need to. I did not confirm in Apple's docs that an AVPlayerItem not attached to a player starts buffering, so check that before you rely on it. I found no documented public API for a persistent segment cache in AVPlayer, so expect to rely on the system's HTTP cache and on your CDN.

5. Offline downloads and DRM

Android. Media3's DownloadManager runs downloads through a DownloadService, writes to a Cache, and respects Requirements such as network type. DownloadHelper selects tracks for adaptive streams, so the user can pick a quality before downloading. Play downloads through a read-only CacheDataSource.Factory, and build the item with the download request's toMediaItem so only the downloaded tracks play. Do not read the download files directly. Downloads must outlive the process. The architecture guide would give that to WorkManager; Media3 ships its own DownloadService for it, and I'd use that.

The download service is a dataSync foreground service, and on Android 15 and later the foreground service timeout docs give those services 6 hours in a 24-hour period. After that the system calls onTimeout and the service has a few seconds to stop. A big offline library can therefore pause part-way, so downloads have to be resumable. That Media3 restarts them through its scheduler (WorkManagerScheduler or PlatformScheduler) when the budget refreshes is my reading of the docs, not something I tested. Start downloads from a user action while the app is visible.

iOS. AVAssetDownloadURLSession needs a background configuration, so downloads continue while the app is suspended. If the user force-quits the app, the system cancels active downloads and does not relaunch it. Save the location the delegate gives you so you can rebuild the asset on the next launch; I'd persist a path relative to the home directory rather than an absolute URL, because the container path can change (unverified against current guidance). Create tasks with makeAssetDownloadTask(downloadConfiguration:), since Apple marks the older asset and destination creators as deprecated. Apple also says you can only start a non-discretionary download while the app is in the foreground, so reserve those sessions for downloads a person explicitly starts, which matches the Android advice above (AVAssetDownloadURLSession).

DRM at a high level. Widevine on Android and FairPlay on iOS keep the decryption keys in the platform, and the license server decides who can play and for how long.

  • Media3 supports Widevine with the two Common Encryption schemes: cenc from API 19 and cbcs from API 25, with DASH and with HLS in fragmented MP4. FairPlay is the iOS counterpart, driven through AVContentKeySession.
  • For offline playback, the client stores a persistent license. On Android the key set ID goes on the download request and the MediaItem.DrmConfiguration. On iOS, AVContentKeySession supports persistable keys and has APIs to get an expiration date and to invalidate keys.
  • Licenses expire. Store the expiry, show it in the downloads list, and refresh the license while online. Show a clear message for "license expired, no network", not a generic player error.

6. Buffering policy, network switching and data limits

  • Bandwidth caps. On Android, TrackSelectionParameters accepts constraints and applies them to every item in a playlist; setMaxVideoSizeSd() is the documented example. By default ExoPlayer limits video resolution to the display size. On iOS, AVPlayerItem has preferredPeakBitRate and a separate preferredPeakBitRateForExpensiveNetworks, plus resolution equivalents, so you can cap expensive networks (cellular, and Wi-Fi hotspots) without custom network code. That property only reacts to expensive paths. Android's data saver is closer to iOS Low Data Mode, which I did not verify in Apple's docs; feed whatever signal you use into the dataSaver flag below.
  • Data saver. Lower the cap, stop preloading, and stop feed autoplay.
  • Buffer size. More buffer protects against stalls but wastes data if the user leaves. ExoPlayer exposes a LoadControl for buffering policy. On iOS, preferredForwardBufferDuration sets how far ahead the player buffers, and automaticallyWaitsToMinimizeStalling (on by default) delays playback when a stall looks likely.
  • Network switches. Rely on the player's retry and bitrate adaptation, show a spinner only after a short delay, and never recreate the player on a connectivity change.
// Sketch: one long-lived player; per-item limits for data saver
@MainActor final class PlaybackController {
    let player = AVPlayer()

    func configureSession() {
        // Playback category; background audio also needs the Audio, AirPlay, and Picture in Picture background mode.
        try? AVAudioSession.sharedInstance().setCategory(.playback, mode: .moviePlayback)
    }

    func play(_ url: URL, dataSaver: Bool) {
        let item = AVPlayerItem(url: url)
        if dataSaver {
            item.preferredPeakBitRateForExpensiveNetworks = 1_500_000   // example value
            item.preferredForwardBufferDuration = 5                     // seconds, example value
        }
        player.replaceCurrentItem(with: item)
        try? AVAudioSession.sharedInstance().setActive(true)
        player.play()
    }

    func startupSeconds() -> Double? {
        // Apple: startupTime is negative when unknown
        player.currentItem?.accessLog()?.events.last.flatMap { $0.startupTime >= 0 ? $0.startupTime : nil }
    }
}

Apple suggests deferring session activation until playback begins. Handle AVAudioSession.interruptionNotification to pause and resume, which is the iOS counterpart of the audio focus callbacks (not verified here). For PiP, AVPlayerViewController has allowsPictureInPicturePlayback and canStartPictureInPictureAutomaticallyFromInline.

7. Autoplay in the feed

Autoplay the most visible item only. Compute visible fraction per row, pick the row with the largest fraction above a threshold (for example 60 percent, an example value), and move one player to it. Start muted, and pause when the row leaves or the app backgrounds.

The costs are real. Each active decoder costs hardware and battery, so run one at a time. Autoplay spends data, so gate it on Wi-Fi or a setting. Reuse one player and swap the media item, and use the preload control to hide swap latency. Show the thumbnail until the first frame renders, or the row flashes black. Thumbnails need the same cancel-when-scrolled-past discipline as in image loading.

8. Resume and cross-device sync

Save the position on pause, on leaving the screen, and every 30 seconds or so while playing (example interval). Write locally first and mark the row dirty (a lazy write in offline-first terms), via an injected app-scoped CoroutineScope. Upload with work that must survive process death (a WorkManager job on Android; a persisted queue drained on foreground and reachability changes on iOS, the same pattern as the outbox in the chat app, section 4).

On open, the server returns resumeMs. If a local row is still dirty, the local position wins, because it is the most recent thing the user did on this device. Otherwise I take the server's resumeMs. Across devices the server decides the order: it stamps updatedAt on every successful PUT and the newest stamp wins. I don't compare device clocks (see the offline-first guide on why). A position within the last few seconds counts as finished.

9. Analytics and QoE

MetricMeaning
Time to first frameFrom play intent to first rendered frame. The main startup metric
Rebuffer ratioStall time divided by watch time; also count stalls per hour
Average and switched bitrateHow often and how far the player changed quality
Playback failure rateErrors per session, split by cause (network, DRM, decode)

On iOS, AVPlayerItemAccessLogEvent exposes startupTime, numberOfStalls, observedBitrate, indicatedBitrate and switchBitrate. On Android, collect the equivalent from player listeners and analytics callbacks. Queue and batch events (a queued write, drained by WorkManager; the analytics SDK case, section 5, designs exactly that) and slice by network type, device class and CDN, since averages hide problem cohorts.

12. What changes by level

  • Mid-level: play HLS with ExoPlayer or AVPlayer, a lifecycle-safe player holder, save the resume position, handle errors.
  • Senior: service-owned player, PiP and audio focus, bounded segment cache, preload of the next item with data-aware limits, cellular bitrate caps, offline downloads with license expiry, field-selected feed API, QoE metrics.
  • Staff: multi-CDN failover, per-cohort tuning of startup rung and buffers from QoE data, experiments on preload depth, a cost model (CDN bytes versus engagement), a shared playback module across apps, and DRM license policy with the backend.

This split into levels is my own reading, not a published rubric. The staff loop guide explains how I think about it.

Staff answer: the decision and the rollout

Decision: move every app onto one shared playback module (player, cache, DRM and QoE reporting) rather than letting each app wire up its own player. Alternative: each app owns its player, which is faster to start and drifts apart over time. Revisit trigger: if one app needs behavior the module can't express without a fork, or the module's release cadence blocks a team for more than a cycle, split it.

What to measure: time to first frame and rebuffer ratio, compared between the old and new player on matched cohorts (same network type and device class). Guardrail: crash-free sessions and playback failure rate must not get worse than the old player; a startup win that raises crashes is not a win.

Rollback on mobile: keep the old player in the binary behind a remote flag, so reverting is a config change for installed versions. If the new player crashes at launch, a flag cannot help, so the fix is a new build, and a Play staged or App Store phased rollout can be paused but not undone on devices that already have it. Offline downloads and DRM licenses tie users to the player that created them, so the flag needs a migration story before you flip it back.

Opinion versus verified: the decision, trigger and guardrails are my judgment. The platform facts are the ones cited in sections 4 to 6, and the cross-app tradeoff is covered in the native versus cross-platform guide.

13. Follow-up questions worth practising

These are questions I'd rehearse, not a claim about what any interviewer will ask.

  1. How would you add live streaming? (Live-edge latency, shorter segments, no long preload.)
  2. How do you cut startup time? (Preload, low first rung, short segments, fewer round trips before the manifest.)
  3. How do you keep data costs down for users? (Quality caps, no preload on cellular, data saver, downloads on Wi-Fi.)
  4. How do you roll out a player change safely? (Feature flag, compare QoE between cohorts.)
  5. A viewer reports the wrong subtitle language on every second video. Where do you look? (Track selection with preferred languages, and whether the choice is persisted per video or per user.)
  6. The user scrubs a long way. What happens to preloading and to time to first frame? (Cancel the preload for the old position and keep the policy tied to the current item; seek preview thumbnails are a separate asset I'd fetch lazily. This is my reasoning, not from the docs.)
  7. A signed manifest URL expires mid-session, or one CDN degrades. What do you do? (Re-fetch /playback and re-prepare at the current position; failover means the backend returns more than one host and the client falls back on repeated failures. Design opinion, not documented.)
  8. How would the same decisions change for a feed of short vertical videos? (See news feed for the paging side; preload depth gets smaller.)
