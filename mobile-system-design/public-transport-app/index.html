TL;DR. My answer: the hard part is not the timetable download. It is telling the user, on every row, how much the app knows. The timetable is one file that the app swaps whole. Realtime data is a short layer on top, and it shows its age. The server decides which disruption is worth a push.

1. Scope and constraints (minutes 0 to 4)

In short: Promise stops, scheduled departures and saved routes offline. Keep trip planning on the server.

A prompt I would expect: "Design an app that shows when my bus leaves, even with no signal." I ask five questions, with a default for each:

  • One city or many? One city, one agency feed.
  • Trip planning? Yes, on the server.
  • Realtime data? Usually, so the app must work without it.
  • Offline? Nearby stops, scheduled departures, saved routes.
  • Location? Not required.

The phone is not one box. It does four things to this design:

Your decision. What do you promise a user with no signal? "Plan any trip", or "the next departures for stops and routes you know"?

First idea, and why it fails. Promise full planning offline, because the tunnel is the main use. It fails on cost. The phone needs a route engine and a bigger timetable file.

What I would say.

Say this. "Offline means the stops and routes you already know. Trip planning stays on the server. Tickets, walking directions and rider reports are out. A live map, a widget and many cities wait until you ask."

The follow-up question I expect:

"Some apps plan trips on the phone."

That is a valid later step. I would want a measure first.

2. Data and contracts (minutes 4 to 14)

In short: The server builds one timetable file. The app swaps it whole. Realtime data stays in memory with its age.

Your decision. Where does the timetable live? Does the phone parse the agency zip, ask the server for every query, or download one compiled file?

First idea, and why it fails. Download the GTFS zip and read it into the app. GTFS (General Transit Feed Specification) is the standard set of timetable text files. Reading a big city's stop times blocks the app. If Android stops the process midway, the database holds half a timetable.

What I would say. The server compiles one SQLite file (a database in a single file). I call it the pack. The app downloads it, checks its hash and schema version, opens it as a new file, and then moves one pointer. Saved routes live in a second database that a swap never touches. I reject patches, because the numbers below do not need them.

The follow-up question I expect:

"A new pack arrives while the user reads a board."

Readers keep the old file. The next query uses the new one.

The follow-up question I expect:

"What about a trip at 25:10?"

GTFS writes times after midnight as more than 24:00:00, on the service day that started earlier. The spec measures them from noon minus 12 hours of that day, in the agency time zone. On the day the clock changes, adding 86,400 seconds is wrong by one hour. That last point is my reasoning.

The contract has four calls:

  • Manifest: version, valid dates, schema version, hash, size.
  • Realtime slice for one stop. The raw feed covers the whole network, so the server cuts a slice.
  • Journey request, answered by the server.
  • Alerts, matched to saved routes by the server.

3 to 5 in short: what the full case covers

In short: Three more decisions follow. Here is each one, and the first idea that fails.

  • 3. Client structure (minutes 14 to 22). Who owns the timetable and its updates? The first idea is to let each screen download when it opens. That starts two downloads and can leave a temporary file with no owner.
  • 4.1 The honest row (minutes 22 to 31). What does a row say when live data is missing, late or old? The first idea is to treat a missing update as on time. In a tunnel the row would still say "2 min".
  • 4.2 Who wakes the phone (minutes 31 to 40). Does the phone watch for a disruption, or does the server tell it? The first idea is to poll in the background and follow the user with location. Android limits both.
  • 5. Break it, ship it, roll it back (minutes 40 to 45). What does the user see when a download stops, the clock is wrong or a release is bad? The first idea is to ship a fix and wait. A store lets you stop a rollout, not recall it.
