Design a hotel or ride booking app (Android and iOS): holds, payments and recovery

How to read this. Sections 1 to 7 are the platform-neutral design, with Kotlin/Android code. Section 8 shows what changes on iOS. The hotel flow is the whole design; ride hailing is a short contrast table in section 6, not a second design. The idempotency pattern in section 5 is the same one as the chat app's send path, so if it feels fast, read the chat app first.

TL;DR. My answer: money and inventory live on the server, so the client is a thin view over server-owned state. Every mutating request carries an idempotency key that is persisted before the first send. Time is server-authoritative: the client counts down from a server-computed duration on a monotonic clock, never from the device wall clock. The booking state machine only advances when the server says so, and after any interruption (3-D Secure, process death, lost response) the client asks the server what happened instead of guessing. I make booking online-only on purpose; viewing saved bookings works offline.

1. Clarify the requirements (about 5 min)

Ask before drawing anything. Good opening questions:

  • Hotels only, or rides too? (Assume hotels as the main flow, rides as a contrast.)
  • Do we hold inventory during checkout? (Yes: a short server-side hold, for example 10 minutes. The value is a product decision.)
  • Which payment methods? (Cards, Google Pay, Apple Pay, with 3-D Secure, the bank's extra check, usually a redirect or pop-up, where the issuer requires it.)
  • Can users book offline? (No. They can view saved bookings offline.)
  • Scale? (Search is read-heavy and cached on the backend; keep the focus on the client.)

Functional: search with autocomplete, browse a list and a map, hold a room, pay, see the confirmation, find the booking later, open it from a link.

Non-functional (the part that makes it a mobile question):

ConcernTarget
MoneyNever charged twice, never charged without a booking
InventoryNo double booking; the server enforces the hold
TimeCountdown correct even with a wrong device clock
SearchSuggestions feel instant; stale responses never overwrite fresh ones
OfflineSaved bookings readable; booking disabled with a clear reason
RecoveryKilling the app mid-payment never leaves the user guessing

Out of scope for now: loyalty, reviews, host tools, multi-room carts. I list them so the interviewer can pull me back if they care about one.

2. High-level architecture (about 10 min)

In Android's own terms: the Compose screen and ViewModel are the UI layer, with the ViewModel exposing one uiState. The Search, Booking and Trips repositories are the data layer, and Room and the REST client are their data sources. I skip a domain layer until two screens share logic. See the Android architecture recommendations.

Two decisions carry the design.

  1. The server owns inventory, price, time and booking state. The client keeps a view of it plus local bookkeeping: the idempotency key, an attempt id, the last known server state.
  2. Booking is online-only. Android's offline-first guide says that fits writes that must happen in near real time, and its example is a bank transfer. A queued booking could "succeed" on a room that is already gone, so offline I disable the button and say why. The read path (saved trips) is offline-first. The offline-first guide on this site puts the two side by side.

3. Data model and API

Local tables (Room)

  • booking_attempt(attemptId, idempotencyKey, offerId, holdId, status, version): written before the first network call. The recovery anchor after process death.
  • trip(bookingId, status, propertyJson, dates, voucherCode, syncedAt): confirmed bookings, readable offline.

A note on snippets: they use Room 2.x (androidx.room). Room 3 (androidx.room3, KSP only) is what the official guide now shows; the tables and the architecture are the same.

  • recent_search(query, placeId, usedAt) and result_page(queryKey, pageIndex, itemsJson, quotedAt).

REST

GET  /v1/places/suggest?q=lis
GET  /v1/offers?placeId=..&dates=..&cursor=..   → items + nextCursor (opaque), each with quoteId, price, quotedAt
GET  /v1/offers?bbox=..&dates=..                (map viewport)
POST /v1/holds     { offerId, quoteId }     Idempotency-Key → { holdId, expiresInMs, price }
POST /v1/bookings  { holdId, paymentToken } Idempotency-Key → { bookingId, state, version, nextAction? }
GET  /v1/bookings/{id}
GET  /v1/bookings?attempt=<idempotencyKey>      (recovery lookup)

Return expiresInMs, a duration computed at response time, not only an absolute timestamp. A duration is immune to the device clock.

Dates and money need the same care. A check-in date is a calendar date in the hotel's time zone, not an instant, so I send 2026-11-03 as a plain date string and never as a UTC timestamp that can slip a day in another zone. Prices travel as an integer amount in minor units plus a currency code, and the server returns the full breakdown (nightly rate, taxes, fees, total). The client formats it and never adds it up.

Server-driven state

  • Happy path: HELD, PAYMENT_REQUIRED, ACTION_REQUIRED (only when the bank asks for 3-D Secure), PROCESSING, CONFIRMED.
  • Before CONFIRMED a booking can end in EXPIRED or FAILED.
  • After CONFIRMED it can become CANCELLED.

The client mirrors this as a sealed type and never advances it on its own. Each response carries a version, a per-booking counter the server increments. I only compare it, so unlike the chat app's seq there are no gaps to detect: ignore anything not newer, and late responses cannot move the state backwards.

4. Holds and server-authoritative time

The trap is System.currentTimeMillis(): a user whose clock is 20 minutes fast sees an instantly expired hold. The server decides expiry; the client only displays it.

  1. POST /holds returns expiresInMs.
  2. Record a monotonic timestamp before sending the request and compute remaining time from it. This is conservative: latency makes the UI show slightly less time than the server grants, never more.
  3. Use a monotonic clock (SystemClock.elapsedRealtime()), which does not jump when the user changes the date.
  4. At zero, lock the pay button but re-read the hold from the server rather than declaring it dead; the server may have extended it.
  5. The pay request is still validated server-side. On EXPIRED, show "Room no longer held" with a re-check action.
// Sketch: countdown anchored to a monotonic clock
data class HoldClock(val expiresInMs: Long, val sentAtElapsed: Long) {
    fun remainingMs(now: Long = SystemClock.elapsedRealtime()): Long =
        (expiresInMs - (now - sentAtElapsed)).coerceAtLeast(0)
}

5. Idempotent booking, payment and recovery

The classic failure: the request reaches the server, the response is lost, a retry or a second tap sends it again. Without protection that is two charges.

  • Generate the key once per checkout attempt (a UUID) and write it to booking_attempt before the first send. Reuse it on every retry of that attempt.
  • Send it as Idempotency-Key. Stripe's docs describe the pattern: the client generates a unique key (V4 UUIDs suggested, up to 255 characters), the server saves the first result, and retries with the same key return it. Stripe also compares parameters with the original request and errors on a mismatch, so use a new key when the cart really changes.
  • Keys expire. Stripe says API v1 keys can be pruned once at least 24 hours old. Your backend picks its own window.
  • Double tap: the ViewModel ignores Pay while the state is Submitting. The key is the safety net, not the first defence.
  • On timeout, look before resending: GET /bookings?attempt=<key>. If a booking exists, adopt it. If not, resend with the same key.
  • Retry rule: retry network errors, 408, 429 and 5xx, honouring Retry-After when present. Any other 4xx is final, except the answers this API defines as states, such as 409 PRICE_CHANGED and SOLD_OUT, which go to the user instead of being retried.

This is the same pattern as the chat app's send path and the second mistake in the offline-first guide. The difference here is that a retry costs money, so the key is persisted before the first send, and there is no queue of pending writes behind it, only the one persisted attempt record.

// Sketch: the key comes from the persisted attempt (wrapped by a data source; not called from the ViewModel)
interface BookingApi {
    @POST("v1/bookings")
    suspend fun confirm(
        @Header("Idempotency-Key") key: String,
        @Body body: ConfirmRequest,
    ): BookingDto
}

The pay call runs in a scope the repository owns, not viewModelScope, because leaving the screen must not cancel a charge in flight. The ViewModel just waits for the result. The recovery lookup on launch could be a WorkManager job, but a plain startup call is enough here. BookingApi sits behind a remote data source and BookingRepository, so the ViewModel never calls it.

Wallets and 3-D Secure

The sheet produces a token; the client never charges anyone. That is also the card-data story: the wallet sheet or the PSP SDK collects the card, and my app and servers only handle a token. As I understand it, that keeps raw card numbers out of my systems and shrinks PCI scope, but I haven't verified the exact scope rules, so confirm them with your PSP.

  • Google Pay: the user picks a method in the sheet and Google Pay returns a token to the app, which sends it with the purchase details to your backend, which passes it to the payment provider. PaymentsClient.isReadyToPay gates the button and loadPaymentData opens the sheet.
  • Apple Pay: PKPaymentAuthorizationController presents the sheet; in didAuthorizePayment you send the token to your server and report the result.
  • 3-D Secure: in Stripe's flow the PaymentIntent moves to requires_action, and the SDK presents the challenge. A web-view fallback uses a return_url that routes back into the app (custom scheme or universal link). Stripe says 3-D Secure isn't always supported for wallet payments, so in practice cards are where you'll hit it.

The redirect result is a hint, not the truth. The user may finish the bank page and never return, or return to a fresh process. On resume or on the return link, move to Processing and ask the server for the booking state (poll with backoff, or wait for a push; push is only a hint, so I still poll once). The server learns the real outcome from provider events (Stripe lists charge.succeeded) and exposes it as booking state.

Process death mid-payment

SavedStateHandle survives system-initiated process death but not a force stop or a swipe from Recents, and it is meant for small values. Keep only the attemptId there and the rest in Room. On startup, find booking_attempt rows not in a terminal state and reconcile each with GET /bookings?attempt=<key>. After a force stop the Room row still lets this run on next launch; only the in-flight UI is lost.

6. Search, staleness, links and the ride contrast

Autocomplete. Debounce (a short delay, for example 250 ms, tuned with data), trim, drop duplicates, and cancel the previous request so a slow "lis" cannot overwrite "lisbon". Show recents from Room when the field is short, and cache suggestion responses by query. Short input skips the debounce so the recents appear at once. If the suggest call fails with an IOException (offline, say), the list goes empty instead of the error escaping into viewModelScope, where it would crash the app on a keystroke. Other exceptions still propagate, because I'd rather see a real bug than hide it.

// Sketch: debounce + cancel-previous with flatMapLatest
@OptIn(FlowPreview::class, ExperimentalCoroutinesApi::class)
class SearchViewModel(private val repo: PlaceRepository) : ViewModel() {
    private val query = MutableStateFlow("")

    val suggestions: StateFlow<List<Place>> = query
        .debounce { if (it.trim().length < 2) 0L else 250L }   // recents show at once
        .map { it.trim() }
        .distinctUntilChanged()
        .flatMapLatest { q ->
            if (q.length < 2) repo.recents()        // Flow<List<Place>> from Room
            else flow { emit(repo.suggest(q)) }     // cancelled by the next query
                .catch { if (it is IOException) emit(emptyList()) else throw it }
        }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())

    fun onQueryChanged(q: String) { query.value = q }
}

List and map. Use Paging 3 with a RemoteMediator (the news feed case walks through it): the database is the source of truth, and the mediator is the signal that cached data ran out, so it fetches the next page into Room. Include the whole query (place, dates, guests, filters) in the page key so a filter change starts a fresh list. Prefetch the next page before the end (PagingConfig.prefetchDistance). For the map, query by viewport once the camera stops, debounce, cancel the previous box request, and cluster pins on the server.

Staleness. Treat every price as a quote. Items carry quoteId and quotedAt; show "Prices may have changed" on old cached pages, refresh on pull and on foreground after a long gap, and always revalidate at checkout: POST /holds takes the quoteId, and if the price differs the server answers 409 PRICE_CHANGED with the new price. The user accepts or goes back. A SOLD_OUT returns to results with the item marked. The client never computes the final total.

Offline. Confirmed bookings sit in trip with the confirmation code and address, so the user can show them at the door. Search shows cached pages with a stale banner; hold and pay are disabled with a reason.

Deep links. A confirmation email opens https://example.com/trips/<id>. On Android, use verified App Links: an intent filter with autoVerify, plus assetlinks.json on your domain. On Android 15 and later the system re-verifies domains periodically, so allow up to a week for changes to that file to reach devices. On iOS, use universal links. Validate every parameter: Apple's guide calls universal links a potential attack vector and says to discard malformed URLs. Route by id, authenticate first if signed out, show the cached trip, then refresh from the server. Never trust state encoded in the link.

Ride hailing: what changes. I treat this as a contrast, not a second design. The skeleton (server-owned state, idempotent requests, state machine) is the same, but the constraint flips from scarce inventory to scarce supply in motion.

AspectHotelRide
ReservedA room for dates, held for minutesA driver, matched in real time
TimeoutHold expiryMatching timeout; show "no drivers", offer retry
PriceQuote, revalidated at checkoutEstimate shown before request
Live dataAlmost noneDriver location stream
PaymentAt bookingOften authorized up front, finalized after the trip
OfflineSaved bookings usefulLittle value

For live location, open a WebSocket (OkHttp, or URLSessionWebSocketTask on iOS) only while the trip screen is visible, interpolate the marker between points, and on reconnect fetch the latest trip state by id instead of replaying the stream. The ride request is idempotent like a booking, and after process death the client resumes by querying the active trip.

What changes in practice:

  • No durable retry framework is needed. Booking is online-only on both platforms, so there is no queue of pending writes, only the persisted attempt record and launch-time reconciliation.
  • Scene phase. SwiftUI's ScenePhase reports active, inactive and background. Use the return to active after the bank page to fetch booking state, and close the driver socket when leaving the foreground.
  • The Apple Pay result blocks the flow. Apple documents that the controller waits for your handler (or, in the async variant used below, for the method to return) before the next delegate method. Apple declares the delegate @MainActor, so the sketch does too. Keep the server call short (a tight timeout on confirm; the sketch doesn't set one). A definite error from the server fails the sheet. A URLError, such as a timeout, means I don't know whether the card was charged. I still fail the sheet, because I won't show a success mark for a payment I haven't confirmed. The delegate also tells the screen to move to PROCESSING, and the screen looks the booking up by the attempt key. If the card was charged, the lookup finds the booking. If not, a retry reuses the same key, so the server can't charge twice. The other option is to report success and reconcile afterwards, which looks smoother but is wrong whenever the charge failed.
// Sketch: Apple Pay delegate sending the wallet token with the persisted attempt key
@MainActor
final class PayDelegate: NSObject, PKPaymentAuthorizationControllerDelegate {
    let api: BookingAPI
    let attemptKey: String
    let onUnknownOutcome: () -> Void   // the screen moves to Processing and looks the booking up by key
    init(api: BookingAPI, attemptKey: String, onUnknownOutcome: @escaping () -> Void) {
        self.api = api; self.attemptKey = attemptKey; self.onUnknownOutcome = onUnknownOutcome
    }

    func paymentAuthorizationController(
        _ controller: PKPaymentAuthorizationController,
        didAuthorizePayment payment: PKPayment
    ) async -> PKPaymentAuthorizationResult {
        let token = payment.token.paymentData
        do {
            _ = try await api.confirm(idempotencyKey: attemptKey, walletToken: token)
            return PKPaymentAuthorizationResult(status: .success, errors: nil)
        } catch is URLError {
            // Timeout or dropped connection: the server may already have charged.
            // Fail the sheet, then look the booking up by the attempt key (a retry reuses it).
            onUnknownOutcome()
            return PKPaymentAuthorizationResult(status: .failure, errors: nil)
        } catch {
            return PKPaymentAuthorizationResult(status: .failure, errors: nil)
        }
    }

    func paymentAuthorizationControllerDidFinish(_ controller: PKPaymentAuthorizationController) {
        controller.dismiss()
    }
}

9. What changes by level

These levels are my own reading of the bar, not any company's rubric.

  • Mid-level: a working flow (search, hold, pay), error states, cached trips, and a pay button that is disabled while submitting. A mid-level answer might say: "I disable Pay while the request is in flight and show the server's error."
  • Senior: the persisted idempotency key and the lookup-before-resend, server-authoritative time with a monotonic countdown, the server-driven state machine, reconciliation after process death and 3-D Secure returns, 409 revalidation, and cancellable debounced search. I'd expect a senior to raise double taps and lost responses before anyone asks. A senior might say: "I write the key to Room before the first send, so after a crash I look the booking up instead of paying twice."
  • Staff: reconciliation across hold, payment and booking services, observability (checkout funnel, price-changed rate, unknown-outcome rate), staged rollout of payment changes behind flags, device risk signals, and a modular split (search, checkout, trips) so teams ship independently. A staff answer might say: "I'd ship the new payment path to 1 percent behind a flag and watch duplicate-charge reports, not conversion."

Staff answer: the decision and the rollout

Decision: keep a server-owned booking state machine and make the client a view of it, instead of letting the client infer outcomes from redirects and timers. The cost is more server work and a polling or push path on the client. Revisit trigger: if the unknown-outcome rate stays high after the lookup-before-resend path ships, the problem is usually in the provider events or the server's state transitions, not in the client.

What to measure: the unknown-outcome rate (attempts that end with no answer from the server and need a lookup), hold-to-pay conversion, and time to confirmation. Guardrail: duplicate-charge reports and support contacts about "charged but no booking" must not rise. A conversion win that moves that guardrail is not a win.

Rollback on mobile: a flag can switch the new path off for clients that already fetched it, but it cannot recall a binary. Old app versions keep sending an idempotency key, so the server has to accept the old request shape for as long as those versions are live. The server must never charge on a rollback path without checking the key. A store rollout can be paused, not undone on devices that installed it, so the real fix is a new build.

Opinion vs verified: the idempotency and 3-D Secure behavior comes from the Stripe docs, and the Google Pay and Apple Pay flows from their docs. The rollout plan, the metrics and the revisit trigger are my opinion. See the staff mobile loop guide for the general shape, and the native vs cross-platform guide if the question is whether to share the checkout logic across platforms.

10. Follow-up questions worth practising

  1. The user is in a tunnel when they tap Pay. What is on the screen when they get signal back? (The persisted attempt, a lookup by key, then the server's state.)
  2. How do you support modify and cancel? (Same idempotent pattern with a version precondition; refund state comes from the server.)
  3. How do you handle two devices on one account? (Server state is the truth; trips sync by version; a hold belongs to the user.)
  4. How do you test checkout? (A fake API that drops the response after success, forces PRICE_CHANGED and EXPIRED, and sends out-of-order versions; kill the process mid-attempt.)
  5. What happens after the booking? (Cancel and modify with refund state, push updates and a calendar entry. The ride contrast adds matching, a cancellation fee and surge.)
