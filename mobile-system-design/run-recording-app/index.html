Build it. The tables, location settings, distance filter code, kill recovery and platform limits are on a separate page: Build it: a run or trip recording app on Android and iOS.

How to read this. This page is the 45 minutes, in the order I would spend them. It uses a run recorder as the example, and the same design fits a hike, a ride or a trip log. The follow-up questions are my reconstruction from public prep material, not transcripts of real rounds.

By the end you can:

  • Say why the recorder cannot live in a screen, and what owns it instead.
  • Explain what you do when the app is killed in the middle of a run.
  • Say why a 10 km run can read as 13 km, and what you do about it.

Read section 4.2 twice. It is the part most answers miss.

TL;DR. My answer: the phone is a hostile place to record for an hour, so the recording must not depend on the screen or on the app staying alive. A small recorder (a foreground service on Android, a background activity session on iOS) owns the location stream. It saves every point to a local database in small batches, and the screen only reads that database. If the app is killed, the next start finds a recording that still says RECORDING and offers to resume it. I keep the raw points and work out distance later, because GPS is noisy and I want to be able to fix the maths.

Patterns in this round.

  • State machine (a recording has a short list of states)
  • Outbox (the finished run waits on the phone until it is uploaded)
  • Idempotency key (the recording id makes an upload safe to repeat)
  • Scoped owner (the recorder lives as long as the recording, not the screen)

1. Scope and constraints (minutes 0 to 4)

In short: Record one run: start, pause, stop, see the route and distance live, and save it. Sharing, route planning and offline maps wait.

A prompt I would expect: "Design an app that records a run." I ask five questions, with a default for each:

  • How long is a recording? Up to 3 hours, with the screen locked most of the time.
  • What do we show live? The route, distance, time and pace. Heart rate and a watch wait.
  • Do we have a backend? Yes. It stores finished runs for the user's account.
  • Offline? Recording works with no signal. Upload waits for the network.
  • How exact must the distance be? Close enough that a runner trusts it. I will say what that means.
In scopeOut of scopeLeft out until you ask
Start, pause, resume, stopMap tiles and map styleLive sharing with friends
Recording with the screen lockedTraining plansRoute planning
Distance, time and paceSocial feedHeart rate and a watch
Saving and uploading a finished runMaps with no networkAuto-pause

The phone does four things to this design:

The system kills the app, or the user removes permissionA run is not lostSection 4.2
GPS is noisy: bad fixes, jumps, drift when standing stillThe distance is believableSection 4.3
Location is a battery cost for the whole hourThe phone lasts the runSections 2 and 4.3

Your decision. The interviewer says: "Also add live sharing, route planning and a smartwatch." Which do you keep?

First idea, and why it fails. Say yes to all three. Each one is a second system, and time runs out before the "the app was killed in the middle of the run" path, which is the real hard part.

What I would say.

Say this. "Recording with the screen locked, a run that survives a kill, and a believable distance are in. Live sharing, route planning and a watch each add a system of their own, so they wait. Tell me if you want one earlier."

2. Data and contracts (minutes 4 to 14)

In short: Two local tables: the recording, and its raw points, written in small batches. The server gets the finished run once, under its recording id.

Your decision. Where does the route live while the run is going on? In memory, in a file you write at the end, or in a database as the points arrive?

First idea, and why it fails. A list in memory, saved when the user taps Stop. It is the shortest code. It also means a kill, a crash or a dead battery in minute 50 loses all 50 minutes. Android can stop an app in the background, and Apple says the system can terminate an app at any time.

What I would say. The phone keeps two tables:

  • Recordings: one row per run. Columns: recording id (a UUID made on the phone), state (recording, paused, interrupted, finished, uploaded), start time, end time, and the current segment number.
  • Points: one row per location fix. Columns: recording id, segment, sequence number, time, latitude, longitude, accuracy, and speed if the phone gives it. The key is (recording id, sequence number). Rows are only ever added, never edited.

The recorder saves points in small batches in one transaction, for example every 10 seconds. A crash can lose only the last batch. The screen reads the database and never keeps the route in memory only. I store the raw points and work out distance and pace from them, so I can fix the maths later without losing data.

The contract with my server has two calls:

  • Upload a run: the recording id, the summary, and the points in chunks of a few hundred. Each chunk has a chunk number.
  • List my runs: the finished runs for this account, newest first.

The recording id is made on the phone, so a retry sends the same id. The server uses it as a unique key, as in the idempotency keys guide, and a second send of the same chunk changes nothing. The server stores chunks by number, so a late or repeated chunk lands in the right place.

If the sign-in expires during upload, I refresh it once and resume from the last chunk the server confirmed, using the same recording id.

The follow-up question I expect:

"Why not upload points live, as they arrive?"

I can add it as a second path, but it cannot be the only copy. With no signal on a trail, live upload stalls, and I would still need the local database to survive. So the phone is the first copy and the server is the second.

3. Client structure (minutes 14 to 22)

In short: A recorder that is not a screen, a database in the middle, and screens that only read.

Your decision. Who owns the location stream? The recording screen, or something that lives as long as the recording?

First idea, and why it fails. The screen's ViewModel (the class that holds one screen's state) asks for location updates while it is visible. The user locks the phone and the updates stop. Android says a background app can receive location updates only a few times each hour, so a run recorded this way has a hole in it. On iOS, Apple says the system suspends most apps shortly after they move to the background, and a suspended app does not receive location updates.

What I would say. A recorder owns the stream, and it has two platform shapes:

  • Android: a foreground service with foregroundServiceType="location", which shows a notification while it runs. The manifest also needs FOREGROUND_SERVICE_LOCATION, and the app must have the location permission before the service starts. Android's docs say the system treats location access as foreground when an activity is visible or a foreground service is running.
  • iOS: the Background Modes capability with Location updates, a CLBackgroundActivitySession and a CLServiceSession, both created while the app is in the foreground. If the app is terminated and relaunched in the background, the session must be created again right away.

On iOS, these settings matter for a run recorder:

  • Add a usage description for When in Use location to Info.plist (NSLocationWhenInUseUsageDescription).
  • With the older CLLocationManager way, which also works before iOS 17, set allowsBackgroundLocationUpdates = true and enable the Location updates background mode.
  • Set pausesLocationUpdatesAutomatically = false. Its default is true, and the system may then pause updates during a run.
  • Set activityType = .fitness, and choose desiredAccuracy and distanceFilter to fit the sport.
  • While a background session runs, iOS shows a blue location indicator in the status bar. It plays the role of the Android notification. showsBackgroundLocationIndicator controls it for the older way.

The recorder does three things only: ask the platform for fixes, drop clearly bad ones, and save batches to the database. The screens (live map, stats, the finished run) read the database and show it. The recorder is the scoped owner of one recording, and the screens are only viewers.

Say this. "A recorder owns the location stream, a foreground service on Android and a background activity session on iOS. It saves points to a local database in small batches, and every screen reads from that database."

The follow-up question I expect:

"Does the app need the Always or background location permission?"

Not for this design, as I read the docs. The user taps Start while the app is open, and the recorder is a foreground service or a background activity session started from there. Android's docs say you cannot start a location foreground service from the background unless the app has the background permission, so I start it only from the visible app and avoid asking for "Allow all the time". That is easier for the user to accept, and Google Play limits background location to apps that need it for their core features. Apple says a background activity session also gives When in Use authorization. This is my reading of the docs, and I would test it on a real device on each OS version.

4. Make the hard part work (minutes 22 to 40)

In short: A recording is a small state machine on disk. Start only from the visible app, expect a kill, and treat every GPS point as a suspect.

4.1 Start, and keep recording with the screen locked (minutes 22 to 29)

Your decision. The user taps Start. What has to be true before the first point is saved, and what keeps the stream alive after the screen locks?

First idea, and why it fails. Request the permission, start listening, and hope. Permission can be missing or only approximate, location can be switched off, and the service may not be allowed to start. The first point never arrives and the user runs for 40 minutes before noticing.

What I would say. Check, then start, then confirm:

  • Check. Is location on? Is the permission granted? On Android 12 and newer the user can grant only approximate location (Android says about 3 square kilometres, against about 50 metres or better for precise). A run needs precise, so ask for it again with a clear reason, or refuse to start. On iOS the same case is reduced accuracy (accuracyAuthorization == .reducedAccuracy). Ask with requestTemporaryFullAccuracyAuthorization, or refuse to start.
  • Start. Write the recording row first with the state RECORDING. Start the foreground service from the visible app. Show the notification with a Stop button.
  • Confirm. The first saved point proves it works. If no fix arrives within a short time, say so on screen: "Waiting for GPS".

The notification needs the POST_NOTIFICATIONS permission on Android 13 and later. If the user denies it, the service still runs, but the notification is hidden, so ask with a reason.

Battery Saver also matters. Android's docs say that if getLocationPowerSaverMode() returns LOCATION_MODE_FOREGROUND_ONLY, the app keeps receiving updates while it runs a foreground service, even with the screen off. That is one more reason to be a foreground service and not a background task.

Say this. "Start is a check, then a recording row, then the service. The service runs with a notification, so the screen can lock. A recording has states, and every state is on disk."

The follow-up question I expect:

"How often do you ask for a location?"

As rarely as the sport allows. A run needs about one fix a second to draw a smooth line. A hike can use one every 5 seconds. A ride at speed needs more spread by distance than by time.

  • On Android, use FusedLocationProviderClient with a LocationRequest built as LocationRequest.Builder(Priority.PRIORITY_HIGH_ACCURACY, 1000), and add setMinUpdateDistanceMeters(...) for a ride or hike.
  • On iOS, set desiredAccuracy, distanceFilter and activityType = .fitness on CLLocationManager.
  • I would tune the exact values on real devices.

4.2 The app was killed in the middle of the run (minutes 29 to 35)

Your decision. At minute 50 the system kills the app. What does the user see when they open it again?

First idea, and why it fails. A new empty screen, because the route was in memory. Or a half-state where the app thinks it is recording but nothing runs, and the runner stops a run that was not recording for the last 10 minutes.

What I would say. The database remembers. On every app start the app asks one question: is there a recording whose state is RECORDING while no recorder is running?

  • If yes: show the run so far, with the time of the last point. Offer "Resume" and "Finish".
  • Resume: start a new segment. The old segment ends at the last saved point, and the new one begins at the first new point. Never draw a straight line across the gap, and never add the gap to the distance.
  • Finish: close the recording at the last point. The user keeps a shorter run, not nothing.

The same path covers the other interruptions. If the user turns location off or takes the permission away, the recorder marks the gap and shows a clear message, and the moment location is back it continues in a new segment. If the battery gets very low, the app can stop cleanly, save, and say so. I would not rely on the system restarting the recorder after a kill. On iOS I also do not count on a relaunch after the user force-quits the app.

Say this. "A kill is expected. The points are on disk in small batches, the recording still says RECORDING, and the next start finds it. The user can resume in a new segment or finish what we have. The gap is marked and never counted."

The follow-up question I expect:

"The user ignores the prompt and starts a new run. What now?"

Two recordings in RECORDING would confuse everything, so the app allows one. Starting a new run first asks about the old one: finish it, or discard it. The old one is never deleted without the user saying so.

4.3 Noisy points and a believable distance (minutes 35 to 40)

Your decision. You have 3,000 points for a 10 km run. How do you get the distance?

First idea, and why it fails. Add up the straight-line distance between each pair of points. GPS is not exact, so every point is a little off. At one point a second, a runner at 5 minutes a kilometre moves 3.3 m between points. If each segment gains only 1 m of noise, 3,000 segments x 1 m = 3,000 m, which is 3 km on top of 10 km. The run reads as 13 km.

What I would say. Clean the points, and do it after the fact, from the raw ones:

  • Drop bad fixes. Each fix comes with an accuracy estimate. On iOS a negative horizontalAccuracy means the fix is not valid. Drop points whose accuracy is worse than a limit, for example 50 metres. That is my starting number, to tune with real runs.
  • Drop impossible jumps. If the speed between two points is not possible for the sport (for a run, faster than a person can sprint), skip the point.
  • Count a new point only after a real move. Add distance only when the new point is further from the last counted point than the noise, for example 5 metres. Standing at a traffic light then adds nothing.
  • Never cross a gap. Distance is the sum inside each segment.

Because the raw points are on disk, I can change any of these numbers later and recompute old runs. If I had saved only a running total, a bug in the first version would stay in every run forever.

Say this. "I keep raw points and work out distance from them. I drop low-accuracy fixes and impossible jumps, I only count a move that is bigger than the noise, and I never add a gap. The numbers are starting values that I tune with real runs."

The follow-up question I expect:

"Why not use the speed the phone gives you, instead of positions?"

It is a good second signal. The platform often reports speed with each fix, and speed is smoother than position. But it can be missing or wrong when the signal is poor, so I use it to check positions, not to replace them.

The follow-up after that: "The user crosses a time zone, or the phone clock changes during the run."

  • I store each point's time as UTC, and the time zone at the start for display.
  • I take elapsed time from the fix times, not from the wall clock. A clock change then adds or removes no running time.
  • A run that spans midnight or a clock change is still one run, with one recording id.

5. Break it, ship it, roll it back (minutes 40 to 45)

In short: Each failure ends in a run the user can keep, with the gap shown. Never a lost run and never a silent hole.

Privacy:

  • A route shows where the user lives and works. Treat it as sensitive data.
  • Let the user delete a run, on the phone and on the server.
  • Offer to hide the start and end of a shared route, a privacy zone.
  • Fill in the Play data safety form and the Apple privacy labels for location.

Releases:

  • A recording bug ships to everyone, and a lost run cannot be re-run. A staged rollout can be halted, but installed copies keep the version they have, as in the chat app case.
  • The filter numbers (accuracy limit, jump limit, minimum move) can come from a remote flag, and recomputing a run from raw points means a better filter fixes old runs too.
  • I would watch: runs that end as "interrupted", runs with a gap, the share of recordings where the first point takes over 30 seconds, upload failures, and battery use per hour of recording.

Say this. "The phone is the first copy and the server the second. A run survives a kill, a revoked permission and a bad upload, and the user always sees what happened. I left out sharing, route planning and the watch."

6. Follow-ups that change a constraint

In short: Each follow-up changes one constraint. A strong answer says what breaks.

Practice prompts, not a claim about what any interviewer asks.

  • Make it a 10 hour hike. Strong: lower the rate and spread points by distance, batch more, cap the notification work, and check the file size: 10 hours at one point every 5 seconds is 7,200 points, about 288 KB at 40 bytes. Weak: keep one fix a second for 10 hours.
  • Add live sharing. Strong: a second path that sends the latest point when the network exists, while the local database stays the first copy. Weak: send every point and drop it if the network fails.
  • Add auto-pause. Strong: detect "not moving" from the filtered speed over a short window, and pause the clock and not the recorder. Weak: pause when one fix looks still.
  • Add a smartwatch. Strong: the watch can be the recorder, and the phone merges two sources by time. Weak: run both and add the distances.
  • The user says the distance is wrong. Strong: raw points are on disk, so I can replay the run and show the dropped points. Weak: "GPS is not exact."
  • Two phones, one account. Strong: runs are keyed by their own recording id, so both appear once in the list. Weak: a shared "current run" on the server.

7. What changes by level

In short: As I read it, the levels differ in who raises the problem: the interviewer, the candidate, or the candidate with a rollout plan.

These levels are my own reading of public prep material, not any company's rubric.

  • Mid-level: Start and stop, a service for the background, a local save and an upload. I want to hear: "The screen cannot own the recording."
  • Senior: A state machine on disk, batched writes, recovery after a kill with a gap, permission cases, and filtered distance. I want to hear: "The database is the memory of the run, so a kill costs seconds, not the run."
  • Staff: Raw points kept so the maths can improve, filters behind a flag, battery and interruption metrics, the cost of the background permission, and a plan for watch and live sharing. I want to hear: "Here is what I would watch, and here is the flag that changes the filter."

Common weak answers. These repeat across public prep material. They are not a dataset.

  • Keeping the route in memory until Stop.
  • The screen owning the location updates.
  • Asking for "Allow all the time" without a reason.
  • Adding up raw distances with no filter.
  • No plan for a kill or a permission change.

Test yourself

In short: Seven questions from this case. Answer each one out loud first, then open the answer.

1. Why can the recording screen not own the location updates?

When the screen locks, the app goes to the background. A background app on Android gets location updates only a few times each hour, and on iOS the system suspends most apps shortly after they move to the background. A recorder (a foreground service, or a background activity session) keeps the stream alive and the screen only reads the saved points.

2. Why save points to a database in small batches, and not keep a list and save at Stop?

The system can kill the app at any time. Points kept only in memory are lost with it. A batch every few seconds in one transaction means a kill costs at most the last batch, and writes stay cheap on the battery.

3. Does this app need the Always (background) location permission?

As I read the docs, no. The user taps Start while the app is open, and a foreground service or background activity session carries on from there. Android says a location foreground service cannot be started from the background without the background permission, so the app starts it only from the visible app.

4. The app was killed at minute 50. What does the next start do?

It looks for a recording that still says RECORDING while nothing is running. It shows the run so far and offers Resume or Finish. A resume starts a new segment, so the gap is marked, never drawn as a line and never counted as distance.

5. Why store raw points and work out distance later?

The distance maths and the filter numbers will be wrong at first. With raw points on disk, I can change them and recompute every old run. If only a running total was saved, a bug would stay in every run.

6. Why can a 10 km run read as 13 km, and what do you do?

At one point a second, points are only about 3.3 m apart, so small errors add up. If each of 3,000 segments gains 1 m of noise, that is 3,000 m extra. Drop low-accuracy fixes and impossible jumps, and add distance only for a move bigger than the noise.

7. What does an iOS run recorder need to keep recording with the screen locked?

The Background Modes capability with Location updates, plus a CLBackgroundActivitySession and a CLServiceSession, both created while the app is in the foreground. If the app is relaunched in the background, it must create the session again right away.

Verification notes (last reviewed 16 Oct 2026)

What I checked in official docs.

  • Android location permissions: foreground access means a visible activity or a running foreground service. Approximate location is about 3 square kilometres and precise is about 50 metres or better. A foreground service of the location type needs the type declared. With location Battery Saver in foreground-only mode, a foreground service keeps getting updates with the screen off.
  • Android foreground service types: the location type needs FOREGROUND_SERVICE_LOCATION. You cannot start a location foreground service from the background without the background permission.
  • Android background limits: on Android 8 and later a background app gets location updates only a few times each hour.
  • Apple background location article: the system suspends most apps soon after they go to the background. Enable the Location updates mode and create a CLBackgroundActivitySession. Create a CLServiceSession in the foreground, and create it again right away if the app is relaunched in the background. The system can terminate an app at any time.

What I did not verify.

  • Apple's own CLBackgroundActivitySession page did not load. The iOS settings in section 3 come from my knowledge of Core Location, not from a page I read.
  • Whether Android restarts a location service after the system kills it.
  • The exact location request values, and phone-maker battery limits on top of Android.
  • That a recorder started from the visible app needs no background permission. It is my reading. Test it on real devices and each OS version.
  • No iOS engineer has reviewed this page.
